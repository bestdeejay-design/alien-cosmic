### 1.2. Сервер (ace-save, gostiny-prod-01, `/opt/ace/server`, health v5)

- `server/save-server.mjs`: **node:sqlite, ноль зависимостей**, БД `/data/saves.db` (том контейнера).
- Таблицы: `saves(player,key,value,ts, PK(player,key))`, `players(nick,pin_hash,created)`,
  `schema_floor(player,key,floor,ts)`.
- Пин: `sha256(nick_lower:pin)` (быстрый хеш, без соли/KDF — см. §3.3).
- Ручки: `/api/save`, `/api/load`, `/api/list` (без пина — только ключи/время), `/api/top`,
  `/api/grant` (ADMIN_PIN), `/api/delete`.
- Уже есть серверные барьеры (в исходнике в git): schema-floor (409 на запись ниже планки,
  ace#10), rate-limit пина, канонический ник.
- **Важно (честно): серверного реестра сессий С2 в git НЕТ.** `server/save-server.mjs` не
  содержит ни `/api/session/start|beat|end`, ни таблицы `sessions`, ни флага `sessions` в
  `/health` — то есть С2-ручки живут только в продовом контейнере ace-save (health v5),
  канонический исходник прод-сервера из репозитория недоступен. Клиент (r/save-client.js)
  при этом С2-логику уже реализует (фича-детект по `/health {sessions:true}`).
- **Предэтап Фазы 1 (блокирующий): извлечь канонический исходник продового сервера из
  контейнера `/opt/ace/server` в git** (сверить с health v5), зафиксировать дифф git vs прод.
  Без этого любая правка сервера = правка по памяти.
- Нагрузка: зелёная зона 200–300 онлайна, потолок ~350–400 зап/с на связке nginx+node
  (SCALING_SAVES §2; узкое место — записи, не SQLite).

### 1.3. Щели для подделки (threat model)

| # | Угроза | Вектор | Суть |
|---|---|---|---|
| T-1 | **Правка localStorage** | DevTools на своей машине | Клиент читает сейв из `localStorage` и пушит его на сервер как есть; сервер хранит строку `value` без проверки содержимого. Игрок пишет себе `raidSeq:999`, кредиты, уровень КЦ — сервер примет |
| T-2 | **Подмена DTO / curl** | POST /api/save напрямую | Пин — единственная защита. Пин знают все устройства игрока; скомпрометированный/подобранный пин даёт полную запись произвольного JSON. Сервер не знает, «честный» ли клиент сформировал value |
| T-3 | **raidSeq-guard клиентский** | отключить JS-проверку | Монотонность raidSeq проверяет **клиент** (`save-client.js:592`); свой клиент её просто не содержит. Сервер raidSeq не сверяет (кроме schema-floor) |
| T-4 | **Replay** | повтор старого запроса | Нет ни nonce, ни подписи: перехваченный (или повторно сыгранный самим игроком) валидный запрос со старым value+пином перезапишет свежий сейв (ts подделывается полем `ts` в теле — сервер берёт `Number(ts) || now`, `save-server.mjs:198`) |
| T-5 | **Гонка двух браузеров** | две вкладки/машины | Частично закрыта С2 (токен+зритель+409), НО: без С2-сервера (фича-детект `/health {sessions}`) гонка вернулась бы к LWW по ts, а ts — клиентское поле (см. T-4) |
| T-6 | **Пин слабый** | перебор | Пин 3–12 цифр (`PIN_MIN..PIN_MAX`), без соли: офлайн-брутфорс по утёкшей БД дешёв (10^3–10^12 вариантов) |
| T-7 | **Внешние каналы** | lovii-туннель, гист/PAT-каналы в коде | `EXT_API` и gist-ветки (`save-client.js:50–75`) — альтернативные хранилища вне БД и вне будущей валидации; PAT лежит в localStorage |

**Вывод:** сегодня сервер — «тупое строковое хранилище с пином». Любая честность значения
делегирована клиенту. Цель плана — перенести доверие на сервер поэтапно, не сломав
офлайн-игру и текущий зелёный контур (200–300 онлайна, payload ~20 КБ, автосейв 1,5 с).

## 2. Предложение

### 2.1. БД: остаёмся на SQLite (не Postgres)

- Сервер — лёгкий Node-контейнер с **нулевыми зависимостями** (канон проекта); `node:sqlite`
  уже в бою и по нагрузочному тесту не является узким местом. Postgres — только по Этапу 2
  SCALING_SAVES (500+ одновременных), не сейчас.
- Обязательные настройки: `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, батч-запись раз в 1 с
  (уже рекомендовано SCALING_SAVES §3 этап 1).
- Схема (миграция, см. §2.4): добавляются таблицы `sessions`, `audit_log`, `user_meta`,
  `save_history` (последние N=20 значений per (player,key), решение владельца);
  в `saves` — колонки `schema` (дублируем floor для скорости), `seq` (монотонный серверный
  счётчик записи per (player,key)).

### 2.2. Серверная валидация сессий

- На проде токен выдаёт сервер (С2, health v5), но в git-исходнике ручек нет (см. §1.2), фича
  опциональна (фича-детект) и сам save может пройти без токена («С1-совместимость»). План:
  после переноса исходника в git — `SESSIONS_ENFORCE=1` на проде: **запись в профиль без
  валидного токена отклоняется** (401/409), токен привязан к (player, device, выдаче по пину).
  Токен живёт до end/таймаута; beat 60 с уже есть в клиенте.
- **Порядок включения — строгий:** (1) сначала новый клиент, который умеет обрабатывать
  session-отказ (401/409), со стемпом в ОБА места деплоя (Pages + rsync `/opt/ace/game`);
  (2) по audit_log Фазы 1 убедиться, что старых клиентов в трафике нет; (3) только потом
  enforce. Включать enforce раньше — значит молча сломать сейв старым клиентам: текущий
  клиент (`save-client.js`) не различает session-отказ от сетевого сбоя (замолчит или
  закольцует ретраи).
- Пин при каждом запросе (сейчас) → оставить на переходный период, затем перевести на
  токен после первого входа (пин перестаёт летать в каждом биде/биконе).

### 2.3. Анти-чит модель (что сервер проверяет сам)

| Проверка | Правило | Закрывает |
|---|---|---|
| **raidSeq monotonic** | сервер хранит `meta.raidSeq` записи `ac_raid_session_v1`; вставка с seq < сохранённого → 409; seq должен расти ≤ +K за окно времени (аномалия). **Ограничение:** защищает только базу рейда | T-1 (частично), T-3 |
| **история версий + restore** | сервер хранит последние **N** значений per (player,key) (таблица `save_history`); админ-restore по решению владельца. Закрывает главный остаточный чит: `terranrts.progress` / `terranrts.quickBattle` остаются LWW-строками — raidSeq их не защищает, и под «легитимный» новый пуш можно записать старое содержимое (откат прогресса). История + monotonic-инварианты (ниже) делают откат обнаружимым и обратимым | T-1, T-2 (откат прогресса) |
| **monotonic-инварианты progress (валидатор)** | для `terranrts.progress`/`terranrts.quickBattle` сервер сверяет ключевые поля с предыдущей версией: credits, ccLevel, hqLevel (и перечень по мере экономики) **только растут**; падение → 409 (или флаг на ревью в audit_log, пока порог калибруется) | T-1, откат прогресса |
| **строгий пер-ключ seq** | серверный счётчик записи per (player,key) (`saves.seq`): принимается ТОЛЬКО `client_seq = server_seq + 1` (или без seq для совместимости в переходном окне, флаг); старые значения не проходят | T-4, T-5 |
| **server ts** | поле `ts` из тела игнорируется; сервер ставит своё `Date.now()` | T-4 (частично) |
| **лимиты значений** | per-key размер (сейчас глобально 4 МБ — ужесточить: raid-снапшот ≤256 КБ, journal cap 60 записей проверяется сервером по JSON), whitelist ключей на запись = **SYNC_KEYS из `save-client.js:24`** (`r.progress`, `r.quickBattle`, `ac_raid_session_v1`) + служебные (`ac_stats`, `ac_grant`); пин **4–12 цифр** (решение владельца: минимум 4, не 6; максимум 12) | T-1, T-2 |
| **schema-floor** | уже есть — сохранить | даунгрейд клиента |
| **структурный валидатор** | для ключа `ac_raid_session_v1`: обязательные поля, диапазоны (credits ≥ 0, ccLevel 1..MAX, hp 0..max) — серверный «косяк», расширяется по мере экономики | T-1, T-2 |
| **подпись (опционально, поздно)** | HMAC(value, server-secret) на выдаче — детект сторонних записей, но НЕ защита от самого игрока (секрет в клиенте не хранится, подписывает сервер свою выдачу для integrity-зеркала) | целостность зеркала |
| **rate-limit** | уже есть по пину; добавить 1 req/s на IP на /api/save (SCALING_SAVES §3) | брут/флуд |

**Открыто и честно:** полный запрет отката progress достигается комбинацией
«история N + monotonic-инварианты + строгий seq», а не одной проверкой. Пороги падений
(например, легальный спенд кредитов между сейвами) калибруются на статистике Фазы 1 —
инварианты в Фазе 2 сначала пишут в audit_log, потом начинают отклонять.

Честно фиксируем границу: **клиент нельзя сделать честным** (весь код открыт в браузере).
Достигается: невозможность отката (monotonic), невозможности мусора (валидатор/лимиты),
кража чужого профиля — только через пин (KDF+rate-limit). Полную серверную экономику
(«начисляет сервер») — вне этого плана, отдельный этап при мультиплеере (R2_NETWORK).

### 2.4. Модель миграции с текущего JSON-хранилища

Существующая БД — уже SQLite, «миграция» = расширение схемы без остановки:

1. **Обратная совместимость чтения**: сервер v+1 читает старые строки (value = сырая строка)
   и пишет новые колонки при первой валидной записи. Строки без `seq` получают seq = rowid.
2. Клиент меняется минимально: игнорировать поле `ts` в теле (сервер и так), уважать
   серверный `seq`, обрабатывать новый 409-код `seq conflict` как уже делает для schema floor
   (плашка «обновите страницу», заморозка повторов — путь есть, `raiseSchemaFloor`).
3. Гист/lovii/PAT-каналы: объявить устаревшими (читают, не пишут), затем удалить —
   иначе T-7 остаётся. Требует решения владельца (вопрос 3).

## 3. Поэтапный план

### Фаза 0 — предэтап (блокирует Фазу 1)

Извлечь канонический исходник продового сервера из контейнера `/opt/ace/server` в git
(§1.2), зафиксировать дифф git vs прод, дамп БД до любых правок.

**Критерии приёмки:**
- [ ] исходник прод-сервера в git, health-версия и ручки совпадают с продом (v5);
- [ ] дамп продовой БД сделан и проверен восстановлением на стенде.

### Фаза 1 — read-only зеркало (без риска)

Сервер пишет каждую принятую запись в журнал `audit_log(ts, player, key, bytes, seq, ip?)`;
отдельная команда/эндпоинт (ADMIN_PIN) строит отчёт: частота записей, скачки raidSeq,
размеры, аномалии, **доли версий клиента**. Ничего не отклоняем — только измеряем.
Ожидаемый объём: 200 онлайна × ~40 зап/мин (автосейв 1,5 с с дедупом) = ~8 000 зап/мин
≈ **480k записей/час** метаданных (~40–60 байт/строка → ~25–30 МБ/ч) — предусмотреть
ротацию/агрегацию, а не вечное хранение сырых строк.

**Критерии приёмки:**
- [ ] audit_log пишется на проде, размер соответствует расчёту (480k/ч на 200 онлайне), ротация настроена;
- [ ] отчёт показывает реальные распределения raidSeq/размеров и **версии клиентов** (базовая статистика для порогов Фазы 2 и решения об enforce);
- [ ] полный регресс зелёный; нагрузка на клиент не изменилась (0 новых запросов);
- [ ] дамп БД до включения сделан и проверен восстановлением;
- [ ] права на бэкап-хост зафиксированы: WAL-архивы и дампы лежат открытым текстом и содержат несолёные пин-хеши до Фазы 2 — доступ к хосту ограничен, в отчёте/доках это отмечено как принятое ограничение переходного периода.

### Фаза 2 — серверная валидация (отклоняем мусор)

Включаются: server-ts (игнор клиентского ts), whitelist ключей, лимиты размеров,
raidSeq monotonic 409, структурный валидатор v1 (только очевидное: отрицательные числа,
schema ниже floor — уже есть), история версий сейвов **N=20** per (player,key) + админ-restore
(доступ — только владелец), пин 4–12 цифр для новых профилей, **вывод легаси-каналов
(гист/lovii/PAT)**, SESSIONS_ENFORCE=1 на проде (строгий порядок §2.2), pin_hash → scrypt (KDF) с
ленивой перекачкой при входе. Пороги аномалий — из статистики фазы 1.

**Критерии приёмки:**
- [ ] curl-подделка: `POST /api/save` с raidSeq < серверного → 409; с отрицательными кредитами → 400; с чужим ключом → 400; с повтором старого value progress (падение ccLevel/credits) → 409/флаг;
- [ ] **старые клиенты обнаружены по audit_log ДО включения enforce** (порядок §2.2: новый клиент в оба места → zero old clients в трафике → enforce);
- [ ] запись без валидного токена → отказ (два браузера: второй — зритель, прогресс первого не теряется — сценарий ace#6 зелёный);
- [ ] история версий: последние N значений per (player,key) доступны админ-restore, восстановление откатывает ровно на шаг;
- [ ] офлайн-конфликт UX: при расхождении локал/сервер локальная база уходит в гостевой бэкап, игрок получает тост («прогресс сохранён локально, серверная база загружена»), а не молча отброшенная очередь пушей;
- [ ] брутфорс пина по утёкшей БД дороже 10^6 попыток на пин (scrypt);
- [ ] p95 /api/save на 200 онлайна ≤ 400 мс (базовый замер SCALING_SAVES: 388 мс) — валидация не просела;
- [ ] известный флейк-регресс и 17 симов + u/v_verify зелёные.

### Фаза 3 — БД как канон-хранилище

`localStorage` понижается до кэша: истина входа — сервер (уже так по духу — `pullSnapshot`
перезаписывает локал без сравнения, `save-client.js:762–765`), добавляется: серверный `seq`
в ответах и сверка на клиенте, авто-recovery при расхождении (сервер канон, локал — бэкап
в гостевой ключ). Внешние каналы (гист/lovii/PAT) удалены (решение владельца: вывод в Фазе 2,
к Фазе 3 они уже не существуют). Бэкап-цепочка: hourly WAL +
сутки-дамп на второй сервер.

**Критерии приёмки:**
- [ ] сценарий «два браузера один профиль»: активный пишет, второй — зритель, после клейма оба видят одну базу, потерь нет;
- [ ] сценарий «потеря сейва»: очистка localStorage на живом профиле → полная реконструкция из БД при входе;
- [ ] сценарий «офлайн»: игра без профиля/сети работает локально, при появлении сети — reconcile без отката сервера;
- [ ] CDN-кэш: /api/* и /health отдаются с `Cache-Control: no-store` (уже есть — проверено) и nginx не кэширует; статика — да;
- [ ] бэкапы: восстановление суточного дампа на стенде даёт рабочий профиль за <10 мин;
- [ ] документация обновлена (r/README.md, HANDOFF.md), письмо поставки с диапазоном коммитов.

## 4. Риски

| Риск | Митигация |
|---|---|
| Два браузера один профиль | С2 уже решает (токен+зритель); фаза 2 делает её обязательной (SESSIONS_ENFORCE по строгому порядку §2.2); откат — история-N + monotonic-инварианты + строгий seq (§2.3) |
| Потеря сейва при миграции | дамп до включения; фазы включаются фича-флагами env (по образцу ALLOW_SCHEMA_DOWNGRADE-килл-свитча); канал отката — старая строка в saves остаётся нетронутой |
| CDN-кэш отдаёт старый клиент | /api/* no-store (уже); версию статики поднимать стемпом (канон деплоя: Pages + rsync оба места разом) |
| Офлайн-игра | игрок без профиля играет локально как сейчас (канон A2 «без профиля ноль запросов»); профиль+офлайн = очередь пушей с единым raidSeq-guard сервера — при расхождении сервер канон, локал в гостевой бэкап |
