## 1. Запрос владельца

> «У нас адаптивная игра, и игра на большом экране сильно отличается. А ты и Арена всё пихаете
> в один экран — и крестики для мобильки, и кнопки зума. Надо определять, что для каких экранов
> нужно, точно разделять и уметь управлять этими состояниями.»

Процесс, которого требует владелец: **аудит → ресерч → выводы и варианты → код**. Документ —
результат первых трёх шагов. Четвёртый шаг (код) начинается только после выбора варианта.

### Что уже закрыто до этого аудита (пакет T, 6eee47f)

Три бага из мобильной сессии владельца устранены и запушены: тап-приказ с контекстной
семантикой (выделение/приказ/двойной-снятие), дрейф камеры на старте (три пути: гвард
compat-мыши, sentinel, sleepMouse на старте миссии), guard отрисовки (`[draw-skip]` — сбойный
элемент пропускается с диагностикой вместо чёрного экрана). Полный регресс зелёный. Этот
аудит — следующий виток: не «починить сломанное», а **навести системный порядок в состояниях
экрана**.

## 3. Ключевое наблюдение: две ортогональные оси, а не одна

Сейчас всё адаптивное пропущено через **одну ось — геометрию окна** (`max-width`,
`orientation`, `max-height`). Но у «что для каких экранов» есть **две независимые оси**:

| Ось | Что определяет | Примеры решений | Чем мерить |
|---|---|---|---|
| **Геометрия** (сколько места) | плотность, иконизация, раскладка панели, размер миникарты | topbar в иконки ≤560px portrait; компакт-панель в коротком ландшафте; колонки cmd-grid | `@media` по размеру — уже работает |
| **Профиль ввода** (чем управляют) | набор афордансов: чем зумить, как отменять, какие подсказки, какие приказы доступны | зум-кнопки vs колесо; × отмены vs ПКМ/Esc; хинты «тап» vs «ЛКМ»; kbd-метки | media `(pointer)`/`(hover)` + события ввода + выбор пользователя |

Геометрия сейчас меряется честно. Профиль ввода — **размазан по шести местам**, и в каждом
решается по-своему (§5). Отсюда и ощущение владельца «всё пихаете в один экран».

Побочный эффект одноосности: на **десктопе с узким окном** (пол-экрана) игрок получает
«мобильные» афордансы — иконки-крестики topbar, компакт-панель с крестиками `panel-hide` —
хотя управляет мышью. И наоборот: геометрия ничего не знает о том, что у планшета
подключена мышь.

## 5. Как сейчас определяется среда (все точки)

1. **CSS**: 9 медиаблоков — только `max-width` / `orientation` / `max-height` +
   `prefers-reduced-motion`. Interaction-фичи (`pointer`, `hover`, `any-*`) не используются
   ни разу.
2. **`js/ui.js:1409`** — `matchMedia('(pointer: coarse)')` для текста хинта выделения.
   Единственное место с профилем ввода.
3. **`js/ui.js:996`** — `matchMedia('(orientation: landscape) and (max-height: 520px)')`
   для компакт-панели (геометрия, легитимно).
4. **`js/ui.js:1562, 1829`** — `event.pointerType === 'touch'` для тултипов (поведенческая
   детекция на событии — легитимно, но локально).
5. **`js/input.js:50`** — `isCompatMouse` через `sourceCapabilities.firesTouchEvents` +
   гео-фолбэк (гвард T2, легитимно).
6. **`js/input.js:68`** — `e.pointerType !== 'touch'` как гейт всего жестового FSM.

**Вывод по разделу:** решения о профиле ввода принимаются в шести местах тремя разными
механизмами (media query по primary input, pointerType конкретного события, гвард
синтетики). Нет источника правды, нет способа спросить «а какой сейчас UI-режим?», нет
способа форсировать режим (ни кодом теста, ни пользователем). CSS о профиле ввода не знает
вообще — поэтому всё, что нужно прятать по профилю, либо показывается всем, либо
обрабатывается JS-точечно.

## 6. Ресерч: что говорит индустрия

### 6.1 Interaction media features — возможности и ловушки

- `(pointer: coarse|fine)` и `(hover: hover|none)` описывают только **первичное** устройство
  ввода браузера. На планшете с подключённой мышью `pointer` может остаться `coarse` —
  браузер решает сам, что «первично».
- `(any-pointer)` / `(any-hover)` сообщают о **любом** из устройств: планшет с мышью даёт
  одновременно `any-pointer: coarse` и `any-pointer: fine`. Порядок media-запросов важен.
- Первичный ввод **меняется динамически** (подключили/отключили мышь, клавиатуру-чехол) —
  media-запросы сами переоцениваются, JS-состояние надо обновлять по `change`.
- Прямая рекомендация web.dev/css-tricks: **давать пользователю явный выбор** раскладки
  «тач/мышь», не полагаться только на медиафичи; не прятать функции по `pointer: coarse`
  (ловушка «коарс = глупый телефон»).
- Источники: css-tricks «Interaction Media Features… Incorrect Assumptions», web.dev
  learn/design/interaction, Smashing Magazine «A Guide To Hover And Pointer Media Queries».

### 6.2 Паттерны мобильных RTS

Разбор ввода открытого RTS-девлога (Ashley, Construct) даёт жестовую карту: «тап по юниту —
выделить; тап по пространству — приказ выделенным; свайп одним пальцем от юнита — рамка;
щипок — зум; перетаскивание — камера». **Это один в один наша FSM из пакета T** (tap /
context / box / pan / pinch). Значит:

- Жестовая база канонична, трогать её не нужно — индустрия подтверждает.
- Различия между играми — не в жестах, а в **афордансах**: что показывать на экране, чтобы
  жесты были открыты (кнопка deselect, кнопка режима атаки, зум-пиктограммы, подсказка
  первого запуска). У нас deselect уже решён (двойной тап по пустому + одноразовый тост);
  атака-движение — не решён вовсе.

### 6.3 Мост состояния JS↔CSS

MDN и практика фреймворков: UI-состояние, вычисляемое в JS, удобно выставлять **data-атрибутом
/ классом на корне** (`<html data-input="touch">`), а CSS выбирает оформление селекторами
от атрибута. Это устраняет дублирование детекции и делает состояние видимым в DevTools и в
тестах. Внутри проекта тот же приём уже применён для состояний документа
(`body.panel-left`, `body.menu-active`, `body.screen-modal-open`) — мы не вводим новый
паттерн, а договариваемся о втором осмысленном атрибуте.

### 6.4 Внутренние обязательства проекта

`design/UX_RESEARCH.md`: «hover не должен быть единственным каналом» (строка 40) и «P2:
пинг на touch — отдельная кнопка/режим, не скрытая комбинация» (строка 141). Системный
профиль — прямое продолжение этих принципов: каждая функция должна иметь афорданс в
каждом профиле.

## 7. Выводы аудита

- **В1. Жесты тача каноничны.** FSM пакета T совпадает с отраслевыми картами жестов
  мобильных RTS. Пересмотр не нужен; ресерч подтверждает выбранную семантику тапа.
- **В2. Проблема — в афордансах, а не в жестах.** Пять контролов не имеют правила «в каком
  профиле я нужен»: зум-кнопки, × отмены, kbd-метки — показываются всем; атака-движение —
  недоступно тачу; хинты — единственный профильный пункт, и тот по первичному вводу.
- **В3. Профиль ввода — сирота.** Шесть разрозненных механизмов, ноль централизованности:
  нельзя спросить, нельзя форсировать, нельзя протестировать в симе, CSS не участвует.
- **В4. Гибриды не обработаны.** Ноутбук с тачскрином, планшет с мышью, Windows-планшет с
  клавиатурой: первичный ввод лжёт, а выбор пользователя отсутствует. Ресерч прямо
  рекомендует явный override.
- **В5. Дыра способности.** Атака-движение есть только на клавиатуре. Это не вопрос стиля:
  тач-игрок лишён боевой механики. Закрывается кнопкой в cmd-grid (афорданс), не жестом.
- **В6. Две оси надо развести.** Геометрия (плотность/иконки) остаётся в `@media`.
  Профиль ввода (чем зумить/отменять/подсказывать) переезжает в управляемое состояние.
  Смешение осей даёт артефакты «мобильных крестиков на десктопе с узким окном».

## 8. Варианты решения

### Вариант A — CSS-only: добавить interaction-запросы

`@media (hover: none) and (pointer: coarse)` вокруг зум-кнопок/крестика/kbd, медиазапросы
рядом с геометрическими. JS не трогаем.

- **Плюсы:** минимальная работа (~50 строк CSS), нулевой риск логики.
- **Минусы:** детекция по первичному вводу лжёт на гибридах; override невозможен; сим не
  может форсить режим; состояние невидимо и неуправляемо («уметь управлять состояниями» не
  выполняется). Полумера, через полгода дорастёт до варианта B с миграцией на ходу.

### Вариант B — ScreenProfile: единый источник правды (рекомендация)

Новый модуль `js/ui/profile.js` (+ тонкая интеграция):

```
сигналы:  matchMedia(pointer/hover/any-*) + события реального ввода
          (первый keydown / pointerType на канвасе) + выбор пользователя
состояние: { mode: 'auto' | 'touch' | 'desktop',
             touchCapable, fineCapable, hoverCapable }
выход:    класс game-touch / game-desktop на <html>,
          data-input-атрибут, событие profilechange, API game.profile
```

- Все шесть точек §5 переводятся на `game.profile`: хинты, тултипы, зум-контролы, × отмены,
  kbd-метки; CSS получает ownership-правила (`.game-desktop #zoom-controls { display:none }`,
  `.game-desktop #placement-cancel { display:none }`, `kbd` скрыт в `.game-touch`) — и при
  этом геометрические `@media` остаются как есть.
- **Override пользователю** в «Ещё»: «Интерфейс: Авто / Телефон (тач) / Компьютер (мышь)»,
  хранится в localStorage рядом с `terranrts.panel`. Гибрид получает честный выбор;
  ресерч именно это и рекомендует.
- **Симулируема:** `game.profile.set('touch')` в тестах — sim_touch проверяет видимость
  афордансов в обоих режимах; на десктопе регресс ловит «всплывший» тач-контрол.
- **Миграция маленькими шажками:** профиль можно завести, не трогая жесты и не переписывая
  CSS сразу — каждый контрол переводится отдельным коммитом.
- **Плюсы:** единственная точка правды; гибриды и override; тестируемо; видимо в DOM;
  создаёт фундамент под будущие профильно-зависимые вещи (пинг P2, тач-подсказки,
  возможно отдельная тач-раскладка панели).
- **Минусы:** ~200–300 строк JS+CSS+тестов; нужна аккуратность с моментом переключения
  (не мигать контролами при случайном касании — решается гистерезисом/подтверждением).

### Вариант C — два поддерева HUD (полные варианты DOM)

Отдельные DOM-ветки тач-HUD и десктоп-HUD с общими оверлеями.

- **Плюсы:** максимальная свобода UX на каждом классе устройств.
- **Минусы:** дублирование всей разметки/локалей/тестов; для текущего размера HUD
  избыточно; каждое изменение приходится делать дважды. Оправдан только при кардинально
  разной раскладке, чего сейчас не требуется.

### Сравнение

| Критерий | A (CSS-only) | B (ScreenProfile) | C (два HUD) |
|---|---|---|---|
| Стоимость | ~50 строк | ~250–300 строк + тесты | ~1000+ строк |
| Гибриды (планшет+мышь) | лжёт | честно + override | честно |
| Управление состоянием | нет | класс/атрибут/событие/API | то же, × 2 сложности |
| Тестируемость | слабая | сим форсит режим | сим, но × 2 объём |
| Риск регресса | низкий | низкий (гварды уже есть) | высокий |
| Соответствие запросу владельца | частично | **да** | с запасом |
