# SCALING_SAVES.md — масштабирование сейв-канала (рекомендации)

Составлено координатором 28.10.2026 по запросу владельца («сколько выдержит
машина, что нужно для 20 000 игроков»). Основано на живом нагрузочном тесте
прода ace.dj1.ru. Пусть лежит — пригодится при росте аудитории.

## 1. Архитектура сейчас

- Игра (static): GitHub Pages + rsync-копия `/opt/ace/game` на gostiny-prod-01.
- Сейвы: `ace.dj1.ru/api/*` → nginx → контейнер **ace-save** (`node:sqlite`,
  ноль зависимостей) → SQLite `/data/saves.db` (том).
- Клиент (r/raid-boot.js): автосейв каждые **1,5 с** только в home-режиме +
  события (запуск/финиш вылетки, скрытие вкладки, уход). Дедуп: неизменённый
  снимок не пишется (сравнение с игнорированием метки capturedAt).
- Payload одного профиля: ~20 КБ (снапшот базы + журнал экспедиций, cap 60 записей).
- Защита: raidSeq-guard от затирания свежей базы старой сессией.

## 2. Замеры (нагрузочный тест 28.10.2026, боевой сервер gostiny-prod-01)

Стенд: 16 vCPU / 31 ГБ (машина общая с 52 контейнерами lovii, занята ~10%).
Каденция реальная: 1 запись / 1,5 с на клиента, payload 20 КБ, через боевой nginx.

| Одновременных игроков | зап/мин | Ошибки | p50 | p95 | CPU сервера |
|---|---|---|---|---|---|
| 10 | 366 | 0 | 88 мс | 281 мс | ~0 |
| 50 | 1 852 | 0 | 86 мс | 262 мс | +3% |
| **200** | 7 220 | **0** | **80 мс** | **388 мс** | **+5%** |
| 500 | 11 644 | 71 (0,6%) | 296 мс | 2 с | +7%, пики 35 с |

Выводы теста:
- **Зелёная зона: до ~200–300 одновременных игроков** (≈150–180 записей/с).
- Потолок ~500: первые отказы на связке nginx+node (очередь соединений),
  НЕ в SQLite — БД справлялась легко.
- Диск: профиль перезаписывается по месту (~20 КБ); 1 000 игроков ≈ 20–40 МБ.

## 3. Целевая точка «20 000 игроков»

20 000 зарегистрированных ≈ **1 000–2 000 одновременных** (5–10% DAU в прайм).
Худший случай: 2 000 × 0,7 зап/с = 1 400 записей/с ≈ 28 МБ/с — «в лоб» текущая
схема не выдержит (тест показал потолок ~350–400 зап/с), лечится конфигурацией:

### Этап 1 — бесплатно, делать можно сразу
1. **Клиентский троттлинг пуша: 1,5 с → 5–10 с** (dedyт уже есть). Снижение
   ×3–5. Одна константа в r/raid-boot.js.
2. **WAL-режим SQLite** на сервере (`PRAGMA journal_mode=WAL`) — очередь
   записи перестаёт блокировать чтения.
3. **Батч-запись** на ace-save: копить пуш и писать транзакцией раз в 1 с.
4. **Бэкапы по расписанию**: hourly-архив WAL + суточный дамп на второй
   сервер (задача ace#3 уже открыта).
5. **Мониторинг**: p95 latency /api/save, ошибки 5xx, размер БД — в watcher
   с тревогой.

После этапа 1: 2 000 онлайна ≈ 300–500 зап/с — внутри зелёной зоны.

### Этап 2 — при 500+ одновременных
6. **SQLite → PostgreSQL** (или 2 шарда SQLite по хешу профиля).
7. **Второй инстанс save-server** за nginx (stateless — масштабируется
   горизонтально, БД общая).
8. **Rate-limit nginx**: 1 req/s на IP на /api/save (аномалии/абьюз).
9. **Выделенный сервер под сейвы**: 4–8 vCPU / 16–32 ГБ / **NVMe** (диск
   важнее CPU — узкое место синхронная запись). Hot-standby + репликация —
   по факту появления аудитории.

### Этап 3 — дальше (не требуется до десятков тысяч онлайна)
10. Read-реплики для /api/list / топов, кэш профилей в памяти, CDN для статики
    уже есть (Pages).

## 4. Ответ на вопрос владельца (коротко)

- **Сейчас** машина держит ~200–300 одновременных игроков без настроек.
- **Для 20 000 зарегистрированных** (≈2 000 онлайн): один выделенный
  NVMe-сервер 4–8 vCPU / 32 ГБ + этап 1 настроек — с запасом.
- Узкое место — **записи, не «мощность»**; лечится конфигурацией, а не железом.
