## Что такое <client> (по словам владельца и публичным материалам)

- Локальный маркетплейс районов: каталог товаров/услуг местных точек, доставка/шаговая доступность.
- **app.example.com** / **staging.example.com** — приложение покупателя: каталог, магазины, авторизация, профиль, PAY-карта, баллы.
- **b2b.example.com** / **b2b-staging.example.com** — кабинет МСП: данные торговой точки, вход телефон + код, passkey.
- **example.com** — публичный сайт: роли, тарифы, схема денег.
- Стартующий проект **без пользователей**, но с **боевой оплатой** в проде (<bank> «<acquiring>», 54-ФЗ, ККТ).
- **Staging с моками банка и касс** — основной полигон пилота.
- Баллы: **1 балл = 1 ₽**, не сгорают, тратятся у всех точек района, вывод через СБП.
- Комиссия не более <commission>%, пул <pool-card>% (карты) / <pool-sbp>% (СБП), сплит <split>;
  тарифы <tariff-1> <rate-1> до <limit-1>, <tariff-2> <rate-2>, <tariff-3> <rate-3> + <fee>/мес.

Источники: владелец (2026-11-11), публичные страницы example.com / app-staging / b2b-staging,
материалы лендинга <client> (репозиторий `<client>/`). Неподтверждённое — `TBD`.

## Классификация и режим

- **Домен:** финтех + маркетплейс + лояльность (баллы = деньги).
- **Режим пилота:** **Grey Box** на staging (нужны 2 аккаунта покупателя + аккаунт точки МСП).
  Black Box — как первый проход по staging и для прода (только публичное, без атак).
  White Box — отдельным scope, если дашь код.

## Ключевое ограничение, которое нужно понимать

Staging ≠ прод. На стенде другие конфиги, другие ключи, отключённые проверки, моки вместо банка.
Поэтому:

- Находки на staging **доказывают** ошибку в коде/логике, но не гарантируют, что она включена в проде.
- Прод может иметь **свои** отличия (реальные секреты, другой WAF, другой билд) — их staging не покажет.
- Формулировка в отчёте будет честной: «подтверждено на staging», «требует проверки в проде».

Это нормальная и правильная практика: сначала ломаем стенд, потом точечно подтверждаем на проде.
