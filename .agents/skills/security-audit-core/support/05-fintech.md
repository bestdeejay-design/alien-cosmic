# Финтех и около-финтех: риски и проверки

> Домен: платежи, кошельки, переводы, обмен, займы, страхование, биллинг, маркетплейсы с деньгами,
> любые сервисы, где есть **настоящие деньги, PII и регуляторные требования**.
> Здесь цена ошибки — деньги клиентов, штрафы и потеря лицензий/партнёрств.
> Комплект не заменяет юридическую и регуляторную консультацию.

## 1. Модель угроз

- **Мошенник:** кража средств, подмена получателя, обход KYC, отмывание.
- **Злоумышленник-инсайдер:** злоупотребление правами, доступ к чужим средствам.
- **Атакующий снаружи:** перебор, IDOR, инъекции, утечка секретов.
- **Партнёр/интеграция:** поддельные вебхуки, повторные уведомления, компрометация ключей.

## 2. Критичные зоны проверки

### 2.1. Деньги и ledger (сердце финтеха)

- [ ] **Двойная запись:** каждая операция — дебет/кредит, баланс сходится, нельзя создать деньги из воздуха.
- [ ] **Double spend / race:** параллельные списания, переводы, выводы — без дублей и отрицательных балансов.
- [ ] **Идемпотентность:** повтор запроса/вебхука не создаёт вторую операцию. Ключ идемпотентности обязателен для платежей.
- [ ] **Транзакционность:** частичная запись запрещена; откат корректен; нет «деньги списаны, а не зачислены».
- [ ] **Округления и валюты:** точность, конвертация, комиссии — без потерь и без «волшебного» начисления.
- [ ] **Лимиты:** на операцию, в день, на получателя, на вывод; обход через мультиаккаунты/разбиение.
- [ ] **Возвраты/отмены/chargeback:** корректный откат, без дюпа, с аудитом.
- [ ] **Сверка (reconciliation):** расхождения между ledger, платёжной системой и банком/провайдером детектятся.

### 2.2. Платежи и вебхуки

- [ ] Подпись вебхуков проверяется, replay-защита, идемпотентность, порядок/статусы.
- [ ] Подмена суммы/валюты/получателя на клиенте невозможна: сумма берётся с сервера.
- [ ] Receipt/подтверждение оплаты проверяется на сервере, а не на клиенте.
- [ ] Таймауты и повторные попытки не создают дублей; статусы честные (не «200 с ошибкой внутри»).
- [ ] Тестовые/боевые ключи разделены; тестовые платежи не могут попасть в прод-ledger.

### 2.3. Доступ и права

- [ ] AuthN/AuthZ разделены: вход ≠ право на чужие средства/данные. IDOR на счета, карты, выписки, документы.
- [ ] Tenant isolation: workspace/клиент не видит чужие данные даже прямыми ссылками.
- [ ] Роли: клиент, мерчант, оператор, админ, саппорт. Саппорт не имеет автоматического доступа к средствам/данным.
- [ ] MFA для админов/операторов и для чувствительных операций (вывод, смена реквизитов).
- [ ] Сессии/токены: отзыв, ротация, хранение, защита от кражи.

### 2.4. KYC/AML и персональные данные

- [ ] KYC: нельзя обойти верификацию подменой документов/данных; статусы проверяются на сервере на каждой операции.
- [ ] AML: пороги, мониторинг подозрительных операций, блокировки — по процессу клиента, не «на глаз».
- [ ] PII: минимизация, шифрование где нужно, доступ по принципу необходимости, сроки хранения, удаление.
- [ ] Логи: PII/секреты не пишутся в открытом виде; маскирование в UI и логах.
- [ ] Экспорт/выгрузка: права, аудит, защита от массовой выгрузки чужих данных.

### 2.5. API, ключи и секреты

- [ ] API-ключи: энтропия, хранение (хеш, не открытый текст), scopes, лимиты, отзыв/ротация, last-used.
- [ ] Секреты провайдеров: secret manager, доступ по необходимости, ротация, аудит чтения.
- [ ] Ключи не уходят в клиентский бандл, логи, аналитику, URL.
- [ ] Rate limiting, защита от перебора, enumeration, credential stuffing.

### 2.6. Архитектура и операции

- [ ] Границы доверия: клиент никогда не решает баланс/статус платежа.
- [ ] Audit trail: кто, что, когда, с какого IP/устройства; append-only, защита от правок.
- [ ] Мониторинг и алерты: аномальные переводы, массовые выводы, сбои сверки.
- [ ] Бэкапы и восстановление: восстановление не дублирует операции; тесты восстановления.
- [ ] Зависимости и CI/CD: секреты в CI, provenance, уязвимые зависимости, права доступа к репо.
- [ ] Криптография: хранение паролей (Argon2id/bcrypt), подписи, TLS, хранение токенов.

## 3. Приоритизация для финтеха

| Приоритет | Пример | Почему |
|---|---|---|
| P0 | Double spend, IDOR на средства, подделка вебхука, утечка секретов | Прямая кража денег / компрометация |
| P1 | Обход KYC, отсутствие MFA у админов, PII в логах, отсутствие идемпотентности | Регуляторный риск, массовый ущерб |
| P2 | Слабые лимиты, enumeration, misconfig | Усиливает атаки, репутация |
| P3 | Информационные утечки | Фон для других атак |

## 4. Особые требования к агенту в финтехе

- **Никаких реальных денег и реальных PII** в тестах без отдельного разрешения. Только тестовые данные и staging.
- Каждая находка про деньги — с **сценарием на тестовых счетах** и сверкой ledger до/после.
- Регуляторные выводы (152-ФЗ, PCI DSS, требования платёжных систем) — только как «требуется юридическая
  проверка», а не как заключение. Агент фиксирует технические факты, юрист — правовые.
- White Box для платёжного контура обязателен, если клиент продаёт «глубокий аудит финтеха».
