# Что получает клиент: результаты проверки и структура отчёта

> Клиент платит за **понятный результат**, а не за «мы что-то проверили».
> Этот файл описывает, что входит в результат каждого пакета и как оценивать риск.

## 1. Состав результата (все пакеты)

1. **Executive summary** ([templates/executive-summary.md](templates/executive-summary.md)) —
   2–4 страницы для руководителя: что проверяли, что нашли, сколько денег/данных под риском,
   что делать сначала, что будет после исправлений.
2. **Технический отчёт** ([templates/final-report.md](templates/final-report.md)) —
   методология, scope, карта поверхности, находки с доказательствами, ограничения.
3. **План исправлений** ([templates/remediation-plan.md](templates/remediation-plan.md)) —
   по приоритету, с ответственными (со стороны клиента), сроками и проверкой.
4. **Retest-сертификат** ([templates/retest-certificate.md](templates/retest-certificate.md)) —
   статус каждой находки после исправлений.
5. **Материалы:** доказательства (скриншоты, логи, запросы), список «не проверено», рекомендации на будущее.

Без executive summary отчёт не считается сданным: руководитель клиента не должен читать 80 страниц кода.

## 2. Структура технической находки

Каждая находка — по [templates/finding.md](templates/finding.md):

- ID, заголовок, режим, домен, дата, версия/коммит, окружение.
- Описание и шаги воспроизведения.
- Фактический vs ожидаемый результат.
- Влияние (бизнес): деньги, валюта, данные, репутация, регуляторный риск.
- Оценка риска: CVSS + бизнес-приоритет (P0–P3).
- Рекомендация: как чинить, пример, как проверить исправление.

## 3. Оценка риска: CVSS + бизнес-влияние

### CVSS 3.1 (техническая серьёзность, 0–10)

| Балл | Уровень | Смысл |
|---|---|---|
| 9.0–10.0 | Critical | Легко эксплуатируется, огромный ущерб |
| 7.0–8.9 | High | Серьёзный ущерб, реалистичная эксплуатация |
| 4.0–6.9 | Medium | Умеренный ущерб или нужны условия |
| 0.1–3.9 | Low | Малый ущерб |
| 0.0 | None / Info | Не уязвимость, а наблюдение |

CVSS считается по вектору (Attack Vector, Complexity, Privileges, User Interaction, Scope, Impact).
Агент фиксирует вектор и балл, а не только «высокий/средний» на глаз.

### Бизнес-приоритет (что чинить первым)

| Приоритет | Смысл | Пример (игра / финтех) |
|---|---|---|
| **P0** | Чинить немедленно, блокирует релиз | Дюп валюты / double spend, подделка оплаты |
| **P1** | Чинить до релиза/в ближайший спринт | IDOR на средства/инвентарь, кража аккаунтов |
| **P2** | В план на ближайший цикл | Слабые лимиты, enumeration, misconfig |
| **P3** | Улучшение, hardening | Информационные утечки, мелкие misconfig |

Итоговый приоритет = max(CVSS, бизнес-влияние). Высокий CVSS без бизнес-влияния может быть P2,
средний CVSS с прямым ущербом деньгами — P0. Это фиксируется в отчёте явно.

## 4. Что значит «исправлено» (retest)

Статусы по каждой находке:

- **Исправлено:** PoC больше не воспроизводится, исправление проверено.
- **Частично:** сценарий усложнён, но полностью не закрыт — нужен дофикс.
- **Не исправлено:** PoC воспроизводится как раньше.
- **Не воспроизводится / не применимо:** с обоснованием (например, scope изменился).

Сертификат содержит дату, версии, кто перепроверял, и итоговую сводку. Без retest
«исправлено» — на веру клиента, а не подтверждённый факт.

## 5. Ограничения результата (обязательно в отчёте)

- Дата и версия проверенного объекта; после изменений результат устаревает.
- Что не проверено и почему (нет доступа, вне scope, стоп-условие).
- Что проверка не гарантирует отсутствие уязвимостей и не заменяет мониторинг/обновления.
- Регуляторные вопросы — только с юристом; агент даёт технические факты.

## 6. Как клиент использует результат

- **Инвесторам/партнёрам:** executive summary + retest-сертификат.
- **Команде разработки:** технический отчёт + план исправлений.
- **Платёжным системам/аудиторам:** scope, методология, отчёт, retest — по их требованиям.
- **Себе:** приоритеты P0/P1 в бэклог, повторный аудит при крупных релизах.

## 7. Приёмка результата

Результат считается принятым, когда: отчёт передан, вопросы клиента закрыты,
план исправлений согласован, retest проведён или дата retest зафиксирована.
Детали приёмки и гарантий — в [08-service-packages.md](08-service-packages.md).
