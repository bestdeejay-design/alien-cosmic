# AGENTS.md — протокол работы агентов проекта Alien Cosmic

**Действует с 23.10.2026. Заменяет все прежние неформальные договорённости.**
Каждая холодная сессия агента начинает с: (1) прочитать этот файл, (2) прочитать
`design/ARENA_MAILBOX_STATUS.md` (канон состояния), (3) `git fetch --prune` и
`git status -sb` (защита от протухшего/откатанного локального .git).

---

## 1. Роли

| Роль | Кто | Полномочия |
|---|---|---|
| **Владелец** | bestdeejay-design | Приоритеты, продуктовые решения, финальная приёмка. Единственный, кто может менять этот протокол. |
| **Координатор** | ZCode | Единственная точка входа для задач. Превращает слова владельца в issues с брифом и критериями приёмки. Назначает исполнителя и ревьювера. Двигает статусы, сливает в main, ведёт борд и статус-карточку. Версия игры (GAME_VERSION) меняется только им. |
| **Исполнитель** | Арена, SZ m1, SZ m2 | Работает ТОЛЬКО в своей ветке поставки. Не пишет в main, не двигает борд, не берёт задачи кроме назначенных координатором. |
| **Ревьювер** | Любой агент, **не автор** работы | Проверяет поставку до приёмки: код + документация + регресс. Отчёт — в issue. |

Жёсткие правила контура:
- **Задача исполнителю — только через координатора.** Слово владельца, написанное напрямую
  исполнителю, не является задачей: координатор оформит её в issue, и только тогда работа легальна.
- **Поставка — никогда в main.** Только ветка + письмо.
- Приёмка финальная — у владельца; ревью — у ревьювера; слияние — у координатора.

## 2. Веточная модель

- `main` — канон. Пишет туда только координатор (слияние принятых поставок, откаты, док-карточки).
- **Каждый исполнитель пушит в ветку своего контура** (у Арены платформа жёстко привязывает сессию
  к ветке `arena/<id>` — это её норма, координатор не диктует имена веток). Единственные требования
  к ветке поставки: ветка — не main, база от **свежего** `origin/main` и **в письме о поставке
  объявлен диапазон коммитов** (хеши от–до), который и проверяют ревьюер с координатором.
- Самопроверка базы до первой строки кода: `git merge-base HEAD origin/main` == кончик main ==
  хеш из статус-карточки. Красный гейт по версии = старая база, не баг (версию в config не трогать).
- Перед пушем: `git fetch`; main уехал — rebase + полный регресс заново.
- Если задача требует чистого диффа от чужих работ (например, изоляция S2), вопрос решается
  порядком слияний и/или новой сессией исполнителя — а не переименованием веток.

## 3. Жизненный цикл задачи

```
Владелец → Координатор (issue: бриф + критерии + исполнитель + ревьювер, статус «К работе»)
         → Исполнитель (ветка + регресс + пуш + письмо, статус «На ревью»)
         → Ревьювер (ревью, статус «Правки» или «На приёмку»)
         → Координатор (слияние в main после approve, регресс на результате)
         → Владелец (приёмка, статус «Готово»)
```

### 3.1. Поставка исполнителя = письмо. Без письма поставки не существует.
Письмо — append-only в `design/ARENA_MAILBOX.md` (для Арены) либо в issue (для SZ):
что сделано, зачем, как проверено (списком), что красное и почему, хеш ветки.
Координатор узнаёт о работе по письму, а не по `git fetch`.

### 3.2. Ревью — обязательный второй заход (двухглазая приёмка)
Ревьювер — **другой агент, не автор**. Проверяет по чек-листу:
1. **Соответствие брифу** — сделано ли ровно то, что в issue; ничего сверх.
2. **Код:** границы задачи (не тронуто чужое), дубли, мёртвый код, i18n RU/EN синхронно,
   отсутствие сети (`check.mjs` гейт), консистентность симов при смене поведения
   (grep по всем `sim_*.mjs` на изменённые строки/селекторы).
3. **Документация:** если меняется поведение — обновлены ли README/GAME_GUIDE/дизайн-доки;
   письмо поставки полное, статусы честные.
4. **Регресс на ветке исполнителя** — полный канонический список (ниже), не выборочно.

Итог ревью — комментарий в issue с вердиктом:
- **approve** — «На приёмку» (координатор сливает);
- **правки** — конкретный нумерованный список; статус «Правки», работает снова исполнитель.
Максимум 2 итерации правок — дальше эскалация координатору (пересмотр брифа или смена исполнителя).

### 3.3. Слияние и приёмка
Координатор после approve: сливает (конфликты разрешает сам или возвращает исполнителю),
гоняет полный регресс **на результате слияния**, коммитит merge-post (что влито, что проверено),
обновляет статус-карточку и борд. Владельцу — короткая сводка «что смотреть и что решать».
Продуктовое (играбельное, сюжеты, UX) — только через приёмку владельца. Инфраструктурное
(CI, скрипты, доки процесса) координатор может принять сам, уведомив владельца.

## 4. Регресс — канонический список, без сокращений

```
node scripts/check.mjs          # гейт
node scripts/smoke.mjs
17 симов: build, codex, edge_reach, gather, grade, hq, i18n, menu, move,
          p1, panel, repair, shell, touch, traffic, ux, wins   (scripts/sim_*.mjs)
node scripts/audit_move.mjs
node scripts/check_minimap_view.mjs
u_verify.mjs + v_verify.mjs     # с локальным сервером: python3 -m http.server 8793
```
Пуш — сразу после коммита, тем же дыханием. Красное на своей ветке — пуш откладывается:
сначала сверка базы (п.2), только потом свой код. Известный флейк: `v_verify` пакет S
(«отмена confirm») может падать — перепрогон, при повторе фиксировать как баг.

## 5. Границы (не твоя зона — не трогай)

- **Версия игры** `js/config.js` GAME_VERSION — только координатор в main.
- **Сеть** — гейт запрещает fetch/WebSocket; MVP-клиент без сети, backend — отдельный сервис.
- **Борд/статусы/приёмки** — только координатор.
- **Сюжеты и кампании** — только после явного GO владельца (урок Сезона 2: S2 отозван целиком).
- **Изоляция Сезона 2 (канон владельца, 23.10):** код Сезона 1 — `js/`, `style.css`, игровая
  часть `index.html` — **заморожен**: правки только по явному запросу владельца через координатора.
  Весь S2 (код, механики, визуал, стили, ассеты, локали, симы) живёт в **`s2/`** и не смешивается
  с движком. Движок S1 — **донор**: импортировать и переиспользовать можно, **редактировать нельзя**.
  Разрешённая зона касания вне `s2/` — только лендинг (`index.html`): ссылка/кнопка «Сезон 2».
  У S2 свой сим-файл; общий гейт `check.mjs` не переписывается под S2. Нарушение изоляции = гарантированный
  реверт всей поставки (прецедент: S2 отозван целиком именно за правки рабочего движка).

## 6. Коммуникация

- Координатор ↔ исполнитель/ревьювер: mailbox (`ARENA_MAILBOX.md`) и комментарии в issues.
- Статус-карточка `ARENA_MAILBOX_STATUS.md` — обновляется координатором перед каждым
  важным событием. История — в mailbox, append-only, не переписывать.
- Несогласие с решением — письмом координатору, а не самодеятельностью в коде.

## 7. Слепые зоны и стартовая последовательность (для любой холодной сессии)

1. `AGENTS.md` → `ARENA_MAILBOX_STATUS.md` → `git fetch --prune` → `git status -sb`.
2. Нет назначенной задачи — работы нет: спросить координатора, а не искать себе занятие.
3. Локальный .git протух/откатился (бывали инциденты) — восстановиться с origin, потери ноль,
   инцидент письмом координатору.

## 8. Рабочий канон команды (с 28.10.2026)

Работа агентов идёт по общему канону команды: эталон — репо `bestdeejay-design/agents`
(PROTOCOL, WORKFLOW, BUS, BOARD, OPS + регламенты AGENT_RULES/COORDINATOR_RULES),
копия канона — в `workflow/` этого репо, проектная конкретизация — `workflow/PROJECT.md`.

Ключевое (коротко):
- **Маркеры шины** — единственный язык сообщений между узлами: 👀 READ, 🎯 CONCLUSION,
  ✅ GATE OPEN, 🏁 DONE, 📬 DELIVERED (внешние, письмом-файлом), ✋ CLAIM, ⛔ BLOCKED,
  ❓ QUESTION, ♻️ RECLAIMED, 📌 DECISION. Словарь — KNOWLEDGE_BASE §5, BUS.md.
- **Каждое сообщение — с подписью узла** («— Роль · сессия»): все могут работать под
  одним аккаунтом, личность — в подписи.
- **ARCA** (AUDIT → RESEARCH → CONCLUSION → ACTION) для size:M/L; гейт ACTION — только
  координатор; size:S — сокращённый цикл.
- **Парковка** дежурных сессий: взял задачу → сделал → сдал → вернулся в ожидание;
  скрипт `scripts/wait-signal` (ETag-поллинг 60–120с, --claim для роя, --version для
  проверки свежести клона).
- **Атомарный claim** + могильщик зависших клеймов (S=15м/M=60м) — координатор.
- **Гигиена веток**: слитая ветка удаляется; база поставки — свежий origin/main.
- Проектная конкретизация (регресс, стемпы, изоляция, соответствие статусов борда) —
  `workflow/PROJECT.md`. Этот файл (AGENTS.md) остаётся каноном проекта; при
  противоречии проектный файл > общий.

## 9. Протокол больших задач (владелец, 26.10.2026)

Каждая БОЛЬШАЯ задача (новый этап/механика) проходит строго по конвейеру:

1. **Аудит** — что уже есть (код, доки, полигоны), что мешает.
2. **Ресерч** — как делается правильно (референсы, лучшие практики, экономика).
3. **Публикация в репозиторий этапа** — отдельный репозиторий `ace/` (Alien Cosmic
   Expedition и далее по этапам): аудиты, ресерчи, спеки, решения.
4. **Задачи в GitHub Projects** — этап разбивается на issues с критериями приёмки.
5. **Аудит другими агентами** — Арена и/или SZ m1 добавляют и обогащают контекст
   (ревью спеки ДО реализации).
6. **Только после этого — реализация** (по общим правилам: исполнитель, ревью, приёмка владельца).

Скачки через ступени = поставка не признаётся. Операционные мелочи (деплой, бэкапы,
правки багов) идут по обычному порядку AGENTS.md, мимо конвейера.
