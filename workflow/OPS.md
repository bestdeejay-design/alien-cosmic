# OPS — рантайм координатора (как на самом деле крутится шина)

Регламент координатора (COORDINATOR_RULES) описывает ЧТО решать. Этот файл — КАК
шина работает день за днём: триггеры, ритм, каналы. Обновляет координатор.

## 1. Триггерная сетка (пассивного ожидания нет)

| Источник | Триггер | Реакция координатора |
|---|---|---|
| Ветка внешнего агента | новый коммит (вотчер, poll 1–2 мин) | ретрансляция письма в issue, аудит |
| Issues (любой комментарий) | изменение счётчика/содержимого | гейт / приёмка / ответ |
| Очереди агентов | регулярный обход (каждые 15–20 мин, автоматизация) | блок «КОМУ ЧТО» владельцу |
| Зависший клейм | лимит размера (S=15м/M=60м/L=день) | пинг → перезахват (reaper) |
| Слитая ветка | merge | удаление ветки (проверив merge-base), merge-пост |

Личность узла — в ПОДПИСИ тела комментария («— Роль · сессия»), не в логине:
все узлы могут работать под одним аккаунтом. Комментарий/письмо без подписи —
не считается сообщением шины.

## 2. Каналы по типам узлов

| Узел | Получает | Отдаёт | Кто ретранслирует |
|---|---|---|---|
| Координатор | всё | гейты, слияния, задачи, DECISION | — |
| Внешний агент (без записи в issues) | текст через владельца / чтение репо | пуш ветки + MAIL-файл | координатор |
| Локальная сессия (полный доступ) | issues + маркеры; паркуется в wait-signal | маркеры + PR/ветка | — |
| Субагенты | поднимает узел сам | через родителя | — |
| Владелец | борд + сводки «КОМУ ЧТО» | подъём сессий, приёмка, развилки | — |

«Ожидание» узлов без встроенного поллинга обеспечивает координатор: вотчер
+ периодический пинок-пакет владельцу (готовый paste-текст).

## 3. Ритм обработки (обязательства)

1. Ревью/письмо пришло → отработка в текущем же ходе (гейт, итерация, слияние).
2. Два approve → слияние в тот же час; merge-пост (что влито, что решено, чьи правки).
3. Правки ревьювера исполнителю — ретрансляция не позднее следующего обхода.
4. Находки/уроки живых прогонов → BUS/регламенты (та же сессия, не «когда-нибудь»).
5. Сводка владельцу — только если нужно его решение/внимание, иначе борд говорит сам.

## 4. Песочницы и полигоны

- Для живых прогонов воркфлоу используются отдельные песочницы (полигоны), не боевые репо.
- Содержимое песочницы координатор чистит без согласования (тестовые issues, ветки, мусор) —
  помечая MOCK/учебное.
- Учебные задачи в песочнице — size:S/M, с маркерами по словарю шины: они же являются
  самопроверкой воркфлоу.

## 5. Запуск нового узла (лист онбординга)

1. Владелец поднимает сессию в нейтральной папке.
2. Координатор выдаёт parking/launch-пакет (КТО ТЫ / ГДЕ ЧТО ЛЕЖИТ / КАК ОБЩАТЬСЯ / цикл).
3. Узел читает канон (README → WORKFLOW → BUS → AGENT_RULES) и паркуется.
4. Первая задача — учебная в песочнице, полный цикл с маркерами.
5. Дальше узел живёт по шине; владелец в сессию не пишет.

## 6. Гигиена контекста: 30 минут тишины (владелец, 03.11.2026 — по умолчанию для всех сессий)

Контекст молчащей сессии протухает: детали задачи забываются раньше, чем задача
возобновляется. Правило — дефолт для всех узлов, без включения:

1. **Сессия без движения дольше 30 минут** (нет коммитов, маркеров, статусов) —
   координатор (вотчер шины / reaper) отправляет ей **пинок-пакет на сжатие контекста**:
   сжать (компакт) диалог, вынести состояние в HANDOFF/статус-карточку проекта
   (что сделано, что открыто, что дальше — чтобы новая сессия продолжила без потерь).
   Исключение: паркованная сессия в штатном ожидании (wait-signal, скан 60–120 с) —
   тишина штатна, пинок не отправляется; пинок — на сессии, ЗАСТРЯВШИЕ в работе
   (есть активная задача/карточка).
2. **При возобновлении после тишины** сессия сначала сжимает контекст и сверяется с
   HANDOFF/бордом, и только потом продолжает работу — не «с места, как помнила».
3. **Долгая работа — с чекпоинтами:** узел на M/L-задаче пишет промежуточные итоги
   в issue (маркером), чтобы сжатие контекста не потеряло принятое решение.
4. Ответственность за таймер — на координаторе: приложение не считает молчание,
   его видит борд.

Не путать с ♻️ RECLAIMED (BUS): там задача возвращается в ready при зависании клейма.
Здесь задача остаётся за исполнителем — сжимается только его память.
