# FIELD-LESSONS — полевые уроки координации многосессионных проектов

> Практические находки с эксплуатации параллельных сессий ИИ-агентов (75+ карточек,
> смешанные контуры с полным доступом к шине и изолированные песочницы без записи в issues),
> сформулированные как универсальные инженерные правила общего слоя.

## 1. Живые проверки вёрстки при отсутствии браузера у исполнителя (→ COORDINATOR_RULES)

Изолированные облачные сессии нередко работают в контейнерной песочнице без GUI-браузера
(headless-движок без системных библиотек не стартует). CSS и вёрстка, проверенные только
разбором каскада и синтетическим DOM, всё равно расходятся на реальном рендере.

**Правило:** в брифе исполнителя заранее фиксируй разделение труда — «живую геометрию и
рендер проверяет координатор/ревьювер с браузером; в твоём контуре доступны код, DOM-разбор
и модульные тесты». При приёмке координатор поднимает локальный стенд (`http.server` +
Playwright) и прикладывает замеры геометрии (`getBoundingClientRect`, computed style)
вместе со скриншотами (подробнее — навык [`ui-render-verification`](../skills/ui-render-verification/SKILL.md)).

## 2. Временные бомбы в тестах — никаких зашитых календарных дат (→ PROTOCOL §5)

Классическая причина ложных падений: входные данные в тесте прибиты к конкретным датам
календаря (`2026-10-18…22`), а тестируемая логика считает окно относительно «сегодня».
Через несколько дней тест разваливается сам по себе.

**Правило для регресса:** запрещай литеральные текущие даты в тестах, зависящих от окна
времени; генерируй фикстуры относительно фиксированного `now` / инъекции часов. Если тест
внезапно покраснел без касания модуля — сначала проверь календарную бомбу, но чини её
отдельной задачей `type:debt` / `type:test`, а не «заодно» внутри продуктовой ветки.

## 3. Самодостаточный бриф для внешнего контура и вопросы одной пачкой (→ WORKFLOW §1)

Изолированная сессия без прямого доступа к issues не может задавать мелкие уточняющие
вопросы на лету — каждый цикл проходит через владельца или координатора.

Рабочая схема:
- бриф содержит всё необходимое на входе: инварианты и контракты со списком тестов,
  краткую сводку предыдущих этапов («не повторяй уже закрытое»), точный формат сдачи;
- вопросы собираются и отправляются **одной посылкой**, чтобы получить ответы за один проход;
- изолированный исполнитель не пишет в issues, не сливает ветки и не двигает борд —
  сдаёт только свою ветку поставки и письмо `docs/MAIL.md`.

## 4. Автономный стенд-пакет для внешних аудиторов (→ WORKFLOW §6, конвейер)

Когда нужен независимый аудит UI или архитектуры от свежих сессий без полного погружения
в инфраструктуру проекта, им выдаётся компактный воспроизводимый пакет одной командой:
**бриф (домен, контракты, критерии приёмки) + обезличенный синтетический слепок данных
без ПДн + предсобранные экраны/артефакты для сравнения**. Критерий формулируется через
наблюдаемый результат («не добавлять новые функции — сделать ключевой сценарий читаемым
за 5 минут»).

## 5. GitHub Projects V2: грабли CLI и гигиена доски (→ BOARD, PROJECTS-BLUEPRINT)

Проверено на реальной эксплуатации досок:
- **Доска показывает только активную работу.** Закрыл issue → статус `Done` → архивация
  элемента `item-archive` (архив не удаляет карточку, но убирает визуальный шум).
- **Номер issue ≠ порядковый номер активной задачи:** сквозная нумерация GitHub включает
  PR и закрытые карточки — проговаривай это явно в сводках.
- Статус выставляется **в момент создания** карточки; вопросы к владельцу маркируются
  флагом `needs-human`.
- Особенности `gh`: `gh project item-list --format json` не возвращает полные `fieldValues` —
  статус надёжнее читать через GraphQL `ProjectV2ItemFieldSingleSelectValue` (запрашивая
  поле `name` значения); `item-add` для уже добавленной карточки идемпотентен.
- **Фильтры Auto-add workflow:** серый текст в поле `Filters` интерфейса GitHub может быть
  активным сохранённым фильтром (`label:bug`), тихо блокирующим автодобавление новых карточек.
  Проверять автоматизацию нужно сквозным живым тестом на проверочной карточке.

## 6. Правила рождаются письменно из прецедентов (→ PROTOCOL §3)

Не пытайся выдумать регламент на все гипотетические случаи вперёд. Реальный сбой
(размытая поставка без диапазона коммитов, попытка ревьюить свой код, бесконечные раунды
правок) → короткое письменное правило (строгий формат письма из 5 пунктов, ревьювер ≠ автор,
лимит 2 итераций правок) → утверждение владельцем. Канон растёт из практики.

## 7. Простой вопрос ≠ заявка на переделку (→ PROTOCOL §3)

Вопрос владельца («есть ли документ про X?», «почему здесь сделано так?») — это запрос
картины текущего состояния, а не команда переписывать файлы. Сначала дай точный ответ по
фактам; предложение что-то поменять выноси отдельным пунктом и уточняй при малейшей
неоднозначности короткого «да».
