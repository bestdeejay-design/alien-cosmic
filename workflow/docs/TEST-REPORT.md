## 4. Находки (честные; минимум требовалось 3)

**F1. Граница путей против спецификации комплекта.** Issue #1 разрешает изменения
в `docs/`, `.github/ISSUE_TEMPLATE/`, `DEBT.md` и issues; AGENT-DOCS-SPEC при этом
хотел корневой `AGENTS.md`, `.github/pull_request_template.md` и CODEOWNERS.
Решение при сборке: AGENTS хранится как `docs/AGENTS.md` (в проект кладётся в корень),
поля PR-шаблона ушли в письмо о поставке и AGENT_RULES §4.4, CODEOWNERS остался
принципом проектного слоя, а `scripts/wait-signal` создан по прямому указанию
владельца путём `scripts/wait-signal`. Предложение: при утверждении владелец
подтверждает это размещение одной строкой, чтобы проектные копии не гадали.

**F2. В словаре варианта C не хватало `type:question`** (WORKFLOW-VARIANTS §4.2
перечислял 8 типов, а question-цикл без девятого не работает). Исправлено при сборке
во всех четырёх местах словаря (KNOWLEDGE_BASE, task/question.yml, create-labels.sh,
поправка в WORKFLOW-VARIANTS). Предложение: ревьюверу проверить grep-ом равенство
словарей ещё раз — это класс ошибки, который вернётся при следующем расширении labels.

**F3. Формы GitHub не ставят labels из своих полей.** Dropdown «роль/тип/размер» —
текст в теле issue; автоматически применились только labels заголовка шаблона
(`status:inbox`, у question ещё `type:question`). Значит, «issue по форме» ≠ «issue
размечен»: координатор обязан первым действием мониторинга перевести поля в labels,
иначе агент не найдёт задачу своим фильтром. В комплект это вписано
(KNOWLEDGE_BASE §6, подсказка в task.yml). Дальше — только автоматизация (§6),
вручную это самое хрупкое место процесса.

**F4. Доступ внешней сессии не умеет вести issue.** Создание issues и repo-labels —
да; комментарии, переходы labels на issue, закрытие — `403`. Следствия: (а) живой
прогон в #2/#3 неполон и mock-issues висят открытыми до координатора; (б) внешний
исполнитель физически не «двигает борд», что совпало с каноном (статусы двигает
координатор), но письмо внешнего исполнителя обязано прямо просить нужные переходы —
это добавлено в шаблон письма («если у тебя нет права менять labels…»);
(в) `wait-signal` при этом читает всё, что ему нужно, — ожидание от прав записи не зависит.

**F5. Прогон одним оператором — не ревью.** Бумажный цикл доказал работоспособность
форм, но второй заход по-настоящему не случился: автор комплекта не может быть его
ревьювером. Предложение: не закрывать issue #1 по этому отчёту; дальше — ревью
не-автором по чек-листу WORKFLOW канона + прогон регресса §2, правки ≤ 2 итераций,
и только потом приёмка владельца и обновление корневого канона координатором.

**F6. Семантика 🏁 DONE двусмысленна без 📬 DELIVERED.** В требовании владельца
DONE читается и как «агент закончил», и как финальное «принято». Комплект развёл:
`📬 DELIVERED` — сдал исполнитель, `🏁 DONE` — принято после приёмки, ставит
координатор. Предложение владельцу при утверждении: подтвердить пару, иначе
ожидатель будет будить владельца на каждую сдачу, а не на приёмку.

**F7. Шаблон AUDIT молча предполагал паспорт модуля.** На зонах без паспорта
(docs, процессные задачи) п.5 шаблона провоцировал выдумывать артефакт. По итогам
вопроса #Q в шаблон AGENT_RULES §4.1 вшита явная строка: «паспорта у зоны нет —
пиши, чем он заменён (канон/статус-карточка проекта) и почему». Заодно это первый
случай, когда question-цикл улучшил комплект до его утверждения, — механизм работает.

## 6. Требуемая инфраструктура сверх GitHub (только спецификация, не реализовано)

MVP поллинга `wait-signal` достаточен, пока: задач немного, задержка сигнала
до одного интервала (60 с) приемлема, ждущий — человек или редкая сессия.
Понадобится сверх GitHub, когда любой из пунктов станет болью:

| Сервис | Какой сигнал отдаёт | Чем его ждёт владелец | Когда нужен |
|---|---|---|---|
| Webhook-слушатель на `issues`/`issue_comment` события репозитория (проверка подписи секретом вебхука, секрет — только в канале владельца) | Мгновенный push о маркере первой строки и переходе label, без поллинга | Уведомление в канал владельца/координатора (мессенджер/почта), либо тот же `wait-signal` в режиме подписки на слушатель | Задержка 60 с стала мешать; issues десятки в день |
| Координатор-автоматизация (например, agentic-workflow в CI по событиям issues) | Авто-перевод полей формы в labels (лечит F3), авто-CONTINUE при снятии зависимости, авто-подсчёт метрик цикла | Владелец не ждёт руками: получает только `👤 NEEDS-HUMAN` сигналы | Ручной label-repair начал пропускать дрейф |
| Heartbeat/реестр внешних сессий (файл или issue-реестр: сессия, issue, ветка, последний сигнал) | «Внешняя сессия жива/молчала дольше порога» — то, чего маркеры не говорят | `wait-signal` по heartbeat-записи + эскалация владельцу при тишине дольше порога проектного слоя | Внешних сессий больше одной одновременно |

Ничего из этой таблицы в этой поставке не реализовано — по требованию владельца
это спецификация на будущее, а не самодеятельность исполнителя.
