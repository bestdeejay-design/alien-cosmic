# AGENT-DOCS-SPEC — спецификация финальной документации для агентов

> Дата: 27.10.2026. Статус: research/draft, не канон.
> Назначение: после того как владелец выберет вариант в [WORKFLOW-VARIANTS.md](./WORKFLOW-VARIANTS.md),
> координатор собирает по этой спецификации финальный комплект. До выбора варианта
> финальные регламенты не пишутся — иначе три редакции одного правила разойдутся,
> как уже произошло в стенограмме прототипа (AUDIT §3, риск Р6).
> Форма задана ресёрчем: короткая точка входа + прогрессивное раскрытие деталей,
> запрет без проверяющего в регламент не попадает (RESEARCH §4–§5).

## 2. Требования к каждому файлу

### 2.1. `AGENTS.md` — точка входа холодной сессии

- **Лимит: ≤ 60 строк.** Это маршрут чтения, а не регламент. Раздутый файл агент игнорирует (RESEARCH §4).
- Обязательное содержимое, по порядку:
  1. Кто ты можешь быть здесь: роли одной строкой + «роль назначена label `agent:*` в твоём issue; нет назначенного issue — работы нет».
  2. Холодный старт из PROTOCOL §4 (5 шагов) — дословно, не пересказом.
  3. Маршрут чтения: этот файл → регламент своей роли → issue → паспорт модуля и ADR из issue. Явный запрет читать «весь репозиторий на всякий случай» вместо радиуса.
  4. Пять абсолютных запретов одной строкой каждый: не писать в main проекта; не начинать ACTION до гейта; не трогать чужие зоны и секреты; не чинить долг «заодно»; поставка без письма не существует.
  5. Куда идти с вопросом: question-шаблон и координатор.
- Никаких проектных имён, путей `src/...` и команд конкретного проекта. Команды регресса —
  ссылкой на проектный слой («список проверок проекта: <место в проектном репо>»).

### 2.2. `docs/AGENT_RULES.md` — регламент исполнителя

Структура (из прототипа, с правками WORKFLOW-VARIANTS §5):

1. Фазы ARCA и размеры S/M/L: таблица «размер → какие фазы → какой формат» (вариант C §4.4).
2. Шаблоны комментариев AUDIT / RESEARCH / CONCLUSION / ACTION — дословно как поля,
   которые исполнитель копирует. В CONCLUSION обязательно поле «Проверка: как докажу,
   что работает» (добавка ресёрча §3, в прототипе отсутствует).
3. Как брать задачу: фильтр labels (`agent:<роль>` + `status:ready`), проверка depends-on
   как вторая линия, что прочитать (и что не читать).
4. Блокировка и question-цикл (вариант C §4.6), включая заморозку фазы.
5. Долг: одна строка в DEBT.md в своей ветке; чинить — никогда «заодно».
6. Сдача: ветка, письмо о поставке (состав из WORKFLOW канона §3), паспорт модуля, `phase:verify` + `status:review`.
7. Зоны ответственности: в общем слое — принцип «зона = список путей в проектном слое
   + радиус issue уже зоны»; таблица папок прототипа (`src/`, `infra/`) в общий слой не входит.
8. Список «нельзя» — только пункты с проверяющим (гейт, ревью чек-лист, координатор).
   Каждый пункт заканчивается тем, кто и как нарушение обнаружит.

Лимит ориентир: ≤ 250 строк. Если не влезает — детали уезжают в KNOWLEDGE_BASE, здесь остаются нормы.

Зафиксированное исключение (второе ревью, решение 03.11.2026): `AGENT_RULES.md`
354 строк — выше лимита осознанно. Причина: полнота регламента исполнителя
(режимы узлов, claim, парковка, сигналы) важнее формального лимита; разбор
(вынос деталей в KNOWLEDGE_BASE) отложен отдельной задачей.

### 2.3. `docs/COORDINATOR_RULES.md` — регламент координатора

1. Декомпозиция: атомарность issue, обязательные поля (бриф, критерии, размер, радиус,
   исполнитель, ревьювер, зависимости, env-потолок, ограничения). Issue без радиуса не существует.
2. Как задавать радиус: модуль + прямые зависимости (1 уровень) по паспорту; меньше — лучше;
   выход за радиус — только question.
3. Гейты: чек-листы приёма AUDIT / RESEARCH / CONCLUSION / ACTION (из прототипа Файл 2 §5,
   с маршрутизацией ревью фаз по варианту C §4.4) и формат approve/reject одной строкой.
4. Мониторинг: разблокировка depends-on, label-repair (ровно один `status:*` и один `phase:*`),
   блокеры старше двух циклов, вопросы без ответа, метрики цикла (AUDIT §5 п.5).
5. Launch-пакеты LAUNCH / CONTINUE / HOTFIX: шаблоны из EXAMPLES §6 + запретный список
   (секреты и инфраструктура в пакеты и issues не кладутся никогда).
6. Промоушен по уровням (вариант C §4.5): кто, условия, инвариант одного SHA, soak — параметр проекта.
7. Приёмка и слияние: правило канона «Готово — после приёмки владельца; инфраструктурное —
   координатор с уведомлением», merge-пост, обновление STATUS/борда как видов.
8. Эскалации: 2× rejected, отмена задачи, пересекающиеся радиусы двух `in-progress`.

### 2.4. `docs/KNOWLEDGE_BASE.md` — шпаргалка

Только справочное, ноль новых норм (норма, встреченная только здесь, — дефект комплекта):
таксономия labels с цветами и hex (приложение для `gh label create`), две state-машины
(status и phase) диаграммами, таблица «кто что может» (вариант C §4.2–4.3),
отображение статусов на колонки BOARD, быстрые ответы («агент хочет кодить — есть `phase:action`?»).

### 2.5. Шаблоны (модуль, ADR, issue, PR)

- **Паспорт модуля:** шаблон прототипа + шапка «последнее обновление: дата — issue — кто»
  и раздел «история значимых изменений». Правило жизни: переписывается под текущую
  реальность; рождается с первой задачей модуля, а не задним числом на все модули.
- **ADR:** статус/дата/issue/автор, контекст, варианты (≥2, включая «ничего не делать»,
  если это реальная опция), решение, последствия; поля Supersedes/Superseded by;
  accepted ADR неизменяем — изменение только новым ADR (RESEARCH §7).
- **task.yml:** поля варианта C §4.3 (размер и радиус — обязательные), dropdown'ы ролей/типов
  синхронизированы с таксономией KNOWLEDGE_BASE; ни одного проектного значения по умолчанию.
- **question.yml:** от кого/кому/блокирует/вопрос/контекст фазы/свои варианты.
- **PR-шаблон:** `Closes #N`, диапазон коммитов, «соответствует CONCLUSION issue #N: да/отклонения
  перечислены», регресс списком, паспорт/DEBT обновлены (да/нет/не применимо).

## 3. Правила качества комплекта (проверяется на ревью)

1. **Проект-агностичность:** grep по именам проектов, репозиториев и команды — пусто
   во всех файлах общего слоя. Примеры — только на условных модулях, как в EXAMPLES.md.
2. **Единственность нормы:** каждое правило встречается ровно в одном файле дословно;
   остальные ссылаются. (Прототип нарушал это трижды на labels и окружениях.)
3. **Нет висячих плейсхолдеров:** `[N часов]`, `@username`, «разумное время» запрещены;
   параметр либо задан общим слоем, либо явно делегирован проектному с именем параметра.
4. **Нет нормы без проверяющего:** каждый запрет называет, кто/что его ловит.
5. **Согласованность словарей:** labels в YAML-шаблонах = labels в KNOWLEDGE_BASE =
   labels в скрипте создания; расхождение = блокирующий дефект ревью.
6. **Лимиты объёма соблюдены** (§2); превышение — только решением координатора с причиной в письме о поставке.

## 4. Как комплект тестируется (требование issue #1, шаг после выбора варианта)

Сухой прогон, оформляется отдельным `docs/TEST-REPORT.md` в финальной поставке:

1. **Пилот вживую:** одна реальная малая задача этого репозитория (например, «создать
   labels ядра и шаблоны») проводится по полному циклу варианта C: issue по task.yml →
   комментарии фаз → гейт → поставка → ревью второго захода. Все переходы labels фиксируются.
2. **Оба исхода гейта:** CONCLUSION один раз отклоняется намеренно (неполный список файлов)
   и принимается после правки — проверяется, что процесс отказа не ломает состояние.
3. **Question-цикл:** один вопрос создаётся и закрывается по §4.6 с заморозкой фазы.
4. **Регресс docs** (WORKFLOW-VARIANTS §4.9) прогоняется и прикладывается списком.
5. **TEST-REPORT:** минимум 3 честные находки формата «где сломалось / что непонятно /
   что добавить» + предложенные правки регламентов. Ноль находок = прогон не засчитан:
   процесс, который не нашёл в себе ни одного трения на пилоте, не тестировали, а демонстрировали.

После TEST-REPORT: ревью (второй заход, не автор комплекта) → правки ≤ 2 итераций →
утверждение владельцем → координатор обновляет корневой канон и STATUS.md. Только с этого
момента финальный комплект — канон, а research-пакет — его история.

## 5. Что координатор вносит в проектный слой при копировании

Чек-лист конкретизации (по правилу слоёв из STATUS.md), чтобы копия не расползлась:

- [ ] Таблица «уровень (test/staging/production) → ветка/механизм/стенд» проекта.
- [ ] Базовая ветка поставок и формат имён веток; способ слияния (один из merge/squash/rebase)
      и авто-удаление веток поставок.
- [ ] Канонический список регресса проекта (команды), включая docs-проверки, если применимо.
- [ ] Soak-периоды уровней и сроки ответов на question (абсолютные значения).
- [ ] Зоны ответственности по путям проекта и замороженные зоны.
- [ ] **Блокирующий пункт:** `AGENTS.md` лежит в **корне** проектного репозитория
      (стандарт AGENTS.md: корень и вложенные папки; файл из `docs/` инструменты
      могут не найти). Копия в docs/ как источник — недостаточна.
- [ ] GitHub Project применён по PROJECTS-BLUEPRINT: главный вид «01 Контроль»
      таблицей, Assignees скрыт, адресация — `to:*`, поля `Адресат/Приоритет/Размер/
      Фаза/Начата/Срок/Завершена` синхронизируются с labels вручную до отдельной
      автоматизации; пилот из трёх задач пройден и записан координатором.
- [ ] CODEOWNERS и настройки protection/environments по лестнице принуждения
      COORDINATOR_RULES §12 (уровень 2 на главную ветку, уровень 3 на production;
      production: required reviewer ≠ автор, prevent self-review) — со ссылкой
      на ruleset как доказательством, а не отметкой «настроено».
- [ ] Список модулей проекта: паспорта создаются по мере первых задач, не задним числом.
- [ ] Ссылка из агентского файла проекта на этот общий комплект (источник, дата копии, версия).
