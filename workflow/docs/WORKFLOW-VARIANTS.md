## 2. Вариант A — минимальный («канон + labels»)

**Идея:** не менять процесс, дать ему машиночитаемую форму.

- Берём действующие PROTOCOL/WORKFLOW/BOARD без изменений смысла.
- Добавляем labels только трёх групп: `status:*` (8 значений = колонки BOARD),
  `agent:*` (4 роли канона + `agent:external`), `type:*` (7 значений).
  Projects остаётся видом: колонки = фильтр по `status:*`.
- Добавляем `.github/ISSUE_TEMPLATE/task.yml` (бриф + критерии + радиус одной строкой)
  и письмо о поставке как обязательный комментарий в issue (mailbox — ссылка на него).
- Регресс docs-проектов определяем проектным слоем (чек-лист из 3–5 проверок).

**Плюсы:** внедряется за день; ноль переучивания; нет риска «процесс ради процесса».
**Минусы:** главная болезнь, ради которой писался прототип — «агент кодит без аудита,
наращивает слои и долг» — не лечится; на size:L задачах по-прежнему один общий цикл.
**Вердикт:** годен как **шаг 1 внедрения варианта C** (см. §7), не как финальное состояние.

## 3. Вариант B — полный ARCA (прототип как написан)

**Идея:** принять 8 файлов прототипа дословно.

**Плюсы:** максимум формализации; ARCA и паспорта — целиком; launch-пакеты готовы.
**Минусы (по аудиту):** наследует блокирующие C1, C2, C5, C8, C11, C18; три редакции одних
правил (стенограмма) заставят координатора самому выбирать, какая действует, — то есть
противоречия не исчезнут, а переедут в голову координатора; 30+ labels без правила
единственности; develop/staging/main как имена веток нарушают проект-агностичность
и решение владельца об абстрактных окружениях; паспорта «на все модули сразу» — недели
работы до первой пользы.
**Вердикт:** не внедрять как есть. Использовать как **источник текстов** при сборке C:
шаблоны фаз, LAUNCH/CONTINUE, паспорт и ADR у прототипа хорошие (с правками §5).

## 4. Вариант C — тир-гибрид (рекомендация)

### 4.1. Принципы

1. **Канон не ослабляется.** 7 пунктов AUDIT §1.3 действуют дословно. ARCA добавляется
   *внутрь* существующего цикла задачи, а не вместо него: фаза ACTION завершается тем же
   письмом о поставке, ревью — тем же вторым заходом, приёмка — владельцем.
2. **Labels — единственная правда о состоянии.** Projects, борд, статус-карточка — виды,
   которые координатор сверяет с labels; при расхождении правятся виды, не labels.
3. **Церемония пропорциональна размеру.** Размер ставит координатор при создании issue.
   Сомнение между S/M → M; между M/L → L (правило прототипа, сохраняем).
4. **Гейты, а не ветки.** Окружения — уровни приёмки одного и того же коммита (§4.5).
5. **Каждый запрет имеет механизм или проверяющего.** Текстовый запрет без проверяющего
   в регламент не попадает: либо label-переход координатора, либо ревью чек-лист,
   либо настройка GitHub в проектном слое.

### 4.2. Таксономия labels (ядро; расширять — только через координатора)

Правило единственности: **ровно один label из каждой группы на issue**; переход =
атомарная замена (снять старый, поставить новый одной операцией). Открытые группы
`needs-human`, `launch-ready`, `has-pr` — флаги, не состояния; их может быть несколько
или ни одного. Координатор на каждом мониторинге чинит дрейф: два `status:*` на issue —
инцидент процесса, правится немедленно с комментарием.

| Группа | Значения | Кто ставит/снимает |
|---|---|---|
| `status:*` — где задача (1) | `inbox` → `ready` → `in-progress` → `review` → `done`; боковые: `blocked`, `rejected` | inbox/ready/done/blocked-разблокировка — координатор; in-progress/review — исполнитель; rejected — координатор или ревьювер по итогам ревью (см. C2) |
| `phase:*` — фаза ARCA (1; только для задач с кодом/контентом, не для question) | `audit` → `research` → `conclusion` → `action` → `verify` | audit/research/conclusion — исполнитель; **`action` — только координатор (гейт)**; verify — исполнитель при сдаче |
| `agent:*` — роль-исполнитель (1) | `coordinator`, `researcher`, `architect`, `coder`, `reviewer`, `qa`, `devops` + модификатор запуска (см. ниже) | координатор при создании |
| Внешний запуск | **Не отдельная роль.** Флаг `external` + `launch-ready`, когда пакет опубликован | координатор. Один и тот же coder может быть сегодня внутренним, завтра внешним — роль не переклеиваем (закрывает C9) |
| `type:*` (1) | `feature`, `bugfix`, `research`, `decision`, `infra`, `test`, `docs`, `debt`, `question` | координатор |

> Поправка по итогам сборки (TEST-REPORT, F2): в первоначальной редакции этой таблицы
> `type:question` отсутствовал, хотя question-цикл §4.6 без него не работает. В финальный
> словарь включён `type:question`; для него `phase:*`, `size:*` и `env:*` не применяются.
| `size:*` (1) | `S`, `M`, `L` | только координатор |
| `priority:*` (1) | `critical`, `high`, `medium`, `low` | координатор по слову владельца |
| `env:*` — высший уровень, которого должна достичь поставка (1) | `test`, `staging`, `production` | координатор |
| Флаги | `needs-human` (нужно решение/приёмка владельца), `launch-ready`, `has-pr`, `blocked-external` (ждём запуска владельцем) | по ситуации |

Отображение на действующий BOARD (закрывает C4): Бэклог=`inbox`, Ждёт=`blocked`,
К работе=`ready`, В работе=`in-progress` (+phase показывает, где именно), На проверке=`review`,
Правки=`rejected` (возврат исполнителю), На приёмку=`review` + `needs-human` после approve
ревьювера и слияния координатором, Готово=`done` (ставится после приёмки, см. C5 в §5).
Projects-колонки настраиваются фильтрами по этим labels 1:1 — дрейф вида виден сразу.

### 4.3. Цикл задачи (канон + ARCA внутри)

```
Владелец (слово)
 → Координатор: issue (бриф, критерии, размер, радиус, исполнитель, ревьювер,
   зависимости, env) + status:ready | blocked        [шаг канона, без изменений]
 → Исполнитель: status:in-progress, phase:audit
     S: один комментарий «мини-аудит + conclusion» → координатор approve в ответ
     M: AUDIT → (ревью фазы) → RESEARCH → CONCLUSION
     L: как M + RESEARCH оформлен ADR в docs/decisions/
 → ГЕЙТ: координатор ставит phase:action               [только координатор]
 → Исполнитель: ветка поставки от свежего main проекта, работа строго по conclusion,
   обновляет паспорт модуля и DEBT.md в той же ветке, письмо о поставке
   (комментарий ACTION в issue + запись в mailbox проекта со ссылкой), phase:verify, status:review
 → Ревьювер (не автор): чек-лист WORKFLOW §4 + соответствие conclusion.
   approve → «на приёмку»; правки → status:rejected, счётчик итераций +1 (макс. 2 — C2)
 → Координатор: слияние, регресс на результате, merge-пост, снятие phase, status:review + needs-human
 → Владелец: приёмка → координатор ставит status:done и закрывает issue.
   Инфраструктурное (CI/доки процесса): координатор принимает сам, needs-human не ставит,
   владельца уведомляет сводкой (правило канона сохраняется).
```

Зависимости (C6): единственный формат — строка `Depends on: #N, #M` в теле issue +
label-логика: есть незакрытые зависимости → `status:blocked` ставит координатор при создании
и снимает на мониторинге, когда все зависимости `done`. Проверка агентом перед взятием —
вторая линия защиты, а не основная обязанность. Projects-поле Depends On не ведём.

### 4.4. Размеры и фазы

| Размер | AUDIT | RESEARCH | CONCLUSION/гейт | Кто ревьюит фазы (C12) |
|---|---|---|---|---|
| S — дифф одним предложением: опечатка, конфиг, строка доков | Одним комментарием вместе с conclusion (3–5 строк: что посмотрел, что меняю, как проверю) | Не нужен | Координатор approve ответным комментарием; `phase:action` не ставится — вместо неё сам approve-комментарий | Координатор |
| M — внутри одного модуля | Отдельный комментарий по шаблону, ≤1 экран | Отдельный комментарий, ≥2 варианта + рекомендация | Шаблон с обязательным «Отвергнуто»; гейт `phase:action` | AUDIT/RESEARCH — architect-роль (если назначена на проект) иначе координатор; CONCLUSION — всегда координатор |
| L — несколько модулей / интерфейсы / новый модуль | Как M | **ADR** (`proposed`) в `docs/decisions/` | Гейт после approve ADR координатором; ADR → `accepted` тем же решением | Architect обязателен на RESEARCH; CONCLUSION — координатор |

Если в ACTION выяснилось, что conclusion неполон: стоп, дописать conclusion,
повторный гейт. «Починить по ходу» запрещено (правило прототипа, сохраняем).
Конвейер больших задач канона (C14) — это **надстройка над L**: этап сначала проходит
6 ступеней канона и порождает L-задачи, каждая из которых идёт по ARCA внутри.
Не два конкурирующих процесса, а два уровня вложенности.

### 4.5. Окружения: абстрактные гейты уровней (решение владельца)

Общий слой не называет веток. Он называет **уровни и условия перехода коммита между ними**.
Проектный слой обязан опубликовать таблицу отображения «уровень → ветка/механизм/стенд».

| Переход | Кто выполняет | Условия (все) | Self-merge |
|---|---|---|---|
| Поставка → **test** | Исполнитель | CI проекта зелёный; issue в `phase:verify`; PR связан с issue | **Разрешён исполнителю** (решение владельца). Пост-фактум выборка ревьювером — на усмотрение проектного слоя; в `status:done` из test ничего не попадает без приёмки ниже |
| test → **staging** | Только координатор | Все issue поставки в `review` с approve ревьювера (второй заход обязателен здесь, если его не было на test); нет открытых question по поставке; регресс уровня staging зелёный | Нет |
| staging → **production** | Только координатор + приёмка владельца | Smoke на staging `done`; soak-период проекта истёк (параметр проекта, в общем слое — «задан проектом, не ноль для пользовательских изменений»); нет открытых `priority:critical`; `needs-human` + approve владельца; план отката в описании релиза | Нет. На уровне GitHub — environment required reviewer ≠ автор и prevent self-review, где применимо |

Инварианты: (а) в production попадает **тот же SHA**, что прошёл staging (промоушен коммита/
артефакта, не слияние ветки в ветку «для догонки»); (б) прямой обход уровня запрещён,
единственное исключение — HOTFIX (§4.7); (в) `env:*` на issue — это потолок поставки,
а не текущий уровень: текущий уровень виден по PR/релизу, а не по label (не плодим сущности).

### 4.6. Question-цикл (закрывает C8)

1. Исполнитель создаёт issue по шаблону question: от кого, кому (роль), блокируемый issue,
   вопрос, контекст фазы, свои варианты ответа — обязательны, если есть.
2. Свой issue → `status:blocked` + комментарий `Blocked by #Q — одной фразой`.
   `phase:*` при этом **не меняется**: фаза заморожена, а не потеряна.
3. Адресат — координатор по умолчанию. Вопрос агенту-исполнителю координатор переадресует
   сменой `agent:*` на question-issue. Внешнему агенту вопрос уходит только launch-пакетом
   CONTINUE через владельца (`blocked-external` на question-issue).
4. Срок ответа: до следующего цикла мониторинга координатора; вопрос старше двух циклов —
   эскалация владельцу на ближайшей сводке. (Абсолютные часы задаёт проектный слой.)
5. Ответ — комментарий в question-issue с явным решением или «решай сам в рамках радиуса».
   Отвечающий закрывает question-issue; исполнитель снимает `blocked` (или это делает
   координатор на мониторинге), продолжает с замороженной фазы; если ответ меняет
   conclusion — повторный гейт.
6. Question, не блокирующий работу (уточнение «на будущее»), создаётся без перевода
   основного issue в `blocked` — блокируемость честно указывает создатель.

### 4.7. HOTFIX и эскалации

- **HOTFIX** (закрывает C11): право объявить — только координатор по слову владельца или
  при `priority:critical` + production-инциденте. Сокращённый ARCA: мини-аудит+conclusion
  одним комментарием (как S) при любом размере фикса; радиус — минимально возможный.
  Прямая поставка в production разрешена, но: второй заход ревьювера обязателен
  (HOTFIX не отменяет ревью, отменяет только soak и staging-остановку), пост-фактум в течение
  следующего рабочего цикла — issue на прогон пропущенного staging-регресса и запись в DEBT.md,
  если фикс создал долг. «Хочется быстрее» без инцидента — не HOTFIX.
- **2× rejected** (закрывает C2): счётчик итераций ведёт координатор в комментарии issue
  (`Итерация правок: 1/2`). Вторая `rejected` подряд → задача снимается с исполнителя,
  координатор пересматривает бриф/размер/радиус или меняет исполнителя; третья попытка —
  только с новым брифом. Это дословно правило действующего канона, прототип его потерял.
- **Отмена задачи:** координатор закрывает issue с комментом-обоснованием, label `status:rejected`
  при этом не используется (rejected = «переделай», а не «снято»). Правило BOARD п.4 сохраняется.

### 4.8. Документы и каналы (C7, C15, C16)

- **Паспорта модулей:** `docs/modules/<module>.md` по шаблону прототипа (+ поле «последнее
  обновление: дата, issue, кто»). Обновляет исполнитель в ветке поставки как последний шаг ACTION;
  ревьювер проверяет актуальность паспорта по чек-листу и может вернуть поставку за один этот пункт.
  Создавать паспорта задним числом на все модули запрещено: паспорт рождается с первой задачей,
  коснувшейся модуля (координатор создаёт каркас при создании issue, если паспорта нет).
- **DEBT.md:** реестр в репозитории проекта. Пишет любой агент **только в своей ветке поставки**;
  конфликт DEBT.md при слиянии разрешает координатор (реестр — append-mostly, конфликты решаются
  сохранением обеих строк с перенумерацией). Одна строка = один долг; чинить — отдельным
  `type:debt` issue по полному ARCA своего размера; `risk:high` → координатор создаёт issue
  немедленно, 3+ записей на модуль → issue на рефакторинг (правила прототипа, сохраняем).
- **Канал поставки (C15):** письмо о поставке живёт **комментарием ACTION в issue** (единый канал,
  виден ревьюверу и будущим агентам). Mailbox проекта получает короткую append-only запись:
  дата, issue, диапазон коммитов, ссылка на комментарий. Не дублирование текста, а указатель —
  mailbox остаётся журналом, issue — содержимым.
- **Диапазон коммитов и ветки (C17):** имя ветки — проектный слой; общий слой требует:
  ветка от свежего `main` проекта (или от базовой ветки, объявленной проектным слоем для уровня test),
  в письме — диапазон `base..head` и хеш кончика. Требование канона «самопроверка merge-base»
  сохраняется дословно.

### 4.9. Регресс (C13)

Общий слой: «перед каждым пушем — полный канонический список проверок проекта, без сокращений»
(канон). Проектный слой обязан опубликовать этот список; минимум по типам проектов:

- **Код:** тесты уровня, линтеры, сборка (как задано проектом).
- **Документация (включая этот репозиторий):** (1) все внутренние ссылки ведут на существующие файлы;
  (2) grep на проектные имена в общем слое — пусто; (3) YAML шаблонов валиден;
  (4) labels, упомянутые в доках, существуют в репозитории (`gh label list`);
  (5) нет `TODO/[...]` плейсхолдеров без владельца и срока. Прогон этого списка по docs-пакету —
  приложение к письму о поставке данной задачи (см. TEST-REPORT в финальном комплекте — AGENT-DOCS-SPEC §4).

## 5. Таблица решений «было → стало → почему»

«Было» = противоречащие редакции канона/прототипа (AUDIT §4). «Стало» = норма варианта C.

| # | Было | Стало в C | Почему |
|---|---|---|---|
| C1 | Self-merge в develop без ревью vs абсолютный второй заход | Self-merge разрешён **только на уровень test**; в staging/production второй заход обязателен; в `done` без приёмки ничего не попадает | Решение владельца + прототипная скорость на тесте сохранена, а риск ограничен уровнем, где цена ошибки минимальна |
| C2 | Бесконечный rejected-цикл vs канон «2 итерации» | Канон: счётчик у координатора, 2× rejected → снятие задачи, пересмотр брифа/исполнителя | Бесконечные переделки = неверный бриф или размер, а не упорство исполнителя |
| C3 | «Координатор не пишет код» vs «может исполнить сам» | Канон: координатор может исполнить малую задачу по полному циклу, но не ревьюит и не гейтит сам себя: гейт и ревью — другой агент/ревьювер | Иначе на малых командах задачи стоят в очереди при свободном координаторе |
| C4 | 8 русских колонок vs 7 status-labels без отображения | Одна шкала `status:*` (§4.2) + таблица отображения на колонки BOARD 1:1; Projects — вид фильтрами | Один словарь состояний; борд перестаёт быть вторым источником правды |
| C5 | `done` ставит координатор, приёмка владельца выпала | `done` — только после приёмки владельца (продуктовое) либо приёмки координатором с уведомлением (инфраструктурное, правило канона); до этого — `review` (+`needs-human`) | Приёмка — продуктовое решение человека; терять её в lifecycle нельзя |
| C6 | Depends-on в трёх местах, отвечает непонятно кто | Один формат в теле issue; blocked ставит/снимает координатор; агент проверяет перед взятием как вторую линию | Дубли форматов гарантированно расходятся |
| C7 | DEBT.md пишут все, конфликты не разрулены | Пишут только в своей ветке поставки; конфликты разрешает координатор; нумерацию при слиянии правит он же | Реестр один на проект; append-mostly минимизирует конфликты |
| C8 | Question без адресата-срока-закрытия | Полный цикл §4.6: адресат, заморозка фазы, срок 2 цикла мониторинга, закрывает отвечающий | Вопрос без SLA — главный генератор зависаний внешних агентов |
| C9 | 10 agent-labels, external как отдельная роль | 7 ролей + флаг `external`/`launch-ready` | Внешность — свойство запуска, а не функции; роль не переклеивается между сессиями |
| C10 | Ветки develop/staging/main и `[N часов]` в общем тексте | Абстрактные уровни-гейты (§4.5); ветки, стенды и soak — параметры проектного слоя; в общем слое плейсхолдеров нет | Проект-агностичность (решение владельца) + инвариант одного SHA вместо слияний по цепочке |
| C11 | HOTFIX: прямой PR в main, критерии отсутствуют | HOTFIX объявляет координатор; ревью не отменяется; пост-фактум staging-регресс + DEBT-запись | Скорость при инциденте — да, тихий обход гейтов «потому что срочно хочется» — нет |
| C12 | Ревью фаз — то architect, то координатор | Матрица §4.4: фазы M/L ревьюит architect (или координатор, если architect на проект не назначен), conclusion — всегда координатор | Один гейткипер на фазу; главный гейт (action) — у держателя брифа |
| C13 | «Полный регресс» не определён для доков | Общее правило канона + обязательный опубликованный список проекта; минимум для docs — §4.9 | Неопределённый регресс = непроверяемый регресс |
| C14 | Конвейер больших задач и ARCA не связаны | Вложенность: конвейер канона порождает L-задачи, ARCA идёт внутри каждой | Два уровня одного процесса, а не два процесса |
| C15 | Письмо в mailbox И комментарий ACTION | Письмо = комментарий в issue; mailbox — короткая запись-указатель со ссылкой и диапазоном коммитов | Один текст поставки; журнал сохранён, дублирования нет |
| C16 | Reviewer «ничего не меняет», паспорт правит только исполнитель | Так и остаётся, + ревьювер вправе вернуть поставку за неактуальный паспорт отдельным пунктом правок | Паспорт — часть поставки, а не побочный эффект |
| C17 | `work/<#>-<slug>` от main vs `feature/<#>-<slug>` от develop | Имя и базу задаёт проектный слой; общий слой требует свежесть базы и объявленный диапазон в письме | Имена веток — конкретика проекта по правилу слоёв |
| C18 | Код в develop до приёмки, откат не описан | На уровень test сам исполнитель; дальше поставки двигает только координатор после approve; непринятое на test просто не промоутится (откатывать нечего) | Промоушен вместо слияний убирает проблему отката из общего слоя |

Плюс находки AUDIT §5 закрыты так: тайм-ауты — §4.6 п.4 и мониторинг координатора
(правило «блокер старше двух циклов — в сводку владельцу» распространяется на все `blocked`);
отмена задачи — §4.7; параллельные радиусы — координатор не ставит две `in-progress` задачи
с пересекающимся радиусом одному модулю (проверка по паспорту модуля при создании issue);
метрики — координатор раз в цикл считает по labels: время `inbox→ready`, долю `rejected`,
число задач, дошедших до `done` с первой попытки (сводка владельцу, без отдельной системы);
безопасность launch-пакетов — в шаблон LAUNCH добавлен запретный список: секреты, адреса
внутренней инфраструктуры и креды в пакет и issue не кладутся никогда (правило канона, продублировано в точке риска).

## 6. Что осталось решить владельцу (не блокирует чтение пакета)
