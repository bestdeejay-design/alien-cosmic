# MAIL — письмо о поставке внешнего узла (формат)

Этот файл — описание формата письма-поставки узла **без записи в issues**
(AGENT_RULES §2, §4.4, §12.3; COORDINATOR_RULES §6). Узел не может комментировать
issue, поэтому кладёт письмо файлом `docs/MAIL.md` на кончик своей ветки; триггер
для координатора — новый коммит ветки: он забирает её, сверяет диапазон коммитов
и ретранслирует письмо в issue от себя, не редактируя смысл. При ретрансляции
координатор фиксирует в issue фактический head ветки и полный диапазон коммитов
итерации (решение владельца, делегированное координатору 03.11).

Обязательный состав письма:

1. Первая строка — маркер `📬 DELIVERED #N — <суть одной фразой>`; вторая —
   подпись `— <роль-исполнителя> · сессия <id>` (BUS, «Подпись узла»).
2. Ветка поставки (только своя) и точный диапазон коммитов от–до, кончик ветки.
3. Что сделано и зачем — по CONCLUSION, без пересказа всего диффа.
4. Как проверено — проверки регресса поименно + ручные шаги.
5. Что красное и почему (или «красного нет»); что не проверено и почему.

Конкретное письмо — в блоке «Пример» ниже; имена и ветка там — плейсхолдеры
(`arena/<hash>-<slug>`), не существующие сессии.

---

## Пример

```markdown
📬 DELIVERED #1 — итерация 2 по вердикту ревьювера: 4 механические правки закрыты, ждёт ре-чек
— <роль-исполнителя> · внешняя сессия, узел без записи в issues (письмо файлом, ретрансляция за координатором)

# Письмо о поставке — issue #1, итерации правок 1–2

## Что это и почему файлом

Я — внешний узел **без доступа к записи в issues**: комментарии и labels ставить
не могу физически, могу только пушить свою ветку. Поэтому это письмо лежит файлом
`docs/MAIL.md` в ветке поставки, а в issue его переносит координатор. Прошу
ретранслировать текст без редактирования смысла; замечания — отдельным
комментарием ниже.

## Диапазон поставки

- Ветка: `arena/<hash>-<slug>` (только она; главная и чужие не тронуты).
- Первичная поставка, принятая к аудиту: `<base>..<head1>`.
- Эта итерация: следующие коммиты на той же ветке после `<head1>`; кончик —
  коммит, содержащий это письмо и правки ниже. Точный head смотрит вотчер/
  координатор по ветке; коммитов вне этого письма в итерацию не включаю.

## Что сделано в этой итерации (по 4 пунктам аудита)

1. **Письмо о поставке** — этот файл `docs/MAIL.md` вместо невозможного комментария.
   Заодно в AGENT_RULES §2/§4.4 и COORDINATOR_RULES §6 канал письма разведён
   по доступу узла: комментарий для пишущих в issues, файл + ретрансляция для
   внешних без записи. Добавлен раздел «режимы связи по типам узлов»
   (AGENT_RULES §12.1, COORDINATOR_RULES §6/§11).
2. **Парковка дежурных сессий** — AGENT_RULES §12.2: цикл «свежесть → скан фильтра
   → перечитал → claim → работа → сдача → обратно в ожидание», сессия после задачи
   не завершается; COORDINATOR_RULES §4.5/§11: stale-claim reaper (пинг без движения
   S=15м / M=60м / L=день, второй интервал — `♻️ RECLAIMED` в ready), гигиена
   закрытых issues; EXAMPLES §10 — парковочный промпт (КТО ТЫ / ГДЕ ЧТО ЛЕЖИТ /
   какие задачи брать / как ждать / как брать и сдавать), §11 — две задачи подряд
   без участия владельца.
3. **Единый словарь маркеров** — KNOWLEDGE_BASE §5: одна таблица канона,
   1-в-1 с BUS.md. Принято наше расширенное ядро (`📬 DELIVERED` — поставка,
   `🏁 DONE` — только после приёмки), добавлены LAUNCH/CONTINUE/HOTFIX, READ,
   CONCLUSION, GATE CLOSED, VERDICT, QA, HEARTBEAT, PING, RECLAIMED, DECISION, CI;
   единые знаки гейта (`✅ GATE OPEN` / `❌ GATE CLOSED`) записаны явно. Правка
   самого BUS.md — за координатором, как он и указал.
4. **Свежесть скриптов** — `scripts/wait-signal --version` печатает версию и SHA-256 скрипта (сверять с свежим клоном)
   и SHA-256 самого файла; при обычном старте версия/хеш выводятся в stderr.
   В AGENT_RULES §12.2 и KNOWLEDGE_BASE §5.2 — правило: перед каждым ожиданием
   обновить клон и сверить `--version`; старый скрипт не ждёт, а молчит.

Попутно закрыто из комментариев владельца, ещё не попадавшее в аудит: обязательные
разделы launch «КТО ТЫ» и «ГДЕ ЧТО ЛЕЖИТ» (COORDINATOR_RULES §6, EXAMPLES §6).

## Как проверено

- `scripts/wait-signal --version` — печатает версию и SHA-256.
- Регресс `wait-signal` на fixture issue #3: DONE ловится (exit 0), `--version`
  не требует issue, claim по не-ready по-прежнему честно даёт exit 3.
- Ссылки внутри docs, `bash -n` всех скриптов, `git diff --check` — зелёные;
  словарь маркеров сверен grep'ом между KNOWLEDGE_BASE, AGENT_RULES,
  COORDINATOR_RULES, EXAMPLES и комментарием скрипта. Полный разбор YAML
  шаблонов в этом окружении недоступен (нет PyYAML) — в этой итерации YAML
  не менялся, проверены только отсутствие табов и структура диффа.
- Проект-агностичность: новые разделы не содержат имён проектов/команд, кроме
  подписи этой сессии в этом письме.

## Что красное / не проверено

- Живую парковку двумя задачами подряд я показать не могу: это проверяется
  локальной сессией с записью в issues на полигоне владельца; у меня — только
  пуш ветки. Протокол и промпт готовы, демонстрация — за SZ/координатором.
- GitHub Project в этой итерации не трогался (как и было: нужен scope `project`).
- На момент итерации 1 это не было финальной приёмкой: дальше по аудиту —
  второй глаз ревьювера, затем решение координатора о слиянии.

## Итерация 2 — по вердикту ревьювера (4 механические правки)

Ревьювер прочитал все 25 файлов, подтвердил labels 52/52, ETag/304, YAML и отсутствие
битых ссылок; блокеров нет. Закрываю его четыре правки:

1. **Мёртвая переменная `MARKERS` удалена** из `scripts/wait-signal`: в ней жили
   чужие эмодзи (`✅ DONE`, `🛑 BLOCKED`, `📋 CONCLUSION`, `🧑 NEEDS-HUMAN`,
   `✨ READY`) вне единого словаря KNOWLEDGE_BASE §5. Скрипт словарём не пользуется
   (матчинг идёт по словам из `--match`), поэтому переменная просто вырезана.
2. **Несуществующий сигнал READY убран из EXAMPLES §9.** Labels не являются
   маркерами: рой находит кандидата сканом открытых issues по `status:ready` +
   `to:sz-pool` + своей функции каждые 60–120 секунд, а `wait-signal` подключается
   когда issue уже известен. Команды claim в примере дополнены `--claim-as sz-N`.
3. **`--since` для комментариев исправлен на явный TAB-разбор**
   (`IFS=$'\t' read -r ts rest`): метка времени отделяется от первой строки
   разделителем, который реально выдаёт jq, а не паттерном из пробелов.
4. **Клин сбойного claim снят.** `wait-signal --claim` теперь запоминает ID своего
   claim-комментария; если PATCH labels падает, скрипт удаляет только собственный
   комментарий и не оставляет задачу навсегда BUSY. Если найден собственный
   claim-комментарий без смены labels (прерванная попытка), claim возобновляется
   повторным PATCH без дубля комментария.

Пункты «для координатора» из того же вердикта (лимит AGENT_RULES ≤250 при факте
354 строк, семантика `👀 READ` против BUS.md, mock-issues #2/#3 без разметки) —
не мои правки этой итерации: фиксирую здесь, чтобы координатор решил их при слиянии.

Проверка итерации 2: `bash -n scripts/wait-signal`; `--version` печатает версию
и SHA-256; регресс DONE на fixture #3 (exit 0); claim по не-ready — exit 3;
явный TAB-разбор проверен на старой и новой датах. Живой claim-спор и парковка —
по-прежнему за локальными сессиями на полигоне.

Прошу ревьювера о быстром ре-чеке только этих четырёх мест; дальше — его approve
и решение координатора о слиянии.
```
