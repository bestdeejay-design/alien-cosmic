### 1.2. Фактическое состояние GitHub (проверено `gh api`, 27.10.2026)

| Проверка | Факт | Вывод |
|---|---|---|
| Labels | Только 9 дефолтных GitHub (`bug`, `enhancement`, `question`, …). Ни одного `agent:*` / `status:*` / `phase:*` | Вся таксономия прототипа — пока бумажная. Создание labels — отдельный шаг внедрения, нужен список + цвета + идемпотентный скрипт/`gh label create` |

| Настройки слияний | Разрешены merge + squash + rebase одновременно; `delete_branch_on_merge = false` | Нет выбранного способа слияния и авто-удаления веток поставок — для агентских веток это источник мусора и неоднозначной истории |
| Branch protection / Projects API | Интеграция `gh` вернула `403 Resource not accessible by integration` | **Не «защиты нет», а «проверить этим доступом нельзя».** Аудит не утверждает отсутствие protection. | Ветки | Только `main` + ветка поставки этой сессии | Модель «ветка поставки, не в main» из WORKFLOW.md уже работает на практике |

### 1.3. Что в текущем каноне сильно (сохранить в любом варианте)

1. **Единственная точка входа:** слово владельца становится брифом только через координатора.
2. **Поставка = ветка + письмо с диапазоном коммитов.** Поставки без письма не существует.
3. **Второй заход:** ревью — агент, не являющийся автором. Максимум 2 итерации правок → эскалация.
4. **Приёмка продуктового — только владелец;** инфраструктурное координатор может принять сам с уведомлением.
5. **Холодный старт сессии** из 5 шагов (протокол → статус → `git fetch` → нет задачи = нет работы → восстановление с origin).
6. **Конвейер больших задач:** аудит → ресёрч → репо этапа → задачи → перекрёстный аудит → реализация.
7. **Правило слоёв:** общий репо без единой проектной ссылки; конкретика — копией в проектный репо.

Эти 7 пунктов прототип не заменяет, а детализирует. Любой вариант, который их ослабляет, — регрессия.

## 2. Аудит прототипа: что он добавляет ценного

| Добавка прототипа | Ценность | Где в текущем каноне пробел |
|---|---|---|
| Таксономия labels `agent/status/type/priority/env` + `phase/size` | Машиночитаемое состояние: агент находит «свои ready» одним фильтром, без чтения борда глазами | BOARD.md описывает колонки словами; фильтра для агента нет |
| ARCA: AUDIT→RESEARCH→CONCLUSION→ACTION, гейт `phase:action` только у координатора | Запрет «сразу кодить» оформлен как переход состояния, а не как призыв. Близко к Explore→Plan→Implement→Commit (см. ресёрч §3) | WORKFLOW.md требует конвейер только для БОЛЬШИХ задач; для обычной задачи фазы не формализованы |
| Радиус аудита задаёт координатор в issue | Защита от расползания аудита на весь проект; агент не выбирает радиус сам | Отсутствует полностью |
| Фиксированные шаблоны AUDIT/RESEARCH/CONCLUSION (≤1 экран, обязательное «Отвергнуто») | Следующий агент за минуту понимает, что отвергли и почему; не исследует тупик повторно | Письмо о поставке формализовано, а промежуточные артефакты — нет |
| Размеры S/M/L с разной церемонией | Не каждая задача — полный цикл; S = 3–5 строк одним комментарием | Отсутствует градация: сейчас один цикл на всё |
| Паспорта модулей (живые, обновляются, а не плодятся аудиты) + DEBT.md (1 строка = 1 долг, чинить только отдельным issue) | Против накопления 40 мёртвых аудитов; чтение агента = паспорт + указанные ADR + долг по зоне | Отсутствует; HANDOFF/статус-карточка частично закрывают, но не на уровне модуля |
| LAUNCH / CONTINUE / HOTFIX пакеты для внешних агентов | Внешний агент запускается владельцем вручную — пакет = самодостаточный бриф для холодной сессии | PROTOCOL упоминает внешних только как «при назначении — любой агент» |
| Question-issue как блокирующий механизм | Блокер — отдельный артефакт с адресатом, а не строка в комментарии | Отсутствует: «спросить координатора» без формата и SLA |

## 3. Аудит прототипа: структурные риски (до противоречий)

**Р1. Комбинаторный взрыв labels.** В прототипе 10 `agent:*` × 7 `status:*` × 9 `type:*`
× 4 `priority:*` × 3 `env:*` × 5 `phase:*` × 3 `size:*`. Без правила «ровно один label
из каждой группы» один issue легко несёт `status:ready` + `status:blocked` одновременно,
и два агента прочтут состояние противоположно. В прототипе правило единственности
нигде не сформулировано. (Внешний аналог проблемы и требование label-repair — ресёрч §1.)

**Р2. Три источника правды одновременно.** Прототип объявляет каноном и labels,
и GitHub Projects (кастомные поля Assigned Agent / Depends On / Target Env дублируют
labels один в один), а текущий BOARD.md добавляет третий — колонки Projects + mailbox.
Дубли без правила синхронизации расходятся гарантированно; вопрос только когда.
Владелец уже решил: labels — канон, Projects — вид (см. README пакета).

**Р3. Длинные живущие ветки develop→staging→main как механизм промоушена.**
Прототип мержит ветку в ветку по цепочке. Внешние данные (DORA/trunk-based, ресёрч §5)
и обычная практика «build once, promote the same artifact/commit» говорят: промоутить
надо тот же коммит/артефакт, а не результат повторного слияния. На общем (абстрактном)
слое это решается просто: задаём гейты уровней, а не имена веток — владелец это уже выбрал.

**Р4. Prompt-only enforcement.** Все запреты прототипа («не коди до phase:action»,
«не мержь в main») — текстовые. Текст агент может нарушить молча. Там, где GitHub даёт
детерминированный механизм (branch protection/rulesets, CODEOWNERS, environment
required reviewers + prevent self-review, required checks), правило должно ссылаться
на механизм, а не только на инструкцию (ресёрч §4, §6). Для docs-only репозиториев
механизмов меньше — остаётся второй заход + проверка labels/диапазона коммитов координатором.

**Р5. Прототип писан под кодовый репозиторий** (`src/`, `tests/`, `infra/`, CI unit/integration/e2e),
а этот репозиторий — docs-only и публичный. Зоны ответственности по папкам и «CI прошёл»
на общий слой переносятся только как абстракция («зона = список путей, задаёт проект»;
«регресс = канонический список проверок проекта»). Иначе общий слой начнёт врать
проектам без `src/`.

**Р6. Стенограмма ≠ спецификация.** В `reference-workflow-source.txt` одни и те же
правила встречаются в редакциях разных дней и местами расходятся (например, кто ревьюит
AUDIT: в ARCA-части — architect, в AGENT_RULES файла 1 — «жди approve от координатора»).
Брать из стенограммы можно только через таблицу решений (WORKFLOW-VARIANTS §5),
а не копированием «финальных файлов» как есть.

## 5. Чего в обоих слоях нет (пробелы, найденные аудитом)

1. **Тайм-ауты и эскалации по времени:** нигде нет «ревью не пришло за X → координатор пингует/переназначает». Для внешних агентов, запускаемых владельцем вручную, это главный источник зависаний.
2. **Отмена/отзыв задачи:** `status:rejected` — это «переделай», а не «задача снята». Статуса/правила закрытия без приёмки в прототипе нет (в каноне есть: закрытие с комментом-обоснованием, BOARD п.4 — прототип это потерял).
3. **Параллельная работа двух агентов над одним модулем:** радиусы могут пересекаться; правило сериализации/очереди на модуль не задано.
4. **Версионирование самих регламентов:** кто и как меняет AGENT_RULES (только владелец через координатора — есть в PROTOCOL про протокол, но прототип свои файлы в этот контур не вписывает; CODEOWNERS на регламенты — ресёрч §6).
5. **Метрики здоровья воркфлоу:** время inbox→ready, доля rejected, число циклов ARCA на задачу. Без них через полгода непонятно, помогает ARCA или тормозит. (DORA-подобные метрики для агентских поставок — ресёрч §5.)
6. **Безопасность внешних запусков:** launch-пакет уходит внешнему агенту; что нельзя класть в пакет (секреты — запрещено каноном, но в шаблоне LAUNCH поля «Репо/Регламент/Входные данные» провоцируют вставить лишнее). Нужен явный запретный список в шаблоне.

## 6. Вывод аудита

Прототип — сильное **содержание** при слабой **форме**: стенограмма, три редакции одних
правил, 6 блокирующих противоречий с действующим каноном. Копировать «8 готовых файлов»
в репозиторий нельзя — они унаследуют противоречия и через месяц разойдутся с практикой.
Правильный путь, который и выбран владельцем: сначала этот аудит и варианты
([WORKFLOW-VARIANTS.md](./WORKFLOW-VARIANTS.md)), затем сборка финального комплекта
под выбранный вариант по спецификации ([AGENT-DOCS-SPEC.md](./AGENT-DOCS-SPEC.md)).
