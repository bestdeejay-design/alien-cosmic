# FIELD-LESSONS-FONOTEXT — полевой опыт координатора (проект Fonotext, 10.2026)

> Автор: координатор (ZCode). Статус: на ревью владельца.
> Это не новый канон, а проверенные находки из реального проекта (панель руководителя,
> 76+ issues, параллельные сессии Арены), оформленные так, чтобы их можно было
> вплести в существующие документы. Ссылки на канон — где какая находка его дополняет.

## 1. Координаторские живые проверки: у исполнителя нет браузера (→ COORDINATOR_RULES)

Сессии Арены работают в песочнице без GUI-браузера (chromium без libnspr4/libnss3 не
стартует). CSS/вёрстка, проверенные только каскад-арифметикой и DOM-разбором, всё равно
ломаются на живом рендере (реальный кейс: mobile-регрессия `.rail`, три цикла фиксов).

**Правило:** в брифе исполнителя заранее фиксируй разделение труда — «верификацию
вёрстки делает координатор живым рендером; тебе доступны код, DOM-разбор, jsdom».
Координатор рендерит демо-стенд локально (`http.server` + IAB/Playwright) и прикладывает
к приёмке скриншоты + замеры геометрии через `evaluate` (getBoundingClientRect,
computed style). Это закрыло пункт, который трижды не ловил исполнитель.

## 2. Временные бомбы в тестах — правило «никаких зашитых календарных дат» (→ §Качество)

Третий раз за неделю один и тот же тест падает не из-за продукта: входные данные
зашиты на конкретные даты (2026-10-18…22), а логика отсчитывает окно от «сегодня».
Через несколько дней сценарий теста разъезжается с календарём.

**Правило для регресса:** grep-гейт на `20\d\d-10-` (или любой литеральный год-месяц)
в тестах, где логика зависит от текущей даты; входные данные генерировать относительно
`now`. Упадёт — сначала проверь, не бомба ли это, прежде чем считать это продуктовым
багом (но и не наоборот: бомба маскирует реальные падения, чинить её — отдельная задача,
не «заодно»).

## 3. Бриф для агента самодостаточен, вопросы — одной посылкой (→ WORKFLOW §1)

Внешняя сессия не может быстро спросить: вопрос идёт через владельца текстом.
Рабочая схема, проверенная на 10+ сессиях:
- бриф содержит всё: контракты, которые нельзя ломать (списком с тестами), известные
  чужие находки («не повторяй сделанное» — таблица этапов), что сдавать и в каком виде;
- вопросы копятся и задаются ОДНОЙ посылкой («скинуть тебе?» = «да, присылай весь
  список»), владелец отвечает одним сообщением;
- исполнитель НЕ пишет в issues, НЕ мержит, не двигает борд — только ветка + письмо.

## 4. Песочница для внешних ИИ-аудиторов (→ WORKFLOW §6, конвейер)

Когда нужен конкурс идей от внешних агентов (UI, архитектура), они не читают репо —
им нужен пакет: **бриф (состав проекта, домен, контракты, критерии приёмки) +
синтетическая копия данных одной командой + готовые экраны для сравнения**.
Проверено: `panel_demo.py --ui` собирает 1,6 МБ (SQLite-снапшот + JSON-артефакты +
24 HTML-экрана) без ПДн. Ключевое в брифе: «не добавлять фичи — сделать сценарий
видимым», и критерий вида «непосвящённый за 5 минут находит главное».

## 5. GitHub Projects V2: грабли CLI и правило триажа (→ BOARD)

Полевое, заплатили недовольством владельца («выполненные в туду», «почему 24 задачи,
а номер 75»):
- **Доска = только активная работа.** Закрыл issue → Done → сразу `item-archive`
  (архив не удаляет). Закрытые issues в Todo «пока решение не принято» владельцем
  читаются как бардак.
- **Номер issue ≠ номер задачи в списке** — нумерация сквозная за жизнь репо;
  владельцу это проговаривать явно.
- Статус выставляется **в момент создания** карточки; решения владельца — метка
  `decision-needed`.
- CLI: `gh project item-list --format json` НЕ отдаёт fieldValues — статус читать
  GraphQL-типом `ProjectV2ItemFieldSingleSelectValue` (запрос `field{name}` внутри него
  ломается — читать только `name`); `item-edit` без `--silent`; `item-add` на
  существующий item молча возвращает тот же id (идемпотентно).
- **Auto-add workflow:** серый текст в поле Filters может быть СОХРАНЁННЫМ фильтром,
  а не подсказкой (маркер — подпись «See 0 existing items that match»). Унаследованный
  `label:bug` тихо отключал добавление. Лечится очисткой поля до пустого.
- Проверка автоматизации — только живьём: тестовый issue → `issue.projectItems` через
  GraphQL → закрыть → Status=Done → item-archive → тестовые issues закрыть.

## 6. Правила рождаются письменно после прецедента (→ PROTOCOL)

Не пытайся расписать канон заранее на все случаи. Прецедент (затяжные правки Арены,
«письмо без формата», ревью «сам себя») → письменное правило (у нас — ARENA-CONTRACT:
письмо о поставке из 5 пунктов, ревьювер ≠ автор, лимит 2 итераций). Владелец
одобряет одним «да». Так канон растёт из практики, а не из фантазии.

## 7. Простой вопрос ≠ переделка артефакта

Вопрос владельца («есть ли документ про все функции?») — это вопрос, а не заявка на
генерацию документа. Сначала ответ текстом с картиной того, что есть; предложение
сделать — отдельным пунктом с вопросом «для кого». Отдельно: недопонятое «да»
владельца — повод СНАЧАЛА спросить, что он имел в виду, при возврате темы (реальный
кейс недочитанной мотивации: три возможных смысла одной фразы).
