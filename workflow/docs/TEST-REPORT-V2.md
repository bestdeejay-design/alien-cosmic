## 2. Живой замер conditional requests (требование владельца к рою)

Стенд: `GET repos/bestdeejay-design/agents/issues/1/comments` через `gh api`.

| Шаг | Результат |
|---|---|
| `gh api rate_limit` до | `remaining=9138, used=212, limit=9350` |
| Безусловный GET (взять ETag) | `200`, ETag получен |
| 5 авторизованных GET с `If-None-Match` | все `304 Not Modified`; `x-ratelimit-remaining` на условных ответах не уменьшался |
| `gh api rate_limit` после | `remaining=9136, used=214`: расход ровно 2 — два безусловных 200-запроса; пять 304 стоили 0 primary |

Вывод: документация GitHub подтверждается замером — авторизованный 304 бесплатен
для primary rate limit. Экономика роя: 5 SZ × поллинг 90 с × 2 эндпоинта без ETag
= ~400 безусловных запросов/час на общий бюджет; с ETag платятся только изменившиеся
ответы. Именно поэтому ETag — не оптимизация, а условие существования роя.
Оговорка, зафиксированная и в скрипте: бесплатны **авторизованные** 304.

## 3. `wait-signal` v2: что изменилось и как проверено

Изменения: ETag-кэш на эндпоинт (`--state-dir`), `--since` (отсекает тело и
комментарии старше порога, включая устаревший DONE в теле), `--sha` (сигнал —
завершение всех check-runs коммита), `--claim "<роль/сессия>"` (захват по §5.1:
BUSY/NOT-READY → 3, CLAIMED → 0, LOST-арбитраж по раннему claim), интервал
по умолчанию 90 с, репозиторий из git remote без зависимости от GraphQL.

| Проверка | Ожидалось | Факт |
|---|---|---|
| `bash -n scripts/wait-signal` | OK | OK |
| Прогон 1 по fixture issue #3 (DONE) | exit 0, HTTP 200 | exit 0; debug: `issue -> HTTP 200 (etag cached: no)` |
| Прогон 2, тот же state-dir | exit 0 из кэша, HTTP 304 | exit 0; debug: `issue -> HTTP 304 (etag cached: yes)` |
| `--since 2999-…`, DONE в прошлом | таймаут, exit 1 | exit 1 (устаревший сигнал отсечён) |
| `--claim` по не-ready issue | отказ, exit 3, ничего не писать | `NOT-READY`, exit 3, записей не сделано |
| `--sha` на незапушенный коммит | не падать, таймаут exit 1 | exit 1, шум 422 подавлен |
| Невалидный `--issue x` | exit 2 | exit 2 |

Не проверено живьём и честно помечено: настоящий спор двух SZ за один claim
(нужны две пишущие сессии — в песочнице внешней сессии запись комментариев даёт 403,
см. первый TEST-REPORT) и полный час поллинга роя (замер §2 покрывает сам механизм
304; часовой прогон — задача проектного слоя при первом внедрении).

## 4. Остальные правки по аудиту (сводка)

- **Claim/аренда/heartbeat** роя: KNOWLEDGE_BASE §5.1, AGENT_RULES §3, EXAMPLES §9;
  протокол честно назван optimistic — GitHub CAS не даёт (эталон семантики — Beads).
- **Зависимости:** нативный `blocked by` — основной механизм, `Depends on:` — fallback;
  декомпозиция L — sub-issues (COORDINATOR_RULES §1, AGENT_RULES §3, KNOWLEDGE_BASE §2).
- **Точный SHA:** approve вердикта называет head-коммит, коммит после approve
  обнуляет его; мерж только этого SHA (AGENT_RULES §7, COORDINATOR_RULES §5,
  `docs/templates/pull_request_template.md` — новый файл).
- **Лестница принуждения** текст → протокол → rulesets → environments с требованием
  доказательств включения (COORDINATOR_RULES §12, AGENT-DOCS-SPEC §5); до уровня 2
  честный статус проекта — «гейты на дисциплине».
- **Безопасность:** недоверенный ввод/prompt-injection как норма (AGENT_RULES §9,
  предупреждение в task.yml); safe-outputs gh-aw — паттерн будущей автоматизации.
- **Качество входа в ACTION:** поименное покрытие критериев приёмки в CONCLUSION
  (analyze-шаг Spec Kit) и calibrate размеров S/M/L порогами (KNOWLEDGE_BASE §4).
- **Живучесть:** WIP-лимит 1 на исполнителя, заместитель координатора, ритм и порог
  метрик, reclaim просроченных захватов (COORDINATOR_RULES §4/§12).
- **Шаблоны:** паспорт — «проверен по коду» отдельно от «обновлён» + владелец;
  ADR — статусная правка как единственное исключение неизменяемости; HOTFIX —
  обязательный post-incident разбор до закрытия issue.

## 6. Честные находки второй сессии (трения, не «всё хорошо»)

1. **Наш собственный процесс чтения источников провалился первым:** регламенты были
   написаны по комментарию, который владелец потом отредактировал, и никто не перечитал.
   Правило перечитывания внесено, но это процессная заплатка; системно её усилит
   только `wait-signal` на само issue с заданием.
2. **Claim-протокол слабее эталона.** Beads даёт настоящий CAS; наш арбитраж
   «ранний claim + пауза + перечитывание» имеет окно гонки в секунды. Для 5 SZ и
   человеческих темпов это приемлемо, но называть его атомарным нельзя — в документах
   так и написано; кто внедрит — пусть не «усиливает» формулировки обратно.
3. **Гейты всё ещё на дисциплине**, пока проектный слой не включит rulesets/environments.
   Лестница §12 определяет целевое состояние, но не создаёт его; первый проект,
   внедряющий комплект, обязан прислать ссылки на rulesets как доказательство.
4. **Рой не прогонялся живьём.** Захват, heartbeat и reclaim проверены чтением
   протокола и тестами скрипта, но не пятью сессиями. Это следующий сухой прогон —
   уже силами внутренних SZ с правами записи.
5. **Документация комплекта растёт быстрее, чем её читаемость.** AGENT_RULES вырос
   с 249 до 290 строк при прежнем ориентире ≤250. Diataxis-разделение (how-to против reference) в этой
   сессии только помечено; если комплект вырастет ещё на четверть — нужна
   реструктуризация, а не новые разделы.
