# PROJECTS-BLUEPRINT — правильная настройка GitHub Projects для работы агентов

> Статус: чертёж второй/третьей сессии, **на применение владельцем или координатором
> с доступом `project`**. В этой сессии проект не настраивался: интеграционный токен
> внешней сессии видит, что у аккаунта есть проекты, но не читает их названия и поля
> (`Resource not accessible by integration`). Поэтому ниже — точная схема, ручная
> инструкция, автоматизируемая часть и чек-лист приёмки, а не отчёт о якобы выполненной
> настройке.
>
> Решения владельца, на которых построен чертёж: главный первый вид — **таблица
> контроля**; адресат показывается **конкретными `to:*` labels**; постановщик отдельной
> группой labels не заводится и пишется **только текстом в issue**; источник правды —
> labels, Projects — вид и инструмент управления вниманием.

## 1. Исходная проблема, которую решает настройка

Все агенты фактически работают через один GitHub-аккаунт владельца. Поэтому:

- GitHub **Author** у всех issue одинаковый и ничего не говорит о реальном постановщике;
- GitHub **Assignees** нельзя содержательно развести между владельцем, координатором,
  Ареной и SZ: это будет один и тот же пользователь;
- колонка **Assignees на борде не нужна** и скрывается во всех видах;
- реальная маршрутизация выражается labels:
  - `agent:*` — **какая функция нужна** (coder, reviewer, qa и т.д.);
  - `to:*` — **кто конкретно должен сделать следующее действие**;
  - сигнальные комментарии второй строкой содержат роль и сессию автора.

`to:*` — динамический label, а не вечный ярлык первого исполнителя. При переходе
задачи к следующему действующему лицу координатор (или исполнитель, меняющий статус
в пределах своих прав) заменяет его в той же операции, что и `status:*`. На открытой
задаче ровно один `to:*`; на принятой `done` и на отменённой задаче `to:*` снимается.

| Label | Адресат | Типовой момент |
|---|---|---|
| `to:owner` | Владелец | Нужно решение, ручной запуск Арена или приёмка |
| `to:coordinator` | Координатор | Триаж inbox, гейт, слияние, label-repair, мониторинг |
| `to:arena` | Внешний исполнитель Арена | После фактического запуска владельцем |
| `to:sz-pool` | Любой свободный SZ | Задача `ready` ждёт claim роя |
| `to:sz-1` … `to:sz-5` | Конкретный внутренний SZ | Назначен, выиграл claim или должен ответить/ревьюить |

Пример: задача сначала `agent:coder + to:sz-pool`, после claim — `to:sz-2`; после
поставки координатор меняет адресата на конкретного не-автора, например
`agent:reviewer + to:arena`; после approve и слияния — `to:owner` для приёмки;
после `status:done` label `to:*` снимается.

## 2. Постановщик: только текст в issue

Отдельной `from:*` группы нет — это сознательное решение владельца против лишнего
шума labels. В начале тела каждой задачи координатор обязан написать одну строку:

```text
Поставил: Владелец — слово в чате, 2026-10-27
Поставил: Координатор — по итогам разбора #N, 2026-10-27
Поставил: SZ-2 — question #Q превращён координатором в отдельную задачу
```

Форма задачи содержит для этого обязательное поле. Следствия приняты явно:

- по постановщику нельзя фильтровать/группировать борд — и не нужно;
- GitHub Author не использовать как замену: на общем аккаунте он у всех один;
- если когда-нибудь происхождение станет важным для отчётности, поле появится
  отдельным решением, а не молчаливым добавлением labels.

## 3. Что является правдой, а что — отображением

| Слой | Роль | Что хранит |
|---|---|---|
| Issue + labels | **Канон** | Бриф, критерии, `status:*`, `phase:*`, `agent:*`, `to:*`, приоритет, размер, сигналы и вердикты |
| GitHub Project | **Вид и пульт внимания** | Те же состояния в полях проекта, даты, группировки, фильтры, сроки и очереди |
| PR | Поставка | Код/документы, проверки, ссылка на issue без автозакрытия до приёмки; сам PR отдельным item в проект не добавляем |

У Projects есть собственное поле **Status**. Оно не связано с label `status:*`
автоматически. Переименование опций проекта под словарь labels не создаёт
синхронизацию: каждое изменение label пока сопровождается ручным обновлением полей
проекта по матрице §7. Встроенные workflows умеют auto-add, смену Status по событиям
добавления/закрытия и auto-archive, но не синхронизацию произвольных labels в поля.
Автоматическая синхронизация — будущая отдельная задача уровня GitHub Actions/API;
до неё истина при расхождении всегда labels и последний вердикт в комментариях.

Источник статуса — labels в issues везде и всегда (решение владельца, делегированное
координатору 03.11): вид Projects — опциональная надстройка видимости, а не канал
управления состоянием; при его недоступности статус читается напрямую из
labels/issues через `gh` (`gh issue view N --json labels,state`). Гейты варианта C
это не меняет.

**Запрет на период ручной синхронизации:** карточки по Board-колонкам не перетаскивать.
Перетаскивание меняет только поле проекта и не меняет labels, то есть создаёт дрейф.
Борд смотрим; переходы делаем в issue labels, затем правим поля проекта.

## 4. Один проект, а не проект на каждый репозиторий

Рекомендуемый контур — один пользовательский Project владельца для всех репозиториев
агентской работы, рабочее название **«Агенты — контроль»**. Причины:

- очереди владельца, координатора, Арена и SZ сквозные между репозиториями;
- поле **Repository** позволяет фильтровать один репозиторий, не плодя борды;
- auto-add добавляет issues из выбранных репозиториев по фильтру `is:issue`.

Если конкретному репозиторию позже понадобится свой фокус, это делается сохранённым
фильтром `repo:OWNER/REPO` в том же проекте, а не отдельным проектом.

В проект добавляются **только issues**. Pull requests не являются отдельными карточками:
они видны через встроенное поле **Linked pull requests** у issue. Так одна задача не
распадается на две карточки «issue + PR».

## 5. Поля проекта

### 5.1. Встроенное поле Status (переименовать опции)

Опции должны один в один повторять `status:*`. Цвета ниже — цвета опций Projects,
а не hex labels.

| Project Status | Label | Смысл |
|---|---|---|
| `Inbox` | `status:inbox` | Создана, координатор ещё не оформил |
| `Ready` | `status:ready` | Можно брать/claim-ить |
| `In progress` | `status:in-progress` | Идёт работа |
| `Blocked` | `status:blocked` | Ждёт зависимость или ответ |
| `Review` | `status:review` | Поставка на ревью/слиянии/приёмке |
| `Rejected` | `status:rejected` | Возвращена на правки |
| `Done` | `status:done` | Принята; issue закрывается координатором |

### 5.2. Создать custom fields

Не плодить поле на каждый label. Отдельное поле создаётся только там, где оно даёт
то, чего Labels не умеют: группировку, срез, сортировку, roadmap или дату.

| Поле | Тип | Значения / источник | Зачем |
|---|---|---|---|
| `Адресат` | Single select | Владелец, Координатор, Арена, SZ (пул), SZ-1…SZ-5; зеркало `to:*` | Группировать и резать очереди; Labels группировкой не являются |
| `Приоритет` | Single select | Critical, High, Medium, Low; зеркало `priority:*` | Сортировка контроля и срезы риска |
| `Размер` | Single select | S, M, L; зеркало `size:*` | Видеть церемонию/риск без раскрытия issue |
| `Фаза` | Single select | Audit, Research, Conclusion, Action, Verify, Не применяется; зеркало `phase:*` | Видеть, где именно стоит ARCA |
| `Начата` | Date | Дата первого перехода в `status:in-progress` | Фактическое начало, а не дата создания |
| `Срок` | Date | Необязательная целевая дата координатора | Просрочки и roadmap; не выдумывать срок каждой задаче |
| `Завершена` | Date | Дата перехода в `status:done` | Фактическое завершение принятой задачи |
| `Итерации правок` | Number | 0 при создании; +1 на каждый возврат поставки | Качество брифов/поставок без чтения всех комментариев |

### 5.3. Встроенные поля: что показывать, что скрыть

Показывать по видам: **Title**, **Status**, **Labels**, **Linked pull requests**,
**Parent issue**, **Sub-issues progress**, **Repository**, **Created**, **Updated**,
**Closed** (только завершённые).

Скрыть везде в рабочих видах: **Assignees** (один аккаунт — шум), **Reviewers**
(относится к PR, а PR не item проекта), **Milestone** (не используем, пока координатор
не введёт релизные вехи отдельным решением).

Не создавать пока: отдельную роль/тип/потолок custom-полями (их достаточно видно
в Labels), `Estimate`, `Возраст, дн` вручную, Iteration. Итерации появятся только
если владелец начнёт планировать недельными волнами; возраст и длительность считаются
из дат в ежемесячной сводке/API, а не ручным ежедневным полем.

## 6. Виды: таблица — главная, остальные — режимы внимания

Порядок полей в каждом виде задан ниже. API умеет создавать виды и задавать видимые
поля/фильтр, но **не умеет** надёжно задать сортировку, группировку, колонки board,
срезы и оси roadmap. Эти пять кликов делаются вручную после скрипта — они перечислены
в колонке «ручная доводка», и без неё вид не считается настроенным.

| # | Вид | Layout / фильтр | Видимые поля по порядку | Ручная доводка |
|---|---|---|---|---|
| 01 | **Контроль** (главный, открывается первым) | Table; `is:issue is:open` | Title, Status, Адресат, Приоритет, Labels, Фаза, Размер, Начата, Срок, Updated, Linked pull requests, Parent issue, Sub-issues progress, Repository | Group by: Status. Sort: Срок ↑; внутри одинакового срока — Updated ↑ |
| 02 | **Мне — решения и приёмка** | Table; `is:issue is:open label:"to:owner"` | Title, Status, Приоритет, Labels, Срок, Updated, Linked pull requests, Repository | Sort: Updated ↑ — сверху то, что дольше ждёт владельца |
| 03 | **По адресатам** | Table; `is:issue is:open -label:"status:blocked"` | Title, Status, Адресат, Приоритет, Labels, Фаза, Начата, Срок, Updated, Linked pull requests | Group by: Адресат. Sort: Приоритет, затем Срок ↑ |
| 04 | **Сроки и зависания** | Table; `is:issue is:open` | Title, Status, Адресат, Приоритет, Начата, Срок, Updated, Labels, Linked pull requests | Sort: Срок ↑, затем Updated ↑. Slice by: Status при разборе |
| 05 | **Блокеры и вопросы** | Table; `is:issue is:open label:"status:blocked"` | Title, Status, Адресат, Labels, Начата, Updated, Parent issue, Repository | Sort: Updated ↑. Вопросы отдельно смотреть временным фильтром `label:"type:question"` |
| 06 | **Roadmap** | Roadmap; `is:issue is:open` | Title, Status, Адресат, Приоритет, Начата, Срок, Labels | Start date: Начата; Target date: Срок. Group/slice: Адресат |
| 07 | **Завершено** | Table; `is:issue is:closed label:"status:done"` | Title, Status, Адресат, Приоритет, Labels, Created, Начата, Завершена, Closed, Linked pull requests, Repository | Sort: Завершена ↓. Адресат здесь исторический на момент завершения — после снятия `to:*` поле очищается, поэтому завершённые смотрим не по нему, а по датам |
| 08 | **Доска** | Board; `is:issue is:open` | На карточках: Приоритет, Адресат, Срок, Labels, Linked pull requests | Columns: Status. Horizontal group: Адресат. **Не перетаскивать** до автоматической синхронизации labels |

Почему главный вид — таблица: владелец видит сроки, адресата, фазу и PR одним экраном,
а не таскает карточки. Доска остаётся пространственной картинкой для координатора,
но не главным рабочим инструментом.

Поле `Адресат` в виде 07 очищается при done, как и label `to:*`; поэтому имя поля
в завершённых не трактуется как история. История адресатов восстанавливается по
комментариям и истории labels issue — борд не является архивом маршрутизации.

## 7. Матрица ручной синхронизации (до автоматизации)

Кто меняет статус в issue, тот же в том же действии обновляет проект. Координатор
чинит расхождения label-repair циклом и не ждёт жалобы владельца.

| Событие в issue | Labels | Поля проекта |
|---|---|---|
| Создано | `status:inbox`, `to:coordinator`, роль/тип/размер/приоритет | Status=Inbox, Адресат=Координатор, Приоритет/Размер, Фаза по размеру, Итерации=0 |
| Координатор оформил и назначил | `status:ready`, `to:<конкретный>` или `to:sz-pool` | Status=Ready, Адресат зеркально |
| Ждёт ручного запуска Арена | `status:ready`, `to:owner`, `external`, `launch-ready` | Status=Ready, Адресат=Владелец |
| Claim/старт работы | `status:in-progress`, `to:<конкретный>` | Status=In progress, Адресат, Начата=сегодня, если пусто |
| Переход фазы | `phase:*` | Фаза зеркально |
| CONCLUSION ждёт гейта | `phase:conclusion`, `to:coordinator` | Фаза=Conclusion, Адресат=Координатор |
| Гейт открыт | `phase:action`, `to:<исполнитель>` | Фаза=Action, Адресат зеркально |
| Поставка сдана | `status:review`, `phase:verify`, `to:<конкретный ревьювер>` | Status=Review, Фаза=Verify, Адресат зеркально |
| Ревью вернуло правки | `status:rejected`, `to:<исполнитель>` | Status=Rejected, Адресат, Итерации +1 |
| Approve, нужно слияние | `status:review`, `to:coordinator` | Status=Review, Адресат=Координатор |
| Нужен владелец | `status:review` + `needs-human`, `to:owner` | Status=Review, Адресат=Владелец |
| Принято | `status:done`, снять `to:*` | Status=Done, Завершена=сегодня, Адресат очистить; затем закрыть issue |
| Заблокировано | `status:blocked`, `to:<кто должен ответить>` | Status=Blocked, Адресат зеркально |
| Разблокировано | прежний статус, `to:<исполнитель>` | Status и Адресат восстановить зеркально |
| Отменено | снять `to:*`; issue закрыть с обоснованием | Адресат очистить; карточку архивировать вручную |

## 8. Встроенные автоматизации: что включить, что выключить

Настройки проекта → **Workflows**:

1. **Auto-add to project**: включить для каждого рабочего репозитория, фильтр
   `is:issue`. Уже существующие issues автоматически не подтянутся — их добавляет
   координатор вручную при первом применении.
2. **Item added to project → Status**: поставить `Inbox`. Это значение по умолчанию
   для новых карточек; координатор сразу доводит поля по матрице.
3. **Item closed → Done**: **выключить.** Issue закрывают и при отмене; автоматика
   назвала бы отмену выполненной. Done ставит координатор только после приёмки.
4. **Auto-archive**: после пилота включить фильтр закрытых и давно не обновлявшихся,
   ориентир `is:closed updated:<@today-30d`. До пилота не включать, чтобы вид
   «Завершено» успел показать реальные даты завершения.
5. **Pull request merged → Done**: не настраивать, потому что PR не являются items
   проекта. Завершение видно по связанному issue.

## 9. Применение: два пути

### 9.1. Скриптом (поля и каркас видов)

Нужна авторизация с правом проекта: классический PAT со scope `project` или
`gh auth login --scopes project` на машине владельца/координатора. Секреты в репозиторий
и команды в чат не кладутся.

```bash
# Только посмотреть план и текущие поля (без изменений):
docs/project-apply.sh --owner <логин-владельца> --number <номер-проекта>

# Создать/обновить поля и виды:
docs/project-apply.sh --owner <логин-владельца> --number <номер-проекта> --apply
```

Скрипт идемпотентен: новые поля создаёт, существующие single-select дополняет,
сохраняя ID уже используемых опций; виды создаёт и обновляет layout, фильтр и видимые
поля. Он специально **не удаляет** лишние опции Status и не задаёт сортировку/
группировку/оси roadmap — это ручная доводка из таблицы §6.

Находка прогона 03.11 (casus → правило): вид Roadmap через API создаётся **без
видимых полей** — GitHub отклоняет `visible fields` для ROADMAP_LAYOUT, поэтому
скрипт падает на этом виде. Создавать Roadmap-вид вручную в UI (или мутацией
`createProjectV2View` с `projectId`, без visible fields). Лишние опции Status
(остатки `Todo`/`In Progress` от старых проектов) скрипт не удаляет — удалить
руками в настройках поля Status.

### 9.2. Вручную через UI

1. Открыть выбранный пользовательский проект владельца; название — «Агенты — контроль»
   или существующее, если проект уже ведётся.
2. В Settings связать рабочие репозитории проекта, если проект будет использоваться
   как сквозной.
3. У поля Status заменить опции на §5.1; не удалять старую опцию, пока на ней есть
   карточки, — сначала перекинуть карточки в Inbox.
4. Создать поля §5.2 ровно с этими именами: `Адресат`, `Приоритет`, `Размер`, `Фаза`,
   `Начата`, `Срок`, `Завершена`, `Итерации правок`.
5. Создать виды §6 в указанном порядке; главный «01 Контроль» поставить первым.
6. В каждом виде скрыть Assignees/Reviewers/Milestone и выполнить ручную доводку.
7. Включить workflows §8.
8. В README проекта вставить текст §10.

## 10. Текст для README проекта (вставить как есть)

```markdown
# Агенты — контроль

Правда о задачах — labels и комментарии в issues. Этот проект — вид поверх них:
он показывает, кому сейчас действовать, что просрочено и что ждёт владельца.

- Assignees не используем: все агенты работают через один GitHub-аккаунт.
- Кто должен действовать: label to:* в issue и поле «Адресат» здесь.
- Какая работа нужна: label agent:* в issue.
- Кто поставил задачу: строка «Поставил:» в начале тела issue, не label.
- Карточки по доске не перетаскивать: переход делается labels в issue,
  затем координатор синхронизирует поля проекта.
- Главный вид — «01 Контроль». Владельцу для решений — «02 Мне».
```

## 11. Приёмка настройки (пилот, а не «галочки в Settings»)

Настройка считается применённой только после живого пилота на трёх разных задачах:

1. Обычная задача: создание → ready → claim/старт → поставка → ревью → приёмка.
   На каждом переходе видны правильный Status, Адресат, Фаза и даты.
2. Задача, ждущая владельца: попадает в «02 Мне», после решения владельца уходит
   из него без ручной правки фильтра.
3. Заблокированная задача: видна в «05 Блокеры и вопросы», после ответа возвращается
   исполнителю и в «03 По адресатам».

Отдельно проверить: вид «Контроль» не показывает Assignees; завершённая задача имеет
Created, Начата и Завершена; PR виден из карточки issue и не плодит вторую карточку;
отменённая задача не стала Done от закрытия.

### Что уже сделано в сессии подготовки чертежа

- В репозитории `bestdeejay-design/agents` обновлённым `docs/create-labels.sh`
  фактически созданы/обновлены все 52 workflow labels, включая новые `to:owner`,
  `to:coordinator`, `to:arena`, `to:sz-pool`, `to:sz-1` … `to:sz-5`.
- `docs/project-apply.sh` проверен на синтаксис и на честную ошибку доступа: текущим
  интеграционным токеном он завершаетcя кодом 2 и объясняет, что нужен scope
  `project`, а не делает вид, что настроил проект.
- Сам GitHub Project в этой сессии **не изменён**: полей, видов и workflows в нём
  должна создать авторизация владельца/координатора по §9, затем нужен пилот выше.

## 12. Что специально не делаем сейчас

- Не заводим автоматическую синхронизацию labels → fields до пилота: сначала должно
  стать ясно, какие переходы реально забывают, и только их автоматизировать.
- Не добавляем оценку в часах, ручной возраст и еженедельные итерации ради «взрослого»
  вида: для событийного роя это будет шумом.
- Не делаем отдельный борд на каждый репозиторий и не добавляем PR карточками.
- Не используем Assignees как костыль маршрутизации на общем аккаунте.
