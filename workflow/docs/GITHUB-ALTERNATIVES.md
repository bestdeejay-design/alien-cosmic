# Альтернативы GitHub для мультиагентной шины, кода и оркестрации

> Статус документа: архитектурная проработка и справочник вариантов («на вырост»).
> Действующий транспорт канона — GitHub Issues + ветки + Actions ([BUS.md](../BUS.md), [OPS.md](../OPS.md)).
> Секреты, адреса серверов и токены в репозиторий не кладутся никогда.

---

## 1. Главный архитектурный факт: 85% нашей системы уже не привязано к GitHub

При переходе с GitHub не нужно переписывать ни протокол коллегии саб-агентов, ни навыки, ни проверки. Репозиторий разделён на два независимых слоя:

| Слой | Артефакты репозитория | Зависимость от GitHub | Что нужно при смене платформы |
|---|---|---|---|
| **Ядро мышления, ролей и качества (Git-универсальное)** | `AGENTS.md`, `schema/bus.json`, `agents/*.md`, `skills/*/SKILL.md`, `.claude/`, `.agents/`, `scripts/spawn-pack`, `scripts/install-skills`, `scripts/preflight`, `.githooks/pre-push` | **Нулевая** (нужен только локальный `git` и `python3`) | Работает без изменений на любом Git-сервере и даже на «голом» SSH-репозитории |
| **Транспорт шины и серверные триггеры** | `scripts/wait-signal`, `scripts/agent-runner`, `.github/workflows/{ci,bus-hygiene,guard-main}.yml` | Используют `gh api` (GitHub REST) и раннер GitHub Actions | Меняется только транспортный адаптер (или для `Forgejo`/`Gitea` остаётся почти совместимый YAML воркфлоу) |

Ниже разобраны **четыре практических класса замен GitHub** — от полного локального клона за один вечер до специализированных платформ управления роем ИИ-агентов.

## 2. Четыре класса альтернатив

### Класс А. Своя self-hosted Git-кузница: `Forgejo` / `Gitea` (или `GitLab CE`)

- **Проекты:** `https://codeberg.org/forgejo/forgejo`, `https://github.com/go-gitea/gitea` (лёгкие бинарники на Go, ~200–300 МБ RAM в Docker), либо `GitLab CE` (тяжёлый комбайн от 4–6 ГБ RAM).
- **Почему для роя агентов это сильнее облачного GitHub:**
  1. **Честные отдельные аккаунты каждому узлу бесплатно:** можно завести реальных пользователей `coordinator`, `sz-1`…`sz-5`, `reviewer-a`, `reviewer-b`. Сразу начинает штатно работать поле `Assignees`, история комментариев не требует текстовых подписей для различения авторов, а **сервер механически запрещает автору PR аппрувить собственную поставку**.
  2. **Бесплатная серверная защита веток на приватных репозиториях:** в отличие от GitHub Free (где Rulesets на приватных репо возвращают `HTTP 403` без тарифа Pro), `Forgejo`/`Gitea` бесплатно блокируют прямые пуши в `main` и требуют зелёный статус CI + независимый аппрув на уровне самого Git-сервера.
  3. **Мгновенные вебхуки вместо поллинга и ноль лимитов API:** нет потолка `5000 req/hr` и пауз ожидания по 60–120 секунд — локальный вебхук будит `agent-runner` за `50 мс` после создания задачи или комментария.
  4. **Совместимость CI:** `Forgejo Actions` / `Gitea Actions` исполняют почти тот же синтаксис `.forgejo/workflows/*.yml`, что и наши текущие `.github/workflows/*.yml`.
  5. **Полный суверенитет:** код, история задач и раннеры физически живут на твоём сервере и не зависят от внешних блокировок и сбоев облака.
- **Ограничение:** внешние облачные песочницы с жёстким белым списком исходящей сети (умеющие ходить только на `github.com`) не смогут пушить напрямую в закрытый `Forgejo`. Если такие песочницы используются, GitHub оставляют тонким «внешним почтовым ящиком» для приёма веток `arena/**` с автозеркалированием в `Forgejo`.

### Класс Б. Специализированные Open-Source оркестраторы команд «человек + ИИ-агенты»

Системы 2025–2026 годов, созданные специально под параллельные CLI-агенты (Claude Code, ZCode, Codex, OpenCode), где вместо комментариев в тикетах работает настоящая транзакционная БД и WebSocket:

| Проект | Репозиторий | Ключевая механика | Сильная сторона |
|---|---|---|---|
| **Multica** | `https://github.com/multica-ai/multica` | Self-hosted рабочее пространство, где ИИ-агенты — полноправные участники доски рядом с владельцем | Атомарный захват задач в БД без гонок и `sleep 3`, живой стрим прогресса и подзадач по WebSocket |
| **Paperclip** | `https://github.com/paperclipai/paperclip` | Оркестрация «компании агентов» с ролями, оргструктурой, бюджетами токенов и очередью задач | Жёсткий контроль лимитов расходов на каждого агента/задачу, аудит-лог всех действий и вызовов |
| **Vibe Kanban** | `https://github.com/BloopAI/vibe-kanban` | Локальный/серверный Канбан поверх Git-репозиториев с нативным запуском Claude Code / Codex | Автоматически создаёт `1 карточка = 1 git worktree`, позволяет параллельно крутить пачку задач и удобно смотреть дифф |
| **Agent Orchestrator** | `https://github.com/OrchestratorInc/agent-orchestrator` | Диспетчер флота из 35+ типов CLI-агентов (десктоп + мобильный контроль с телефона) | Автоматически заворачивает упавший CI и замечания ревью-агента обратно владельцу ветки до показа человеку |
| **Symphony (+ Plane / Linear)** | `https://github.com/openai/symphony` + `https://github.com/makeplane/plane` | Разделение человеческого трекера (`Plane` self-hosted или `Linear`) и демона-оркестратора по контракту `WORKFLOW.md` | Лучший визуальный UI трекера для владельца + строгий конечный автомат ретраев, хуков и Proof-of-Work у демона |

- **Когда выбирать:** когда основной рой исполнителей работает в виде CLI-сессий на твоих машинах/серверах и хочется заменить текстовые маркеры шины на нативные события, транзакции и живой дашборд с телефона/браузера.

### Класс В. Git-native трекер задач внутри самого репозитория (`Beads`)

- **Проект:** `https://github.com/gastownhall/beads`.
- **Как устроено:** задачи, статусы, приоритеты и строгий граф зависимостей (`blocked by`) хранятся как версионируемые строки `.beads/*.jsonl` прямо в Git с локальным быстрым индексом на `SQLite`.
- **Плюсы:**
  - вообще не требует веб-сервера — достаточно любого SSH-хоста с `git init --bare`;
  - агент читает очередь и дерево блокеров локально за `1–2 мс` с нулевым сетевым трафиком;
  - работает полностью оффлайн; состояние доски воспроизводится на любой точке истории Git.
- **Минусы:**
  - нет привычного веб-канбана «из коробки» для владельца (нужна сторонняя TUI/веб-обёртка);
  - при одновременном пуше десятка агентов в одну ветку задач возможны git-конфликты индекса — лучше выносить журнал задач в отдельный Git-реф или проводить запись через одного координатора.

### Класс Г. Свой сверхлёгкий микро-брокер шины поверх нашего `schema/bus.json`

Поскольку вся наша модель данных (52 метки, 21 маркер, тиры `size:S / size:M / size:L`, роли сабов и лимиты аренды) **уже формализована в `schema/bus.json`**, при желании полный уход от ограничений GitHub Issues пишется за 300–400 строк на `Python (FastAPI + SQLite/PostgreSQL)` в связке с любым Git (`Forgejo` или голый SSH Git):

1. **Настоящий атомарный `CLAIM` одной транзакцией:**
   `UPDATE tasks SET assignee = :node, lease_until = :ts WHERE id = :id AND current_state = 'ready'` — `0` гонок, `0` ожиданий `sleep 3`, автоматический возврат просроченной аренды по `lease_until`.
2. **Мгновенная доставка сигналов (`SSE` / `WebSocket` / `LISTEN-NOTIFY`):**
   `wait-signal` вместо поллинга раз в 90 секунд держит лёгкое соединение и просыпается в ту же долю секунды, когда пришёл `GATE OPEN`, `VERDICT` или завершился `preflight`.
3. **Стопроцентное сохранение канона:** все названия меток, маркеров, коллегия 4 сабов (`agents/`), 11 навыков (`skills/`) и `spawn-pack` остаются один-в-один прежними.

## 3. Сравнительная таблица вариантов

| Критерий | GitHub (сейчас) | `Forgejo` / `Gitea` (self-hosted) | `Multica` / `Vibe Kanban` / `Paperclip` | `Beads` (Git-native) | `Forgejo` + микро-брокер `bus.json` |
|---|---|---|---|---|---|
| **Отдельные логины каждому агенту** | Платно / неудобно (живём на одном аккаунте + `to:*`) | **Да, бесплатно** (любое число ботов) | **Да, из коробки** (профили агентов) | По подписи Git-автора | **Да, бесплатно** |
| **Серверный запрет пуша в `main` и само-ревью PR** | На приватном репо нужен платный Pro (`403`) | **Да, бесплатно на сервере** | Зависит от Git-хостинга | Только хуки `pre-receive` | **Да, бесплатно на сервере** |
| **Атомарность `CLAIM` без гонок** | Квази-атомарно (`sleep 3` + арбитраж) | Через API / вебхук | **Транзакция в БД** | Через коммит/лок | **Транзакция в БД** |
| **Задержка сигнала между агентами** | `15–90 с` (поллинг с `ETag`) | **`< 100 мс`** (локальный вебхук) | **`< 100 мс`** (WebSocket) | При `git fetch` | **`< 50 мс`** (SSE/WS) |
| **Удобная доска для владельца** | GitHub Projects | Встроенный Канбан + PR UI | **Заточенный под агентов UI** | Нужна внешняя обёртка | Канбан `Forgejo` или мини-панель |
| **Независимость от внешних облаков** | Нет (облако GitHub) | **Полная (свой сервер)** | **Полная (self-hosted)** | **Полная (даже оффлайн)** | **Полная (свой сервер)** |
| **Стоимость переезда нашего репо** | `0` (уже работает) | **Низкая (1 вечер)** | Средняя (новая доска задач) | Средняя (CLI вместо Issues) | Низкая/средняя (1–2 вечера) |

## 4. Практическая рекомендация: как пробовать без ломки текущей работы

1. **Этап 1 (сейчас — боевая проверка методологии на готовом проекте):**
   Не тратить время на переезд инфраструктуры до первого полевого аудита. Обкатать коллегию 4 саб-агентов, 11 скиллов, `install-skills`, `spawn-pack --preset fullstack-audit` и Волну 2 со сменой ролей прямо на текущем контуре. Это проверит главное — качество инженерного выхода.
2. **Этап 2 (если захочется свою автономную площадку без лимитов GitHub):**
   Самый прагматичный первый шаг — поднять **`Forgejo` + `Forgejo Runner`** в двух контейнерах Docker:
   - сразу появляются отдельные бесплатные аккаунты для `coordinator`, `executor-a`, `executor-b` и серверная блокировка `main` + запрет само-аппрува PR;
   - все карточки `agents/`, навыки `skills/`, `.claude/`, `.agents/`, `spawn-pack` и `preflight` работают там без единой правки;
   - в `wait-signal` и `agent-runner` URL-вызов `gh api repos/...` заменяется на тонкую функцию-обёртку к совместимому REST API `/api/v1/repos/...` (эндпоинты issues, labels и comments у `Gitea`/`Forgejo` повторяют структуру GitHub REST API почти 1-в-1).
3. **Этап 3 (когда рой вырастет до 5–10 постоянно кипящих локальных воркеров):**
   Подключить поверх `Forgejo`-репозиториев визуальный диспетчер worktree вроде **`Vibe Kanban` / `Agent Orchestrator` / `Multica`** — тогда владелец управляет карточками и видит живые стримы саб-агентов в реальном времени, а внутри каждого воркера по-прежнему работают наши строгие `agents/`, `skills/`, `REVIEWER_KICK` и `scripts/preflight`.
