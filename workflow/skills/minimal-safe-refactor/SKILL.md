# Навык: Безопасный точечный рефакторинг (`minimal-safe-refactor`)

Используй этот навык на задачах `type:debt` и при расчистке сложного кода после аудита.

## Три запрета против поломки рабочего кода

1. **Запрет рефакторинга без страховочной сетки:** если поведение меняемого участка ещё не покрыто тестами, **сначала** напиши характеризационные тесты на текущие входы/выходы и убедись, что они зелёные.
2. **Не смешивай смену структуры и смену бизнес-логики в одну кашу:** рефакторинг сохраняет внешнее поведение побайтово/поконтрактно; новая функциональность идёт отдельным явным шагом или отдельной задачей.
3. **Никакого расползания за радиус:** не переименовывай файлы, публичные функции, CLI-флаги, поля JSON и маршруты API «ради красоты», если это не входит в бриф и ломает внешних вызывающих.

## Порядок чистой работы

1. Зафиксируй все точки вызова меняемой функции/модуля (`grep` / `AUDIT_PACK`).
2. Прогони базовые и новые характеризационные тесты ДО первой структурной правки.
3. Делай малые обратимые шаги: убирай реальное дублирование (от 3 повторов), но не плоди пустые абстракции-прокладки ради одного вызова.
4. Полностью удаляй заменённый мёртвый код — не оставляй закомментированные куски «на память» (история уже есть в `git`).
5. Прогони `python3 scripts/preflight` и весь тестовый набор проекта, сверив дифф на отсутствие случайных побочных изменений.
