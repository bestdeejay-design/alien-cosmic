# AUDIT_PACK — <client> (для агента)

> Выход роли `auditor` (read-only). Основа для SPEC_PACK и REVIEWER_KICK.

## 1. Фактическая карта

- Полигон: staging (`app-staging`, `b2b-staging`, `api-staging`), моки банка и касс; прод — пассивно.

- Цели: `app.example.com` (покупатель), `b2b.example.com` (МСП), `example.com` (публичный, пассивный).
- Роли: покупатель, точка МСП, представитель, амбассадор, админ/оператор (TBD: есть ли).
- Потоки: OTP/passkey-вход → каталог → заказ → оплата (карта/СБП/баллы) → начисление баллов →
  вывод СБП → выплаты сети (<split>) → чеки 54-ФЗ.
- Деньги: боевые платежи <bank>; баллы 1:1 = деньги; PAY-баланс.

## 2. Неприкосновенные инварианты

- Баллы не создаются из воздуха; трата/вывод не дублируются; баланс не уходит в минус без контроля.
- Цена/тариф/сплит не берутся с клиента; статус платежа подтверждает банк/сервер.
- Чужой профиль/заказ/точка/фото недоступны по подмене ID.
- OTP нельзя перебрать; сессия отзывается.
- Прод-ledger не загрязняется тестовыми операциями; staging не пишет в прод-данные.
- Моки на staging включены на всех платёжных флоу (оплата, возврат, чек, вывод баллов).

## 3. Точки слома

- Race/повтор/откат в баллах и платежах; частичная запись «списано, но не начислено».
- Вебхуки банка: подпись, replay, идемпотентность.
- Хранилище фото на b2b-домене: прямые ссылки, перечисляемость.
- QR-онбординг и тариф <tariff-1>: обход лимитов.
- OTP: лимиты, enumeration, хранение кода.

## 5. Вердикт по границам

Радиуса Grey Box достаточно для пилота **при условии** выдачи тестовых аккаунтов покупателя ×2
и точки МСП. Без них — только Black Box с честными ограничениями.
Расширение до White Box — отдельным scope при доступе к коду.
