# Процесс, scope, правила взаимодействия (RoE) и безопасность

> Этот файл — обязательный для любого режима. Без scope и разрешения работа не начинается.
> Шаблон для заполнения: [templates/scope-authorization-roe.md](templates/scope-authorization-roe.md).

## 1. Жизненный цикл (детально)

### Этап 0. Intake (1–2 дня)

- Заполняется [templates/intake-questionnaire.md](templates/intake-questionnaire.md).
- Результат: понимание цели, активов, сроков, ограничений, бюджета.
- Гейт: клиент ответил на обязательные вопросы; нет ответов — нет scope.

### Этап 1. Scoping (1 день)

- Фиксируются: цели (домены, приложения, API, репозитории), режим (Black/Grey/White),
  домен (игра/финтех/оба), что **вне** scope, окно тестирования, стоп-условия, контакты.
- Результат: подписанный scope. Устная договорённость не считается разрешением.
- Гейт: scope подписан обеими сторонами.

### Этап 2. Authorization + RoE + NDA

- Письменное разрешение владельца системы, RoE, NDA/обработка данных.
- Назначаются: технический контакт клиента, контакт проверяющего, канал экстренной связи.
- Гейт: разрешение получено. Без него — стоп, даже если «клиент просил быстрее».

### Этап 3. Recon / Threat model / Карта поверхности (1–3 дня)

- Карта: цели, роли, потоки (регистрация, оплата, валюта, торговля), активы, границы доверия.
- Для Grey/White: threat model с приоритетами (что проверяем глубже).
- Гейт: карта согласована с клиентом (нет сюрпризов «а это тоже в scope?»).

### Этап 4. Testing (5–15 дней в зависимости от scope)

- Проверки по чек-листу режима + домена. Каждая находка — по [templates/finding.md](templates/finding.md).
- Доказательства собираются по стандарту §4 ниже.
- Гейт: чек-лист пройден или «не проверено» зафиксировано с причиной.

### Этап 5. Reporting (2–3 дня)

- Отчёт по [templates/final-report.md](templates/final-report.md) + [templates/executive-summary.md](templates/executive-summary.md).
- Независимое ревью находок (не автором). См. [06-ai-agent-protocol.md](06-ai-agent-protocol.md).
- Гейт: ревью пройдено, нет находок без доказательств.

### Этап 6. Remediation (сроки клиента)

- Клиент исправляет по приоритету. Проверяющий консультирует по вопросам, но не вносит
  изменения в прод клиента без отдельного договора.
- Гейт: клиент сообщил, что исправления готовы, с указанием версий/коммитов.

### Этап 7. Retest (3–5 дней)

- Перепроверка по списку находок. Результат — [templates/retest-certificate.md](templates/retest-certificate.md).
- Гейт: каждая находка имеет статус: исправлено / частично / не исправлено / не воспроизводится.

### Этап 8. Handover и рекомендации

- Передача материалов, рекомендации: мониторинг, обновления, повторный аудит, подписка.
- Гейт: материалы переданы, NDA/хранение данных согласованы.

## 2. Scope: обязательные поля

- **Цели:** домены, IP (если есть), приложения, API, репозитории, окружения (staging/prod).
- **Режим и домен:** Black/Grey/White; игра/финтех.
- **Вне scope:** явно перечислено (например, «третьи лица, DDoS, social engineering, физический доступ»).
- **Окно:** даты и часы, допустимая нагрузка, запрещённые действия.
- **Данные:** тестовые данные; запрет на реальные PII/платёжные данные без отдельного разрешения.
- **Контакты:** технический контакт, экстренный канал, кто может остановить тестирование.
- **Стоп-условия:** см. §3.
- **Результат:** отчёт, план, retest; сроки и приёмка — см. [08-service-packages.md](08-service-packages.md).

## 3. Запреты и стоп-условия (RoE)

**Запрещено всегда (без отдельного письменного разрешения и участия человека):**

- Атаки на системы вне scope, включая третьих лиц (провайдеры, партнёры, другие клиенты).
- DDoS, деградация сервиса, удаление/порча данных, шифрование/вымогательство.
- Эксфильтрация данных сверх минимального доказательства (PoC — скриншот/хеш/фрагмент, а не дамп БД).
- Социальная инженерия, фишинг сотрудников, физический доступ.
- Использование найденных секретов/ключей за пределами scope и окна.
- Публикация уязвимостей до согласованного раскрытия (coordinated disclosure).

**Стоп и эскалация немедленно, если:**

- Обнаружен доступ к реальным персональным/платёжным данным сверх scope.
- Сервис деградирует, есть риск для пользователей/денег.
- Обнаружен активный инцидент/вторжение (не твоё тестирование).
- Клиент отозвал разрешение или изменил scope.

При стопе: прекратить действия, сохранить доказательства, уведомить контакт клиента,
зафиксировать в отчёте как «остановлено по стоп-условию».

## 4. Стандарт доказательств

Каждая находка обязана иметь:

1. **Идентификаторы:** ID, заголовок, режим, домен, дата, версия/коммит, окружение.
2. **Шаги воспроизведения:** роль, аккаунт (тестовый), запросы, порядок действий.
3. **Фактический результат:** что произошло (ответ, скриншот, лог, хеш).
4. **Ожидаемый результат:** что должно было произойти.
5. **Влияние:** что может сделать злоумышленник (деньги, валюта, данные, репутация).
6. **Оценка риска:** CVSS + бизнес-влияние (см. [07-deliverables.md](07-deliverables.md)).
7. **Рекомендация:** как чинить (конкретно, с примером где уместно), приоритет.

Нет шагов воспроизведения — нет находки. «Возможно, есть уязвимость» — это гипотеза
в раздел «не проверено / требует проверки», а не находка.

## 5. Работа с секретами и данными

- Секреты клиента (ключи, пароли, токены) не кладутся в отчёты открытым текстом:
  только prefix/хеш/маска и место хранения.
- Реальные PII/платёжные данные не собираются. Если случайно получены — удалить,
  зафиксировать, уведомить клиента.
- Материалы проверки хранятся по NDA, доступ — только у участников, срок хранения согласован.
- Агент не должен выводить секреты в логи, коммиты, issues и письма (правило репозитория, `PROTOCOL.md` §2).

## 6. Coordinated disclosure

Уязвимости сообщаются клиенту конфиденциально до исправления. Публикация, CVE, bug bounty —
только по согласованию с клиентом и после retest. Сроки раскрытия фиксируются в RoE.
