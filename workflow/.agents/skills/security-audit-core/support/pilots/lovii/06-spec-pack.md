# SPEC_PACK — <client>: план проверок

> Выход роли `researcher`. План по чек-листам режима + домена. Агент исполняет по порядку,
> каждую находку — по [finding.md](../../templates/finding.md).

## Фаза 0 — проверка среды (до всего остального)

0. Staging: не индексируется, нет реальных ПДн, моки включены на всех платёжных флоу
   (`/pay`, возвраты, чеки, вывод баллов). Если мок где-то выключен — стоп, вопрос владельцу.
   Отдельно: пересечение данных staging ↔ прод (фото с `b2b.example.com`, общие ID, общие ключи).

## Фаза 1 — Black Box по staging (без доступов)

По [black-box.md](../../checklists/black-box.md):

1. Recon: DNS/TLS, заголовки, CORS, технологии, публичные утечки, карта эндпоинтов.
2. OTP/passkey снаружи: enumeration, лимиты, перебор (безопасными объёмами).
3. IDOR без аккаунта и с публичным доступом; прямые ссылки на `/storage/merchants/...`.
4. Ввод: XSS/SQLi/SSRF/path traversal/file upload — безопасными PoC.
5. Misconfig: ошибки/стектрейсы, debug, rate limiting.
6. Бизнес-логика снаружи: подмена цены/количества в публичных флоу, повтор купонов/акций.

## Фаза 2 — Grey Box по staging (с тестовыми доступами)

По [grey-box.md](../../checklists/grey-box.md) + [fintech.md](../../checklists/fintech.md):

7. Роли: покупатель ×2 (IDOR профиль/заказ/баланс), точка МСП (чужая точка, чужой кабинет/выплаты).
   IDOR по `/stores/1…15` и по ULID фото из хранилища.
8. Баллы: race, повтор, откат, отрицательные/переполненные суммы, подмена цены с клиента.
9. Платежи: receipt/вебхук (подпись, replay, идемпотентность), двойная трата, возвраты.
10. PAY/вывод СБП: лимиты, идемпотентность, статусы.
11. Тарифы/сплит: обход <tariff-1> <rate-1> (<limit-1>), подмена выручки, сговор сети.
12. QR-онбординг: подделка/повтор, захват чужого кабинета.
13. Сессии/токены: отзыв, ротация, хранение; админка/саппорт (если есть).
14. Файлы: фото точек (права, перечисляемость, типы, хранение), загрузки.
15. PII/секреты: логи, клиентский бандл, URL, экспорт.

## Фаза 3 — White Box (только отдельным scope, код и схемы)

По [white-box.md](../../checklists/white-box.md): код, схемы/ledger, секреты, зависимости,
криптография, логи/мониторинг, тесты безопасности. Корневые причины.

## Приоритеты исполнения

Фаза 0 — обязательно первой. T1–T4 из [04-threat-model.md](04-threat-model.md) — следующими. T5–T7 — в том же пилоте.
Всё, что не удалось проверить — в список «не проверено» с причиной.

## Критерии готовности

- Чек-листы пройдены или «не проверено» зафиксировано.
- Каждая находка: PoC на тестовых счетах, CVSS + P0–P3, рекомендация.
- Отчёт + план + retest-план готовы к независимому ревью.
