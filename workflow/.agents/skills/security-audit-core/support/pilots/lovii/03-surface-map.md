# Карта поверхности <client> (пассивная разведка)

> Метод: чтение публичных страниц без активных атак. Дата: 2026-11-11.
> Активные проверки — только после подписи scope и на staging. Ниже — наблюдения, **не находки**.

## Окружения

| Окружение | Домены | Что видно |
|---|---|---|
| Staging (полигон) | `staging.example.com`, `b2b-staging.example.com`, `api-staging.example.com` | Полный каталог (15 точек), магазины `/stores/1…15`, `/popular`, вход b2b OTP/passkey; моки банка и касс |
| Прод | `app.example.com`, `b2b.example.com`, `example.com` | Каталог, тестовая точка, вход b2b; боевые платежи |
| Демо | `demo.example.com` | Витрина, кабинет точки, тестовая оплата |

## Наблюдаемые активы

- `staging.example.com/` — витрина: 15 точек, «Популярные заведения», «Возле вас», поиск, баллы 1:1.
  Карточки: `/stores/1` … `/stores/15` (**последовательные ID**), `/popular`.
- `b2b-staging.example.com/panel/login` — вход по телефону + код, passkey, RU/EN.
- `api-staging.example.com/images/demo/logos/*.jpg` — демо-изображения, отдаются API-доменом.
- `b2b.example.com/storage/merchants/<ULID>.jpg` — фото точек. **Staging ссылается на прод-домен b2b**
  для части фото (наблюдалось: «Тестовая пекарня "Пышка"»).
- Публичные страницы example.com: роли, тарифы, схема денег, ссылки на приложение и демо.

## Наблюдаемые потоки (гипотезы, проверяются в Grey Box)

1. Вход: телефон + OTP (app и b2b), passkey (b2b). Регистрация и её условия — TBD.
2. Каталог: поиск, список магазинов, карточка, расстояние, минимальный заказ.
3. Заказ/оплата: карта/СБП/баллы, PAY-карта, баланс (на staging — моки банка и касс).
4. Баллы: начисление 1:1, трата у всех точек, вывод через СБП (мок на staging).
5. Точка МСП: онбординг, заполнение данных, фото, товары/услуги, тариф.
6. Сеть: представитель/амбассадор, сплит <split>.
7. Чеки: ККТ платформы по 54-ФЗ (на staging — мок).

## Первые гипотезы (НЕ находки, требуют PoC)

- **Хранилище фото:** прямые ссылки `/storage/merchants/<ULID>.jpg`; ULID не перебирается,
  но проверяются ли права на чтение, отдача приватных фото, перечисляемость каталога.
- **Смешение окружений:** staging-витрина грузит фото с **прод**-домена `b2b.example.com`
  и с `api-staging` — проверить, нет ли общих данных/ключей между staging и прод.
- **Последовательные ID магазинов** (`/stores/1…15`) на staging — удобная мишень для IDOR:
  проверить, отдаёт ли API скрытые/неопубликованные/чужие точки по прямому ID.
- **OTP-вход:** лимиты, перебор, enumeration телефона, срок жизни кода, повторное использование.
- **Баллы/PAY:** race, повтор, откат, отрицательные суммы, подмена цены с клиента.
- **IDOR:** чужой профиль/заказ/баланс, чужая точка в b2b.
- **Тариф <tariff-1> <rate-1>:** обход лимита 30 000 ₽ через мультиаккаунты/разбиение заказов.
- **Индексация staging:** стенд не должен попадать в поисковики (robots, мета, авторизация).

## Чего в карте нет (нужны ответы)

API-документация, админка/саппорт, staging-доступы, коды ответов и заголовки (нужны реальные HTTP-запросы),
схема БД, где хранятся секреты, режим моков (какие именно провайдеры замоканы).
