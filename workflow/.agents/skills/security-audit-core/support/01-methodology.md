# Методология: Black Box / Grey Box / White Box

> Ядро комплекта. Агент выбирает режим **по scope и разрешениям**, а не «что удобнее».
> Режим фиксируется в [templates/scope-authorization-roe.md](templates/scope-authorization-roe.md)
> до начала тестирования. Смена режима — только изменением scope.

## 1. Сравнение в одной таблице

| Ось | Black Box | Grey Box | White Box |
|---|---|---|---|
| **Знает проверяющий** | Только публичное: домены, приложения, открытые API | Часть: тестовые аккаунты, API-документация, архитектура, staging, без полного кода | Всё: исходный код, схемы БД, конфиги, IaC, логи, CI/CD |
| **Аналогия** | Злоумышленник снаружи | Злоумышленник с утечкой / недовольный инсайдер | Аудитор внутри |
| **Что находит лучше всего** | Внешние дыры: раскрытие информации, слабую аутентификацию, misconfig, IDOR через публичные API | Логические баги: права, потоки, race, идемпотентность, экономика, платежи | Скрытые баги: жёсткие секреты, небезопасные паттерны, криптография, зависимости, архитектурные flaws |
| **Что НЕ находит** | Баги, видимые только в коде; внутренние сервисы; логику за аутентификацией без аккаунтов | То, что скрыто в коде/конфигах, к которым нет доступа | Реалистичность внешней эксплуатации (код «плохой», но снаружи может быть недостижим) |
| **Ложные срабатывания** | Выше: вывод по поведению без кода | Средние | Ниже, но риск «теоретических» находок без PoC снаружи |
| **Время/цена** | Ниже при малом scope | Средняя | Выше: объём кода и архитектуры |
| **Требуется от клиента** | Список целей, окно, контакт, тестовые данные если есть | + тестовые аккаунты/роли, документация, доступ к staging, схема потоков | + доступ к репо (read-only), схемам, конфигам (без секретов в открытом виде), логам |
| **Типичный результат** | «Снаружи видно вот это» | «Вот сценарии злоупотребления и где они ломаются» | «Вот корневые причины в коде/архитектуре и как чинить системно» |

## 2. Что входит в каждый режим (обязательно)

### Black Box — обязательный контур

1. **Recon (разведка):** публичные домены/поддомены, DNS, TLS, открытые порты/сервисы,
   публичные репозитории/утечки (только чтение публичного), технологии по заголовкам/баннерам.
2. **Карта поверхности:** список целей, эндпоинтов, форм, загрузок, публичных API.
3. **Аутентификация снаружи:** регистрация/вход/восстановление, перебор, enumeration,
   слабые политики паролей, отсутствие MFA там, где она должна быть.
4. **Авторизация через публичные API:** IDOR/доступ к чужим объектам без аккаунта и с минимальным аккаунтом, если он публичный.
5. **Ввод и инъекции:** XSS, SQLi, SSRF, path traversal, file upload — в рамках scope и без деструкции.
6. **Конфигурация:** security headers, CORS, TLS, раскрытие ошибок/стектрейсов, directory listing, debug-режимы.
7. **Rate limiting / brute force / enumeration** — безопасными объёмами, без DoS.
8. **Бизнес-логика снаружи:** обход оплаты/доната, подмена цены/количества, повторное использование промокодов/купонов, если это публичный флоу.

**Не входит по умолчанию:** чтение кода, внутренние сети, социальная инженерия, DDoS, физический доступ.

### Grey Box — Black Box + частичное знание

Всё из Black Box, плюс:

1. **Тестовые аккаунты всех ролей** (игрок/клиент, модератор, админ, мерчант) — проверка AuthZ между ролями.
2. **API-документация (OpenAPI/Postman), схема потоков** (регистрация, оплата, выдача валюты, торговля).
3. **Staging-окружение**, максимально близкое к проду, но с тестовыми данными.
4. **Логика и состояние:** race conditions, идемпотентность, повторные запросы, откаты, частичные записи.
5. **Экономика/платежи:** дюп, двойная трата, подмена суммы, вебхуки (подпись, повтор, порядок), возвраты.
6. **Сессии и токены:** время жизни, отзыв, привязка, хранение на клиенте.
7. **Файлы и загрузки:** типы, размеры, хранение, доступ по прямым ссылкам, сканирование на вредоносное содержимое (в рамках scope).
8. **Чек-листы домена:** [checklists/gaming.md](checklists/gaming.md) или [checklists/fintech.md](checklists/fintech.md).

**Не входит по умолчанию:** полный исходный код, продакшн-БД, реальные персональные данные, деструктивные тесты.

### White Box — Grey Box + полный доступ

Всё из Grey Box, плюс:

1. **Исходный код** (read-only): клиент, сервер, API, воркеры, миграции, IaC, CI/CD.
2. **Схемы БД и модели данных:** индексы, уникальность, транзакции, ledger, инварианты.
3. **Конфиги и секреты:** где хранятся, кто читает, ротация, попадание в логи/репозитории/клиентский бандл.
4. **Зависимости и supply chain:** уязвимые версии, lock-файлы, provenance, секреты в CI.
5. **Криптография и токены:** алгоритмы, хранение паролей (Argon2id/bcrypt), JWT, подписи вебхуков.
6. **Архитектура и threat model:** границы доверия, server-authoritative vs client-authoritative, tenant isolation.
7. **Логи и мониторинг:** что логируется, что не должно логироваться (секреты, PII), алерты, audit trail.
8. **Тесты безопасности:** есть ли тесты на права, идемпотентность, инварианты денег/валюты.

**Не входит по умолчанию:** продакшн-данные, право вносить изменения в код (аудит read-only),
эксплуатация за пределами PoC, юридические заключения.

## 3. Дерево выбора режима

```text
Есть ли письменное разрешение и scope?
  Нет → СТОП. Сначала [templates/scope-authorization-roe.md](templates/scope-authorization-roe.md).
  Да ↓

Что нужно доказать клиенту?
  «Снаружи ничего не торчит» / быстрый внешний взгляд → Black Box
  «Покажите сценарии злоупотребления деньгами/валютой/правами» → Grey Box
  «Нужен корневой разбор кода перед инвестициями/партнёром/инцидентом» → White Box

Что готов дать клиент?
  Только URL → Black Box (и честно зафиксируй ограничения)
  Тестовые аккаунты + документацию + staging → Grey Box
  Доступ к коду и архитектуре → White Box

Есть ли деньги/персональные данные в scope?
  Да → минимум Grey Box; для финтеха с реальными платежами — White Box для ledger/платежного контура
  Нет, только публичная поверхность → Black Box допустим как первый шаг
```

**Комбинированный подход (рекомендуемый для продажи):**
Black → Grey → White по этапам. Каждый этап — отдельный scope/отчёт, клиент видит прогресс
и может остановиться. Это снижает риск «продали White, а внутри оказалось, что и Black не закрыт».

## 4. Ограничения, которые честно фиксируй в отчёте

- **Black Box не доказывает отсутствие внутренних дыр.** Формулировка: «внешних уязвимостей
  не выявлено в рамках scope и объёма» — не «система безопасна».
- **Grey Box зависит от полноты выданных доступов.** Если не дали роль/эндпоинт — зафиксируй как «не проверено».
- **White Box находит корневые причины, но не гарантирует отсутствие 0-day.** Отчёт — снимок на дату/коммит.
- **Ни один режим не заменяет** мониторинг, обновления, резервное копирование и incident response.
  Это рекомендации в отчёте, а не «гарантия».

## 5. Как агент фиксирует режим

В каждом пакете агента ([06-ai-agent-protocol.md](06-ai-agent-protocol.md)) обязательно:
режим, список целей, список «не проверено» (что не вошло и почему), версия/коммит/дата.
Находка без привязки к режиму и scope не принимается ревьюером.
