# Навык: Шина GitHub и сдача поставки (`bus-delivery`)

Используй этот навык при захвате задачи из очереди, публикации сигналов и оформлении поставки.

## 1. Захват задачи и ожидание сигналов

- Свободную задачу из `status:ready` с `to:sz-pool` бери **только скриптом**:
  `scripts/wait-signal --issue <N> --claim "<Роль / сессия>" --claim-as sz-1` (подставь свой номер `sz-1`..`sz-5`).
- Проиграл арбитраж (`BUSY`/`LOST`, код `3`) — не трогай метки, вернись к сканированию очереди.
- Ожидание чужого сигнала или CI: `scripts/wait-signal --issue <N> --since <ISO> [--sha <commit>]` (ETag внутри, квоту API не жжёт). Перед ожиданием сверь `scripts/wait-signal --version`.

## 2. Поток сдачи по размеру задачи

- **`size:S` (Fast-Track):** не жди промежуточного `GATE OPEN`. За один проход запиши компактный `🎯 CONCLUSION #<N>`, внеси правку в ветке, пройди `python3 scripts/preflight`, запушь свою ветку и сдай письмо поставки на независимое ревью.
- **`size:M` / `size:L`:** сначала сдай `AUDIT` / `RESEARCH` / `🎯 CONCLUSION #<N>` и дождись гейта координатора (`phase:action` + `✅ GATE OPEN #<N>`), затем выполняй Волна 1 → Коллегия → Волна 2 со сменой ролей.

## 3. Оформление поставки (комментарий или `docs/MAIL.md`)

- Первая строка всегда строгий маркер: `📬 DELIVERED #<N> — <суть одной фразой>`, вторая строка — подпись `— <Роль> · <сессия>`.
- Узел с записью в issues публикует письмо комментарием; узел без записи в issues кладёт его в `docs/MAIL.md` своей ветки (GitHub Action `bus-hygiene.yml` или координатор ретранслирует его в issue с точным `HEAD SHA`).
- В описании PR и письмах пиши `Refs #<N>` / `Связанный issue: #<N>` — **никогда не пиши ключевые слова автозакрытия** до финальной приёмки.
