# Проектный профиль адаптации канона (`PROJECT.md`)

> Человекочитаемая половина проектного оверлея (ADR-0003, ADOPTION §5). Машинная
> половина — `project.json` рядом с этим файлом; при расхождении источник правды —
> `project.json`, этот файл синхронизирован с ним. Конкретные имена узлов, меток,
> репозиториев и доменов здесь намеренно не дублируются литералами (Гейт Чистоты,
> ADR-0003) — они читаются из `project.json` и корневого `AGENTS.md` проекта.

## 1. Паспорт и раскладка

- **Проект / репозиторий:** см. `project.json` → `project.repo` и `project.slug`
- **Раскладка канона:** подкаталог `workflow/` (режим B, ADOPTION §5)
- **Конфигурация оверлея:** `workflow/project.json` (создан из `project.example.json`)
- **Версия комплекта:** `workflow/CANON_VERSION.md` (апстрим, дата копии, расхождения)

## 2. Состав узлов и режимы доступа (проектный roster `project.json`)

> Роли `owner` и `coordinator` — зарезервированные id ядра
> (`CORE_RESERVED_IDS` в `scripts/project_overlay.py`), в проектный roster не входят.
> Полномочия ролей и жёсткие правила контура — корневой `AGENTS.md` проекта (§1).

| Узел (`id`) | Метка адресации | Режим доступа | Кто запускает |
|---|---|---|---|
| `arena` (см. `project.json`) | см. `project.json` | изолированный контур (`isolated_branch`): только пуш своей ветки + письмо-файл в design/, записи в issues нет | владелец словом → координатор оформляет |
| пул исполнителей и их слоты — фактические `id` см. `roster` в `project.json` | см. `project.json` | `direct_gh` (issues + маркеры шины, claim через `wait-signal --claim` / `agent-runner`) | координатор (spawn-pack) |

- **Подпись узла** обязательна в каждом сообщении («— Роль · сессия»): все работают
  под одним GitHub-аккаунтом, личность живёт в подписи.
- **Задача внешнему изолированному исполнителю** — только текстом через владельца
  / брифом координатора под репо его сессии; поставка = ветка + письмо-файл.

## 3. Проектные постоянные

- **Регресс:** канонический список — §4 корневого `AGENTS.md` (гейт, smoke, 17 симов,
  audit_move, minimap, u/v verify с локальным сервером); для полигона `r/` —
  дополнительно `check_r`. Обязателен перед каждым пушем.
- **Стемп версий:** `?v=` единый по всем импортам `r/` (js + boot + index + lab),
  менять одним движением по всем файлам.
- **Изоляция сезонов:** S1 заморожен (§5 AGENTS.md); полигон — в изолированных
  каталогах; версия игры — только координатором в main.
- **Борд проекта:** GitHub Projects V2 «задачи» — единственный источник правды задач
  (§10 AGENTS.md); отображение борд ↔ labels шины — таблица ниже и PROJECTS-BLUEPRINT §7.
- **Этапный репозиторий и песочницы:** отдельный репо этапа + репо-полигон воркфлоу —
  адреса см. в корневом `AGENTS.md` и памяти координатора (вне канона по чистоте).

## 4. Соответствие статусов (борд ↔ шина)

| Борд | Labels шины |
|---|---|
| Бэклог | — (нет label) |
| Ждёт / Блокирована | `status:blocked` |
| К работе | `status:ready` |
| В работе | `status:in-progress` |
| На ревью | `status:review` |
| Правки | `status:review` + маркер 🔁 REJECTED в issue |
| На приёмку владельца | `status:review` + `needs-human` (issue открыт до приёмки) |
| Готово | `status:done`, issue закрыт координатором (🏁 DONE) |

## 5. Уровни окружений (отображение COORDINATOR_RULES §8)

| Уровень канона | У нас | Кто двигает |
|---|---|---|
| test | локальные стенды + ветка `test` → Pages `/test/` | исполнитель (self-merge разрешён) |
| staging | игровой домен (rsync на прод-сервер) после approve ревьювера и полного регресса | координатор |
| production | Pages deploy-prod **И** rsync prod-сервера — оба разом, после приёмки владельца | координатор + приёмка владельца |

Инвариант SHA: в production уезжает тот же коммит, что прошёл staging/приёмку.
HOTFIX — только координатором (§7). Правила уровней соблюдаются процессно;
rulesets/environments (уровни 2–3 лестницы принуждения §12) НЕ установлены —
честный статус: «гейты на дисциплине»; кандидат в задачу (type:infra).

## 6. Обновление канона (режим B)

1. Апстрим fetch, diff от SHA из `CANON_VERSION.md`; rsync в `workflow/` с
   `--exclude docs/history` и сохранением проектного слоя: `project.json`,
   `PROJECT.md`, `CANON_VERSION.md`.
2. Поднять SHA и список нового в `CANON_VERSION.md`.
3. `python3 workflow/scripts/preflight --ci-main` — зелёный (ветка проекта = main
   по установленному порядку; для саб-веток — без `--ci-main`).
4. Коммит в main координатором (док-слой канона, прецеденты синков в истории).
