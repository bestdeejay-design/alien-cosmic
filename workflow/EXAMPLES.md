# EXAMPLES — примеры прогонов внутри этого репозитория

> Дата: 27.10.2026. Статус: research/draft, не канон.
> Примеры иллюстрируют **вариант C** из [WORKFLOW-VARIANTS.md](./WORKFLOW-VARIANTS.md).
> Имена модулей (`auth`) — условные заготовки общего слоя; в проектном слое координатор
> подставляет реальные модули своего проекта. Номера issues/PR — иллюстративные (#12, #45).
> До утверждения канона примеры — образцы оформления, а не инструкция к действию.

## 1. Полный прогон: задача size:M внутри одного модуля

**Исходное issue (создаёт координатор):**

```markdown
Title: [auth] Единая валидация токена в session middleware
Labels: agent:coder, type:bugfix, size:M, priority:high, env:staging,
        status:blocked   (зависимость #10 не закрыта)

## Задача
Убрать дублирование валидации токена: session middleware должен использовать
тот же валидатор, что и API-слой. Поведение для валидных/невалидных токенов не меняется.

## Зависимости (depends-on)
#10 — [auth] Паспорт модуля auth актуален

## Радиус аудита
Аудировать:
- src/auth/ — весь модуль
- Всё, что импортирует src/auth/validator (найти поиском по репозиторию)
- docs/modules/auth.md — паспорт модуля
- DEBT.md → записи с тегом модуля auth
НЕ аудировать:
- src/payment/, src/ui/ — вне зоны. Нужно выйти за радиус → question координатору.

## Ожидаемый результат
- PR в целевую ветку уровня test, файлы: только радиус выше
- Обновлён docs/modules/auth.md; DEBT.md — если найден новый долг
- Письмо о поставке комментарием в этом issue

## Ограничения
- Публичный интерфейс модуля не менять.
- Существующие тесты не ослаблять и не удалять.
```

**Хронология (labels + комментарии):**

```
День 1  Координатор: #10 закрыт → status:blocked снят, status:ready поставлен.
День 1  Исполнитель: status:in-progress, phase:audit; to:sz-2 уже его конкретный,
        GitHub Assignees не ставим — все агенты делят один аккаунт.

🔍 AUDIT — Issue #12
1. Что уже есть: validator.ts (API-слой), собственная проверка в session.ts:40-68.
2. Переиспользовать: validator.validate() покрывает оба случая, включая refresh-токены.
3. Сломается при изменении: session.ts импортируют 3 точки входа (перечислены);
   внешний интерфейс модуля не затрагивается.
4. Долг в зоне: D-014 (два способа валидации) — эта задача его и закрывает.
5. Паспорт модуля актуален? Нет: в паспорте не указан второй потребитель validator.
6. Непонятно: вопросов нет.

День 1  Architect (или координатор, если architect не назначен):
        ✅ AUDIT approved. П.5 — поправь паспорт в составе ACTION.
        Исполнитель: phase:research.

📚 RESEARCH — Issue #12
Вариант A: session.ts вызывает общий validator (удалить локальную проверку).
  Плюсы: один источник правды; закрывает D-014. Минусы: session становится синхронно
  зависим от конфига validator. Совместимость: высокая.
Вариант B: оставить обе проверки, вынести только общие константы.
  Плюсы: минимальный дифф. Минусы: долг остаётся, D-014 не закрывается.
Рекомендация: A — задача поставлена именно ради устранения дубля.

День 2  Architect: ✅ RESEARCH approved, вариант A.
        Исполнитель: phase:conclusion.

🎯 CONCLUSION — Issue #12
Решение:      session middleware использует общий validator; локальная проверка удаляется.
Почему:       закрывает D-014 (аудит п.4); переиспользование уже покрывает refresh-кейс (аудит п.2).
Отвергнуто:   вариант B — сохраняет дубль, ради которого заведена задача.
Что меняю:    src/auth/session.ts (удалить локальную проверку, вызов validator),
              тесты session на невалидный токен — добавить кейс refresh.
Что НЕ меняю: публичный интерфейс модуля и поведение для клиентов (ограничение issue).
Проверка:     существующий набор тестов модуля + новый кейс; ручная проверка на test-стенде.
Новый долг:   нет.

День 2  Координатор: ✅ CONCLUSION approved — GATE OPEN → phase:action.
День 2  Исполнитель: ветка от свежего main проекта → правки строго по conclusion →
        паспорт auth обновлён (второй потребитель validator, дата/issue указаны) →
        полный регресс проекта зелёный → PR #45 в уровень test (Closes #12).

🔧 ACTION (письмо о поставке) — Issue #12
PR: #45. Диапазон коммитов: <base>..<head>, кончик <hash>.
Что сделано: по conclusion, без отклонений. Паспорт модуля обновлён: да, auth.
DEBT.md: D-014 → resolved (#12). Красного нет. Чужие зоны не тронуты.

        Исполнитель: phase:verify, status:review. Координатор сливает PR в test
        (уровень test: self-merge исполнителем допустим по C1, здесь PR вёл координатор).
День 3  Ревьювер (не автор): чек-лист — бриф/код/документация/регресс + сверка с conclusion.
        ✅ approve.
        Координатор: промоушен того же SHA на staging (все условия §4.5 проверены),
        status:review + needs-human, сводка владельцу «что смотреть».
День 4  Владелец: приёмка. Координатор: status:done, issue закрыто.
        Mailbox проекта: одна строка-указатель на письмо о поставке и диапазон коммитов.
```

**Что показывает пример:** фаза не равна статусу; гейт ставит не исполнитель;
отвергнутая альтернатива зафиксирована; паспорт и DEBT обновлены в той же поставке;
в production путь лежит через промоушен того же коммита, а не новое слияние.

**Второй исход гейта (как выглядит отказ):**

```
Координатор: ❌ CONCLUSION rejected.
Причина: в «Что меняю» нет тестов, а ограничение issue требует не ослаблять существующие.
Действие: дополнить conclusion тестами и шагом проверки; phase остаётся conclusion.
Итерация правок: 1/2 (счётчик ведёт координатор с первого rejected — и на фазах, и на ревью).
```

## 2. size:S — одним комментарием

```
Issue: [docs] Опечатка в README модуля. Labels: agent:coder, type:docs, size:S,
       priority:low, env:test, status:ready.

Исполнитель (один комментарий):
  Мини-аудит: посмотрел README и паспорт модуля; других вхождений опечатки поиском нет.
  Conclusion: правлю одну строку; альтернатив нет; проверка — повторный поиск по репозиторию.
Координатор (ответ): ✅ approved — действуй.
Исполнитель: правка, письмо одной строкой (файл, как проверено), status:review.
Ревьювер/координатор: approve → done по правилам приёмки для docs.
```

Никаких `phase:*` для S не требуется: approve-комментарий координатора и есть гейт (вариант C §4.4).

## 3. Question-цикл (блокировка в фазе audit)

```
Исполнитель, фаза audit по #12, обнаружил: validator читает конфиг, которого нет в радиусе.
1. Создаёт issue #13 по шаблону question: кому agent:coordinator (переадресация — координатор),
   блокирует #12, вопрос: «конфиг X задаётся проектом или модулем?»,
   контекст: фаза audit, радиус не включает конфиг; варианты: (а) считает проект, (б) считает модуль.
2. В #12: status:blocked, комментарий «Blocked by #13 — не задан владелец конфига X».
   phase:audit не меняется (фаза заморожена).
3. Координатор в ближайший цикл мониторинга: отвечает в #13 (вариант а, со ссылкой на ADR),
   закрывает #13.
4. Исполнитель: снимает blocked (status:in-progress), продолжает audit с той же фазы.
   Если бы ответ менял уже принятый conclusion — повторный гейт phase:action у координатора.
```

Если адресат — внешний агент: координатор ставит на #13 флаг `blocked-external`
и включает вопрос в ближайший CONTINUE-пакет, который запускает владелец. Вопрос без
ответа два цикла мониторинга подряд уходит в сводку владельцу.

## 4. HOTFIX в production

```
Владелец/мониторинг: production-инцидент. Координатор объявляет HOTFIX (только он вправе).
Issue: priority:critical, env:production, размер по факту фикса.
Исполнитель: мини-аудит + conclusion одним комментарием (как S, при любом размере фикса),
радиус — только строки инцидента.
Гейт: координатор approve. Ревьювер: второй заход обязателен (HOTFIX ревью не отменяет),
но staging-остановка и soak пропускаются.
После поставки: в следующий рабочий цикл координатор создаёт issue на пропущенный
staging-регресс; созданный фиксом долг — строкой в DEBT.md в той же ветке.
```

Не HOTFIX: «фичу нужно быстрее обычного». Без инцидента/`priority:critical` — обычный цикл.

## 5. Два rejected подряд → эскалация

```
Ревью по #12: правки списком → status:rejected, «Итерация правок: 1/2». Исполнитель чинит → review.
Ревью повторно: существенные правки → status:rejected, «Итерация правок: 2/2».
Стоп: исполнитель больше не назначается на эту задачу автоматически.
Координатор: пересматривает бриф (радиус? размер занижен? критерии неполны?) —
либо правит issue и назначает заново с новым брифом, либо меняет исполнителя,
либо эскалирует владельцу, если проблема в самом решении.
```

Смысл: две неудачи подряд — сигнал о брифе, а не о старании. Третья попытка по тому же
брифу запрещена вариантом C (§4.7) — это правило действующего канона, возвращённое в процесс.

## 6. Внешний агент: LAUNCH и CONTINUE

**LAUNCH (публикует координатор, запускает владелец):**

```markdown
🚀 LAUNCH: coder — Issue #12 «[auth] Единая валидация токена»

## КТО ТЫ
Ты — coder, внешний узел **без записи в issues** (комментарии/labels ставить не можешь
и не должен пытаться). Можешь: читать пакеты владельца, коммитить и пушить только
свою ветку. Не можешь: главную и чужие ветки, мержи, PR без прямого указания.
Твой координатор — ZCode: он получает твою поставку по новому коммиту ветки,
ретранслирует письмо в issue и возвращает правки следующим CONTINUE.
Узнаём тебя по ветке поставки и подписи «Арена · сессия <дата-id>» в письме.

## ГДЕ ЧТО ЛЕЖИТ
- Репозиторий работы и ветка: укажет координатор в проектном слое.
- Issues и критерии приёмки: <ссылка на issue>; читать можно, писать нельзя.
- Борд: GitHub Project проекта, главный вид «01 Контроль».
- Регламент: AGENTS.md в корне проектного репозитория, далее AGENT_RULES.md.

## ЗАДАЧА

## ВХОДНЫЕ ДАННЫЕ

## РАДИУС АУДИТА
Аудировать: <модули/файлы>. НЕ аудировать: <что>. Выход за радиус — только question.

## СДАТЬ
- Фазы ARCA веди по шаблонам регламента; тексты фаз, которые узел с записью в issues

## ВЕТКА И РЕЖИМ (внешний — дословно)

Поставка = запушенная ветка + `docs/MAIL.md`; координатор ретранслирует письмо в issue.

## ОГРАНИЧЕНИЯ
<из issue>. Никогда не клади в issue/PR/комментарии секреты, креды и адреса

```

После публикации: `launch-ready` + пометка владельцу «пакет готов, нужен ручной запуск».

## 8. Сигналы: как выглядит ожидание между сессиями

```text
Исполнитель в issue #12, первой строкой комментария:
📬 DELIVERED #12 — поставка готова, ждёт ревью

Владелец/координатор у себя, сессию агента не держа:
$ scripts/wait-signal --issue 12 --match DELIVERED,BLOCKED,QUESTION --timeout 7200
📬 DELIVERED #12 — поставка готова, ждёт ревью     ← stdout, код выхода 0

Координатор открывает гейт, первой строкой комментария в #12:
🟢 GATE OPEN #12 — phase:action открыт

Исполнитель ждал именно его:
$ scripts/wait-signal --issue 12 --match "GATE OPEN" --timeout 3600
🟢 GATE OPEN #12 — phase:action открыт             ← код выхода 0
```

Полная таблица маркеров (DONE / BLOCKED / QUESTION / NEEDS-HUMAN / GATE OPEN /
REJECTED / DELIVERED), кто публикует и кто ждёт, — KNOWLEDGE_BASE §5.

## 9. Рой SZ: одна задача, пять ожидающих, один захват

```text
Координатор: issue #21 готов (status:ready, to:sz-pool, agent:coder).
Пять SZ припаркованы: каждые 90 секунд сканируют открытые задачи по labels
(status:ready + to:sz-pool + своя функция). Это именно скан, а не
`wait-signal --match READY`: READY — не маркер, labels сами по себе сигналом
не являются. wait-signal подключается, когда issue уже известен и ждут его
маркер, гейт или CI.

Кандидата видят SZ-2 и SZ-5 почти одновременно; обе перечитывают issue
целиком (свежесть!) и пытаются взять:
$ scripts/wait-signal --issue 21 --claim "SZ-2 / сессия 2026-10-27-b" --claim-as sz-2
✋ CLAIM #21 — взял: SZ-2 / сессия 2026-10-27-b        ← первой строкой в issue
CLAIMED …                                            ← stdout, код 0: работает SZ-2

$ scripts/wait-signal --issue 21 --claim "SZ-5 / сессия 2026-10-27-e" --claim-as sz-5
BUSY / LOST — задачу взял другой                      ← код 3: SZ-5 ждёт дальше,
                                                         labels не трогает
```

Захват optimistic (GitHub не даёт атомарного CAS): выиграл самый ранний
claim-комментарий; аренда держится heartbeat-комментариями, просроченную
координатор возвращает в `ready` — протокол KNOWLEDGE_BASE §5.1.

## 10. Парковочный промпт дежурной сессии (владелец вставляет один раз)

```markdown
🅿️ PARKING — дежурная сессия <роль/имя сессии>

## КТО ТЫ
Ты — <SZ-N / локальная сессия роли agent:<роль>>, узел с записью в issues.
Можешь: брать задачи по своему фильтру, ставить labels и маркеры, пушить ветки
поставок. Не можешь: брать чужие `to:*`, начинать ACTION до гейта, завершать
себя после одной задачи. Твой координатор — <роль/имя>; узнаём тебя по подписи
«— <роль> · сессия <id>» второй строкой каждого сигнального комментария.

## ГДЕ ЧТО ЛЕЖИТ
- Репозитории и борд: <ссылки>; главный вид борда — «01 Контроль».
- Регламент: AGENTS.md в корне, дальше AGENT_RULES.md и KNOWLEDGE_BASE.md.
- Скрипт ожидания: scripts/wait-signal в свежем клоне.

## КАКИЕ ЗАДАЧИ БРАТЬ
Открытые issues: ровно один `status:ready` + (`to:<ты>` или `to:sz-pool`)
+ твоя функция `agent:*`. Всё остальное — не твоё, даже если задача интересная.

## КАК ЖДАТЬ
1. Обнови клон и проверь `scripts/wait-signal --version` (версия + SHA-256
   должны быть свежими). Старый скрипт — сначала обновись, потом жди.
2. Сканируй свой фильтр каждые 60–120 секунд. Нашёл кандидата — перечитай
   issue целиком прямо перед действием (свежесть!), проверь зависимости
   и отсутствие чужого claim.

## КАК БРАТЬ И СДАВАТЬ
- Claim одной заменой: `status:ready → status:in-progress` (+ `to:sz-pool →
  to:<ты>`), затем `✋ CLAIM`. Ровно один `status:*` на issue всегда.
- Работа — ARCA по AGENT_RULES; движение показывай маркерами/heartbeat.
- Сдача: переход labels + `📬 DELIVERED` письмом. Блокер: `status:blocked`
  + `⛔ BLOCKED`. Вопрос: question-issue + `❓ QUESTION`.
- Сдал — **вернись в ожидание по этому же промпту**. Сессия не завершается;
  владелец в тебя больше не пишет, следующую задачу возьми с борда сама.
```

## 11. Одна сессия, две задачи подряд, владелец не участвует

```text
12:00 Владелец один раз вставил парковочный промпт в сессию SZ-2 и ушёл.
12:04 Координатор публикует #31: status:ready, to:sz-pool, agent:coder.
12:05 SZ-2 сканирует фильтр, перечитывает #31, claim: in-progress + to:sz-2.
13:10 SZ-2: 📬 DELIVERED #31, status:review. Возврат в парковку (не выход!).
13:40 Координатор публикует #32: status:ready, to:sz-2, agent:coder.
13:41 SZ-2 без единого сообщения владельца берёт #32 тем же циклом.
```

Именно п. «сдал → вернулся в ожидание → взял следующее» проверяется на приёмке
