# BUS — шина координации агентов на GitHub (v1.1; ядро — живые прогоны 27.10, словарь синхронизирован 03.11 и 05.11)

Одна шина для всех узлов: координатор, локальные сессии (со своими субагентами),
внешние агенты. Ни один узел не пишет другому напрямую — только через общий репозиторий.
Владелец не передаёт сообщения: он видит всё на борде.

## Узлы и адресация

| Узел | Как получает работу | Как сдаёт |
|---|---|---|
| Координатор (1) | слово владельца / маркеры шины | гейты, приёмка, задачи, решения |
| Локальная сессия (N, паркованная) | скан issues `label:<роль> + status:ready + to:*` каждые 60–120с | маркеры + ветка |
| Внешний агент (N) | launch/CONTINUE-пакет от владельца | пуш своей ветки + маркеры |
| Субагенты | поднимает узел сам | через своего родителя |
| QA-узел (зарезервирован, в пилоте не задействован) | назначает координатор для арбитражной проверки | вердикт `🔍 QA` в issue |

Адресация по роли узла — через `to:*` в issue. Отдельный адресат `to:infra`:
любое инфра-действие или запрос агента = issue с меткой `to:infra` в СВОЁМ репо
(нужна услуга — сервер/порт/домен/БД/доступ/бэкап; запись об изменении инфры —
юнит, порт, Caddy/compose, крон, DNS — можно закрыть сразу; сломал/чинит — инцидент).
Крон-пуллер координатора (*/15, `gh search --label to:infra` по всем репо) сводит
открытые на борд INFRA — projects/11 «журнал изменений» (журнал инфры) — и снимает закрытые.

## Сообщения шины (маркеры — первая строка комментария)

| Маркер | Кто | Значение |
|---|---|---|
| `🚀 LAUNCH` / `🔄 CONTINUE` / `🔥 HOTFIX` | координатор | задача узлу (самодостаточный пакет: КТО ТЫ / ГДЕ ЧТО ЛЕЖИТ / порядок) |
| `👀 READ #N — прочитал, проверяю свежесть` | исполнитель | подтверждение прочтения; claim отдельный |
| `🎯 CONCLUSION` | исполнитель | решение до кода (гейт для M/L, для S — компактно) |
| `✅ GATE OPEN` / `❌ GATE CLOSED — причина` | координатор | разрешение на ACTION / возврат |
| `🔁 REJECTED #N — <что возвращено одной фразой>` | координатор | возврат: гейт CONCLUSION или правки поставки (детали переходов — KNOWLEDGE_BASE §5) |
| `🏁 DONE #N — <итог одной фразой>` | координатор | финальная отметка после приёмки (не сама поставка; поставка — `📬 DELIVERED`) |
| `📬 DELIVERED #N — поставка готова, ждёт ревью` | исполнитель (комментарием в issue) / внешний узел письмом `docs/MAIL.md` в ветке | поставка: единый маркер сдачи обоих режимов; внешний узел без записи в issues ретранслируется координатором |
| `👤 NEEDS-HUMAN #N — <что решать>` | координатор | требуется решение владельца |
| `🔍 QA #N — OK/FAIL: <что проверил>` | QA-узел | вердикт проверки |
| `🔎 VERDICT #N — approve <sha7> / правки: <первый пункт>` | ревьювер (не автор) | вердикт ревью на точный коммит |
| `💓 HEARTBEAT #N — <фаза/прогресс>` | исполнитель | движение по задаче, продление аренды |
| `📣 PING #N — нет движения с <время>, подтверди, что жив` | координатор | stale-claim: первая проверка живости |
| `✅ CI #N — checks: <success\|completed-with-failures> <sha7>` | CI / `wait-signal` как наблюдение | завершение всех check-runs коммита |
| `✋ CLAIM #N — <кто>` | узел роя | захват уже увиденной задачи (optimistic; аренда + heartbeat) |
| `⛔ BLOCKED #N — причина` | любой | блокировка, узел паркуется |
| `❓ QUESTION #N — кому: <роль>` | любой | вопрос, ответ — обычным комментарием |
| `♻️ RECLAIMED #N — клейм снят по таймауту, был: <роль/сессия>` | координатор | перезахват зависшей задачи |
| `📌 DECISION #N — <суть решения>` | координатор/владелец | решение, обязательное к исполнению |

## Гарантии шины (проверены на прогонах)

1. **Скорость:** паркованный узел подхватывает задачу ≤120с после появления label; координатор отвечает на маркер ≤ одной минуты активной фазы. Ожидание — только блокирующим `wait-signal` (ETag-поллинг 60–120с, rate limit не расходуется).
2. **Свежесть:** перед КАЖДЫМ запуском ожидания — `git pull`; скрипты шины при ошибке (404/нет auth) падают ГРОМКО, не ждут молча; `wait-signal --version` печатает версию + SHA-256 (проверка клона машинна).
3. **READ ≠ CLAIM:** `👀 READ` — только подтверждение прочтения; захват задачи — `✋ CLAIM` (для роя) или label-переход. Полный канон словаря — KNOWLEDGE_BASE §5 комплекта воркфлоу.
4. **Claim-протокол (атомарность):** захват задачи — `scripts/wait-signal --claim`; GitHub не даёт compare-and-swap на labels, протокол честно optimistic (не «атомарный»). Единый источник — [KNOWLEDGE_BASE §5.1](./docs/KNOWLEDGE_BASE.md).
5. **Самовосстановление:** in-progress без движения дольше лимита размера → пинг координатора → ещё один интервал → `♻️ RECLAIMED`, задача возвращается в ready (аренда = 2× stale-лимита). Единый источник — [KNOWLEDGE_BASE §5.1](./docs/KNOWLEDGE_BASE.md).
6. **Конфликты:** два узла увидели одну задачу — берёт тот, чей claim первый по времени; второй перечитывает issue и паркуется. Единый источник — [KNOWLEDGE_BASE §5.1](./docs/KNOWLEDGE_BASE.md).
7. **Идемпотентность:** маркер никогда не публикуется дважды; перед действием узел перечитывает issue.
8. **Подпись узла:** все узлы могут работать под одним аккаунтом — личность живёт в подписи
   тела («— Роль · сессия/дата»). Комментарий/письмо без подписи не считается сообщением шины.
9. **Гигиена веток:** слитая ветка удаляется (после проверки merge-base); активные контуры
   и ветки на ревью не трогаются; неслитые замороженные — только по слову владельца.

## Интерактив для владельца

- Смотреть **борд** — там весь трафик в колонках; каждый маркер виден в issue.
- Вмешательство = один комментарий в issue (узлы на маркеры реагируют сами).
- Запуск новых узлов — единственное, что владелец делает руками (сессии поднимает только он), и один раз: парковочный промпт делает их автономными.

## Гигиена веток (обязанность координатора)

1. Ветка поставки удаляется сразу после слияния в main — проверка «целиком в main»
   (`merge-base --is-ancestor`) перед удалением обязательна.
2. Не удалять: активный контур исполнителя (платформа привязывает сессию к ветке),
   ветки на ревью, ветку тестового стенда.
3. Замороженные ветки с неслитыми коммитами не удаляются молча — только явным словом
   владельца (неслитая история — единственный носитель таких коммитов).
4. Агент работает от свежего origin/main (`fetch --prune` в начале сессии) — мёртвые
   ветки не должны попадаться на глаза и путать выбор базы.
