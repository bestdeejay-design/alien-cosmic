# PROTOCOL — общие правила работы агентов

Канон работы команды. Меняется только владельцем (через координатора — оформит правку).

## 1. Роли и полномочия

| Роль | Кто | Может | Не может |
|---|---|---|---|
| **Владелец** | bestdeejay-design | Всё: приоритеты, приёмка, смена протокола | — |
| **Координатор** | назначается владельцем на проект | Оформлять задачи (issue с брифом и критериями), назначать исполнителя и ревьювера, двигать статусы, сливать принятые поставки, вести борд, менять версию продукта | Принимать продуктовые решения за владельца |
| **Исполнитель** | назначается координатором (любой агент или сессия) | Работать только в своей ветке поставки по назначенной задаче | Писать в main, двигать борд, брать чужие/свои задачи |
| **Ревьювер** | назначается координатором; всегда — не автор работы | Проверять поставку до приёмки: бриф, код, документация, регресс. Вердикт — в issue | Ревьюить собственную работу |

## 2. Границы (не твоя зона — не трогай)

- **Версия продукта** — только координатор, только в main.
- **Борд, статусы, приёмки** — только координатор.
- **Сюжеты, кампании, новые механики** — только после явного GO владельца.
- **Замороженные зоны проекта** (если объявлены в репо проекта — например, стабилизированный код) — правки только по явному запросу владельца через координатора.
- **Секреты** — никогда в коде, письмах и документах; только в специальных каналах владельца.

## 3. Коммуникация

- Координатор ↔ агенты: mailbox проекта (append-only) и комментарии в issues.
- Несогласие с решением — письмом координатору, а не самодеятельностью в коде.
- Поставка, не сопровождённая письмом, не существует (не признаётся при ревью и слиянии).
- История — не переписывается: mailbox и письма append-only.

## 4. Старт новой (холодной) сессии — обязательная последовательность

1. Прочитать протокол (этот репозиторий) и статус `STATUS.md`.
2. Прочитать mailbox / статус-карточку проекта.
3. `git fetch --prune && git status -sb` — защита от протухшего локального git.
4. Нет назначенной задачи — работы нет: спросить координатора, не искать себе занятие.
5. Локальный git протух/откатился — восстановиться с origin, потери ноль, инцидент письмом координатору.

## 5. Качество

- Красный регресс на своей ветке — пуш откладывается: сначала сверка базы с origin/main, только потом свой код.
- Перед пушем: `git fetch`; main уехал — rebase + полный регресс заново.
- i18n (если в проекте): RU/EN синхронно, один ключ на оба языка.
- Комментарии в коде — только о том, чего код сам сказать не может.

## 6. Гигиена поставок и деплоя (владелец, 03.11.2026)

- **Маркер поставки уникален.** Версия/стамп/бейдж поставки идентифицируют её однозначно:
  два деплоя никогда не носят один маркер. Совпадение маркера = молчаливая перезапись
  чужого кода, запрещено.
- **Пост-деплой верификация.** Координатор после каждого деплоя сверяет хеши (md5/sha)
  ключевых файлов с ожидаемыми и целевой маркер на живом сайте/сборке. «Задеплоил» ≠
  «на проде моё».
- **Изменение валидатора/формата данных = миграция обязательна.** Если поставка меняет
  формулу пересчёта или формат сохранённых данных, существующие данные должны проходить:
  миграция в точке загрузки или толерантный приём. Гейт поставки — тест на РЕАЛЬНЫХ
  данных владельца, не на синтетике.
- **Красный регресс — сначала атрибуция (A/B).** Падающий тест прогоняется на базовом
  коммите без поставки: красный и там — среда/чужая незакоммиченная работа, не поставка.
  Вердикт ревью без атрибуции не принимается.
- **Мёртвые ветки.** Перед слиянием внешней ветки — трёхточечный дифф `main...branch`:
  пустой = ветка полностью покрыта main («мёртвая история»), не лить; удалить после
  подтверждения автора.
- **Деплой без карточки борда запрещён** (BOARD.md): карточка с ревью и приёмкой —
  единственное основание. Внепроцессный деплой = гарантированный откат + разбор в issue.

## 7. Миграции данных игроков (владелец, 03.11.2026)

Когда работа игры меняет формат сохранений, формулы пересчёта или смысл полей —
данные игроков мигрируют. Два равноправных канала, выбор за координатором:

- **Канал А — миграция в коде загрузки.** Продукт при чтении данных приводит их к
  текущей схеме (односторонне, с сохранением оригинала в backup). Плюс: работает у
  всех игроков сразу, часть обычной поставки. Минус: код миграции живёт вечно.
- **Канал Б — прямая правка данных (data-fix).** Координатор правит сохранения
  адресно: выгрузка → трансформация скриптом → запись, с бэкапом ДО и отчётом.
  Плюс: не ждёт переделки UI/панели, чинит точечно. Минус: разово, руками, только
  через координатора.

**Правила канала Б (без исключений):**
1. Бэкап выгруженных данных до правки — в защищённое место владельца, не в git.
2. Трансформация — версионируемым скриптом в репо проекта (не руками в консоли):
   тот же скрипт можно перепрогнать и получить тот же результат.
3. Сверка до/после по инвариантам (суммы, уровни, счётчики) — в отчёте поставки.
4. Пробный прогон на копии, запись — только после сверки.
5. Запись в хранилище — тем же API продукта (CAS/версионность), не прямой записью в БД, если API это позволяет.

**Общие правила обоих каналов:**
- Каждое изменение формата = номер версии схемы; потребители обязаны принимать
  все предыдущие версии или мигрировать (валидатор, отвергающий старое без
  миграции, — баг поставки, а не «старые данные»).
- Тест миграции — на реальных данных владельца; тест-кейсы фиксируются в поставке.
- Откат поставки учитывает данные: если новая схема уже записана игрокам, откат
  кода без обратной миграции ломает сейвы. Перед откатом — сверка версий схем.
